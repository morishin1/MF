# 内定通知PDF → 本人承諾 → Office（2026-10-28再構築）

## 対象と表示

作成済みPDFを正本として登録する追加経路。既存の条件書生成・社労士/LegalSign経路は、他の応募者では変更しない。
- HR：内定通知書準備中 → 内定承諾待ち → 内定承諾済み（Officeへ）
- Office：労働条件通知書準備中 → 本人確認待ち → 入社手続中 → 入社準備完了 → 入社済み
- 書類の送付・閲覧・受領確認・契約への同意・期限・取消は別の事実。旧 `applicant.status=accepted` を新しい内定承諾として読替えない。
- 新原本は応募者1名1フロー。Officeダッシュボードと入退社は同じ原本の一覧で、複製しない。入社済みは担当者による実入社の確認であり、社員名簿/アカウント登録ではない。
- HR詳細の「作成済みPDFで内定通知する」から `/hr/pdf-flow.html?applicantId=...` を開く。

## 正本・送付

アップロードPDFは5MBまで。サーバでPDFを検証し、版・SHA-256・送信先/送信元・確認文言を固定する。差替えは別版で旧リンクを失効し、承諾済みの内定通知書は変更しない。送信前に宛先・送信元・添付PDF・版・件名・本文・回答期限を確認する。同じ送信キーの再試行は二重送信しない。結果不明は成功と扱わず、むやみに再送しない。

本人リンクはURLのfragmentから取り、APIへはPOST本文だけで渡す。画面を開いただけでは承諾しない。最新版PDFを確認してから、表示された文言に明示同意する。PDFは保存・印刷できる。回答期限と閲覧期限は別で、期限後も有効な最新版リンクから保存・閲覧できるが、新しい回答は受け付けない。差替え・取消による旧リンク失効は期限後保存より優先する。リンクを受け取った人の回答であり、OTP・本人確認書類の審査・強い電子署名を提供するものではない。

労働条件通知の電子交付には本人の希望を確認した日時・記録を保存する。受領確認と契約への同意は選択・証跡を分離する。内定承諾で契約が成立する運用なら労働条件明示を後回しにしないよう、通知時期と文言を社労士へ確認する。参考：厚生労働省 https://www.mhlw.go.jp/bunya/roudoukijun/faq_kijyunhou_4.html 。この機能だけで法的な有効性を判定しない。

## 旧未承諾案内からの明示移行

旧URL送付済み/再送待ちでも、未承諾・未契約の対象者だけ移行できる。対象者・旧版・送付/閲覧記録と理由を確認し、「旧案内を無効化して新PDF方式へ」を明示実行する。旧PDF/送信/証跡は削除しない。旧リンク失効と新原本作成を同じトランザクションで行い、二重クリック・同時承諾・旧送信の競合では二重の有効経路を作らない。

承諾/辞退済み・契約証跡/社員連携あり・送信中/結果不明などは自動移行しない。過去データの一括変更は禁止。既存対象者全員が適格とは未確認。

## 初版で行わない操作

- 承諾後の採用全体の辞退・取消、社員名簿/アカウント自動作成は行わない。書類の「この案内を取消」は現在の未回答版だけを無効にし、準備へ戻す。
- 労働条件に同意できない本人は送信者へ連絡する。労働条件の不同意ボタンで採用全体を辞退にしない。
- 新方式の対象者は、旧メール画面での新規送信も停止する。旧送信テーブルにoffer_idがなく、安全な文書別限定ができないため。他候補者の旧メール機能と過去送信履歴は維持する。

## 安全な導入

`HR_PDF_FLOW` は既定OFF。新保存先・版・同意・引継ぎのSQLと専用private Storageが必要。本番SQLは本人がレビューして適用する。agentは本番・共有DB変更を行わない。2026-10-28 20:37 JSTの指示に基づく使い捨て隔離DBでの構文・不変性試験だけは別途検証対象とする。未適用・権限不足・読取失敗を「0件」や成功として扱わない。

架空データのPreview画面は共有済み。2026-10-28 20:43 JSTに本人がPreview待ち条件を撤回し、検証後の本番コード反映を指定。通常の公開は本人の2026-10-28 20:17–20:18 JST依頼の対象だが、実応募者への送信・契約通知・採用判断・実データ更新はテストで行わない。新しい権限拡張は別途判断。
