# Sales：提案 → CS → クロージングのバトンタッチ（db/141）

## 目的・担当
- **提案担当：藤本・中村** — dx.engerでマッチング、企業への提案
- **CS：中村・工藤** — 企業に連絡がつくまでフォローし、一次対応と進行判断
- **クロージング：池永・野澤** — 詳細ヒアリング、条件調整、面談、成約

氏名をコードに固定しません。管理者が「フォローの設定」で実際の社員IDをCS・クロージングチームに割り当てます。

## 標準フロー
1. マッチング確定：既存dx.enger→Salesの「提案待ち」。Slackのマッチング通知（既存仕様）。
2. 企業に提案：Salesが「CS対応中」に進み、**CS全員・クロージング全員へSlack共有**（今回追加）。送信1件につき1回。
3. CSへの正式割当：管理者または現担当が「CSに正式引継ぎ」。引継ぎ元・先、理由・判断・次の対応・日時をSalesに保存しSlack共有。
4. CSフォロー：不通、担当不在、再連絡、返信を電話・メール履歴へ記録。先方が連絡停止を希望したら追客停止。
5. CS接続：通話成功または返信が記録されたら、進行、詳細確認、保留、見送りを選択し、判断理由・次の対応を記録してSlack共有。
6. クロージングへ正式引継ぎ：接続実績＋進行判断を条件に担当（池永・野澤など）を選択し、理由と次の対応を必須で記録。Slackでチームに共有。
7. 詳細商談・面談・成約／見送りは引き続きSalesの既存機能で管理。

※提案送信だけで「CS対応中」には進みますが、**個人への正式割当は手動**です。引継ぎ履歴がないのに自動で特定の人が担当になったとは表示しません。

## 権限と安全装置
- 引継ぎはログインしたSalesユーザーのうち、現在の担当または管理者のみ。
- 引継ぎ先は、そのテナントの在籍・Sales利用可能者かつ設定したCS/クロージングチームのメンバーのみ。
- PostgreSQL RPCで担当更新、タスク再割当、追記専用引継ぎ履歴、活動記録を**1トランザクション**。
- 履歴は削除・書き換えず、いつ誰から誰へ渡したかを保持。
- CS→クロージングは連絡成功の実績とCS進行判断が必須。
- Slackには人材実名・連絡先・自由入力の引継ぎ理由を記載しない。詳細は権限のあるSales画面で確認。
- Slackは送信時刻で重複防止。送信失敗時の記録は残し、管理者が再共有可能。
