## 2. 入社準備の6ステップ（既存の判定への写像）

**4つ目の判定は作っていない。** 入社の進み具合は、すでに次の2か所で決まっている。6ステップはその結果を並べ替えるだけ。

- 手続きの段階: `lib/onboard-stage.js` の `computeStage`（一覧・通知・採用〜育成の流れが使う）
- キャリア: `lib/career.js` の `careerStatus`

「署名が済んだか」「書類の残りは何件か」の読み取りは `stageFlags` に切り出し、`computeStage` と 6ステップが同じものを使う。
`test/onboardsix.mjs` が、事実の組み合わせ 3,000 通り以上で、6ステップと段階が食い違わないことを確かめている。

| 6ステップ | 元になる既存の事実 | 状態 |
|---|---|---|
| ① 入社案内 | まだ持つ表が無い（案内の作成・送信・本人の確認） | **「データ未連携」**。進み具合に数えない |
| ② 労働条件・契約 | 段階 `conditions` → `advisor_review` → `signing`。締結と誓約書の同意が済めば完了（`gw_doc_orders`・`gw_sign_requests`・`gw_onboard_consents`） | 連携済み |
| ③ 本人情報・必要書類 | 段階 `intake` の本人の作業（入社情報の提出・必須書類・オリエンテーション確認） | 連携済み |
| ④ アカウント準備 | 段階 `intake` の社内の作業（チェックリストの社内項目。PC・Slack・勤怠など）。③ と並行 | 連携済み（MFA の設定状況・メール初期設定は未連携） |
| ⑤ キャリア設計 | `careerStatus`（未設定 / 本人確認待ち / 設定済み）。入社手続きが終わってから「要対応」にする（`lib/journey.js` の順と同じ） | 連携済み |
| ⑥ 最終確認 | ②〜⑤ がそろい、段階が `complete` のとき。導出（別に「確認した」を持たない） | 連携済み |

- 一覧は「完了率」より **次に誰が何をするか** を先に出す（経営者・本人・社労士・上長の番）。
- 各ステップの「開く」は、既存の画面（`admin-esign.html`・`admin-hr.html`・`admin-career.html`）へ。作業の場所は増やしていない。
- 事実が読めないときは、完了とも要対応とも言わず「データ未連携」にする。
- 給与・手当の金額と、給与入りの書面の中身は返さない（状態だけ）。
- 手続きが完了して30日を過ぎ、キャリアも済んだ人は一覧から外す（数だけ返す）。

## 4. 本番へ反映する前に

**未確認の migration を前提に、本番を変更しない。** 次の順で進める。

1. `db/check_salary_exposure.sql`（読み取りだけ）を流し、結果を確認する。あわせて `db/035`・`db/041`・`db/094` が本番に当たっているかを確かめる（`db/check_status.sql`）。
2. 経営者アカウントの二段階認証を登録する（**`/keiei` は登録前は開けない**。10/1 の強制日とは別に、常に必要）。
3. `db/099_owner_only.sql` → `db/100_hr_pay.sql` → 検査 → 環境変数 `HR_PAY_SPLIT=1` で再デプロイ → 給与が正しく出ることを画面で確認 → `db/101_hr_pay_clear.sql` → `db/102_contracts_pay_rls.sql` → `db/103_tool_access.sql`（詳細と元に戻し方は `docs/keiei-salary-separation.md` §2）。
4. 段階2（`SALARY_OWNER_ONLY=1` と `gw_can_see_salary` の差し替え）は、§3 の 5 のあと。

`test/sql/run.sh` は、PostgreSQL 上で 099〜103 を実際に流し、権限のある人・ない人の読み書きと安全装置を確かめる（106 件）。

## 5. 入社案内メール（次の段階）に向けた確認

現状、システムから本人へメールを送る仕組みは無い。次の点を教えていただければ、提供元に依存しない形（送信の窓口を1つにして、提供元は差し替え可能）で作る。

1. 会社のメールは何で運用しているか（Google Workspace か、ほかか）。差出人にしたいアドレス（例: `noreply@` か、経営者個人か）
2. 送信元ドメインの DNS（SPF・DKIM・DMARC）を、こちらの指示で設定できるか
3. 案内 URL の有効期限（案）: 初回 7 日・再送で更新。パスワードは本文に書かず、期限つきの設定用 URL だけを送る
4. 送った本文の確定版・送信日時・送信者・再送履歴・閲覧・提出の状況を残す（表は新設が必要）
