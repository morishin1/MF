# 提案後の連絡結果・NG分析

ENGERで提案後の連絡結果を記録し、Salesが同じデータを読んで分析する。企業・提案のマスタや同期キューを新設しない。

## 操作

1. 提案詳細の「連絡結果・理由・担当者」から対象の案件側／人材側企業を選ぶ。
2. 電話・メール・SMS、状況、理由、当社対応担当者、先方担当者、補足、根拠URL、次の対応と期限を保存する。
3. 当社担当者と記録者は別項目。記録者と記録日時はサーバーで確定する。
4. 提案のNGは既存の「見送り・失注」で記録する。企業全体のNGは折りたたみ内のリンクから既存の企業NG設定へ移動し、理由を入力する。既存の管理者・マネージャー権限を維持する。
5. 企業詳細にも最新50件の連絡結果を表示する。Sales分析ページから理由・担当者・期間・企業・先方担当者で絞り、行を開いて根拠へ戻る。

## データと権限

- 保存先は既存 `enger.company_touchpoints` の nullable JSONB `dx2_contact_result`（version 1）。既存行はNULLのまま。
- 企業IDは提案の正規IDを優先し、未設定の場合は既存の一意な企業名照合を利用。曖昧な企業は保存不可。人材側も既存の照合結果を使う。
- 提案に書き込める社内メンバーに限定。partnerは閲覧・保存不可。企業別読み取りも社内認証後に実行する。
- 新規記録はDBの制限ポリシーでanon/authenticatedの直接SELECTから除外する。認可済みサーバーだけが読む。
- 保存UUIDで同一内容の再送を一件にする。異なる内容での同一UUIDは拒否する。
- UPDATE/DELETEをDBで禁止。訂正は元の記録が分かる補足を付けて新規追加。監査ログは同一トランザクションで作る。
- この履歴がある企業の物理削除・履歴付け替えを伴う企業統合はトリガーで拒否される。通常の論理削除と異なり、統合・保持期限削除を行う際は別途履歴保持設計が必要。
- 新規記録は既存の接触成功・営業KPIの読み取りから除外し、専用一覧で集計する。未返信を未読／NGと推定せず、ステージやis_ngを自動変更しない。

## Salesとの集計契約

- `/api/sales/contact-results`、画面 `/sales/contact-results.html`（MF側PR）。Eightテナントかつ営業権限が必要。
- 連絡結果は対応日時、提案NGは現在見送り・失注の提案のstage_updated_atで期間集計。企業NGは現在is_ngの一覧で期間を適用しない。
- 連絡結果の件数は連絡記録数。提案NG件数や企業数とは区別する。
- 1,000件で表示を制限し、超過時は取得総数と表示件数を明示する。企業NGが1,000件を超える場合、全件の監査用途には別途ページングが必要。
- 過去のNG理由や担当者が空の行は「未記録」。提案NGの担当者は既存のcloser/proposer/owner、記録者は元の提案履歴で確認。古い企業NGは自由記述なので理由の表記揺れが残る。

## 導入と検証

2026-11-05に共有DB `htglvascsuqkixpmclwr` へ `20261105014952_dx2_contact_results.sql` 相当をapply_migrationで適用済み。再実行しない。Supabase側の記録バージョンはツールが付与するため、CLI同期時は履歴を照合する。

`supabase/tests/contact_results.sql` を実行し、未認証・一般認証の閲覧不可、service_roleでの読み取り、監査一件、更新・削除禁止、重複ID拒否を確認。テストはROLLBACKし実データを残さない。

アプリの展開順はMF（読み取り）→ENGER（入力）。アプリ本番未反映。入力検証、保存処理、認可、再送、集計のテストを追加。型検査・lint・ビルドと関連既存テストで確認する。

全体 `npm run check` は変更前から存在する `check-enger-workboard.mjs:14` の文言期待値（人材／本人・所属元）不一致で停止する。この変更で検査を弱めない。ブラウザからローカルプレビューへ接続できず、ログイン後の実画面操作は未検証。マージ前に認証付きプレビューで保存→再表示→Sales集計を確認する。

Gmailの「NG企業リスト」は通常の案件・人材メールも含むため自動NG移行しない。過去分の分類・名寄せ・理由確定は別工程。企業NG設定を追加の全送信経路に強制する変更やメール/SMS送信機能はこの変更に含めない。
