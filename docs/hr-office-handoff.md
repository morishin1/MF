# HR → Office 引き渡し（HR で条件承諾・正式契約まで → HR が確認して引き渡す → Office は入社書類から）

採用HR（`/hr`）と Office（`/admin-hr.html` ほか）の境界と、その UI/UX・運用です。
引き渡しは **自動ではなく、HR が承諾内容を確認して押したとき**に起きます（#102 の手動引き渡しの流れのまま）。

> 2026-10-19 から、正社員・パート・業務委託・スポットは、社労士の正式PDFで本人へ案内し、締結の証跡と版の照合を確かめてから引き渡します
> （書類タブの「契約手続き」。db/139）。詳しくは `docs/hr-contract-procedure.md`。育成枠と db/139 より前に送った版は、この文書の流れのままです。

> **2026-10-21：早期引き渡し（新フロー）を追加（PR A。機能フラグ `HR_OFFICE_INTAKE`、既定 OFF）。**
> 社長合格 → 条件ヒアリング → ［Officeへ引き渡す］で、条件手続き（社労士・本人の同意・契約）を Office へ早めに渡す流れです。
> **この文書の旧フロー（承諾・正式契約のあと `handoff_at`）はそのまま残ります。** どちらが当てはまるかは末尾の「早期引き渡し（新フロー）」を参照。
> **PR B（同フラグ）：新フローの人の契約手続き（採用条件・社労士・正式PDF・本人の同意・LegalSign・社員登録へ進める準備）は Office 人事・労務の「HRからの引き継ぎ」で進めます。**

## 1. ルール

| # | ルール |
|---|---|
| 1 | 本人が採用条件を承諾しただけでは、Office へは**自動送信しない**。HR が承諾内容・条件・入社予定日を確認して［承諾内容を確認してOfficeへ引き渡す］を押したときに、Office の「HRから引き渡し」に載る。 |
| 2 | **正式契約が必要**（`formal_contract_required = true`）な版は、`accepted_at` と `formal_signed_at` が揃ってから引き渡せる。LegalSign（URL 登録 → 本人へ案内 → 署名済み）は **HR 側**の採用条件・契約フローとして完了させ、完了後に引き渡す。Office には移さない。 |
| 3 | 正式契約が**不要**（`formal_contract_required = false`）な版は、本人の承諾後、HR の確認でそのまま引き渡せる。 |
| 4 | **育成枠（training）は Office へ引き渡さない**。`formal_contract_required` の値に関係なく、LMS・育成開始（HR で進める）。DB でも止める（db/133 の `offer_type <> 'training'`）。 |
| 5 | `handoff_at` / `handoff_by` は「**誰が・いつ**Office へ引き渡したか」の監査記録。一度入ったら変えられない（db/133 のトリガー）。 |
| 6 | Office の「HRから引き渡し」には、`handoff_at` が入った人**だけ**が載る。承諾済みだけでは載らない。 |
| 7 | Office の入社の流れは、**HRで正式契約まで完了 → 入社書類 → アカウント・端末 → オリエンテーション → 入社完了**。「正式契約」は Office のステップではない（HR で完了済み）。 |
| 8 | 書類は**再登録させない・二重管理しない**。履歴書・職務経歴書・スキルシート・内定通知書・労働条件通知書・承諾済みPDF は、HR が登録した原本を Office が**閲覧専用**で参照する（登録・差し替え・削除は HR だけ）。 |
| 9 | HR と Office の両方で、現在のフェーズと次にやること（NEXT ACTION）を表示する。 |

> 添付仕様（HR → Office 切替ルール・UI/UX・運用マニュアル）のうち、「承諾したら Office へ自動引継ぎ」「正式契約からが Office」は採用していません。
> 理由：引き継ぎ忘れ・二重登録を防ぐには自動が良い、という考えもありますが、承諾内容の最終確認と、正式契約（LegalSign）の完了を HR が確かめてから渡す運用にするため。
> 二重登録は、引き渡し（`handoff_at` は一度だけ）・社員登録の確定（`employee_id` が空のときだけ）をサーバで止めて防ぎます。

## 2. 状態の遷移（HR → Office）

| 段階 | HR（応募者の詳細） | Office（入退社） | 引き渡し・社員登録 |
|---|---|---|---|
| 条件承諾待ち（送付済み） | 条件承諾待ち | 載らない | できない |
| **条件承諾済み**（本人が承諾） | 大きく「条件承諾済み」＋承諾日・採用区分・入社予定日・条件通知書確認済み・正式契約 必要／不要・正式契約の状況 | **載らない**（書類も見られない） | できない（社員登録は 409 `handoff_required`） |
| 正式契約が必要：未対応 → 案内済み | NEXT ACTION［正式契約へ］→［正式契約済みにする］ | 載らない | 引き渡せない（409 `formal_required`） |
| 正式契約済み（署名済み） **または** 正式契約が不要 | NEXT ACTION［承諾内容を確認してOfficeへ引き渡す］ | まだ載らない（HR が引き渡すまで） | 引き渡せる |
| **引き渡し済み**（`handoff_at` あり） | 「Office引き渡し済み」・引き渡した日時と人・［Officeで確認する］ | **「HRから引き渡し」に載る**。HRで正式契約まで完了 → 入社書類 …／書類を閲覧専用で見られる | 社員登録へ進める |
| 社員登録済み（`employee_id` あり） | 本採用（社員登録）完了 | 「HRから引き渡し」から外れ、入社手続きに「HRから引き渡し」の印 | 確定は一度だけ（409 `already_advanced`） |
| 育成枠（承諾済み） | 「条件承諾済み」＋ LMS・育成開始（HR） | 載らない（`handoff_at` が入っていても出さない） | 引き渡せない（409 `training`） |

この表は `test/hrhandoffflowapi.mjs`（本物のハンドラをつないだ状態遷移テスト）が各段階で確かめています。

## 3. 画面

### HR（`/hr/applicants.html`）

- 書類タブ：応募書類（履歴書・職務経歴書・スキルシート・その他）と、採用条件書類（内定通知書・労働条件通知書・承諾済みPDF）の状態
  （未登録／登録済み／送付済み／本人確認済み／承諾済み）。
- 条件承諾後は、応募者の詳細の上部に大きく **「条件承諾済み」**：
  承諾日・採用区分・入社予定日・条件通知書 確認済み・正式契約（必要／不要）・正式契約の状況（未対応／案内済み／署名済み）・次の手続き。
  引き渡し済みなら「引き渡し済み」と、引き渡した日時・人。
- 正式契約が不要、または必要で署名済みになったら、NEXT ACTION に［承諾内容を確認してOfficeへ引き渡す］が出る。
  押すと**最終確認**が開く（承諾日・入社予定日・条件通知書・正式契約の内容、「引き渡した人と日時が記録され、あとから取り消せません」、確認のチェック）。チェックして［確認して Office へ引き渡す］で確定。
- 正式契約が必要な間は［正式契約へ］（LegalSign の URL 登録 → 本人へ案内 → 署名済み。HR で完了させる）。育成枠は LMS・育成開始（Office へは渡さない）。

### Office（`/admin-hr.html`、入退社）

- **HRから引き渡し**：引き渡された人だけ。氏名・区分・職種・条件承諾日・入社予定日・労働条件通知書の確認・引き渡した日時と人、
  「HRで正式契約まで完了（正式契約：署名済み／不要）」の印と、入社の流れ（4つ）・NEXT ACTION。
  1. 入社書類 → 2. アカウント・端末 → 3. オリエンテーション → 4. 入社完了
- ［社員登録へ］（既存の社員登録の画面。条件は引き渡した版から事前入力）。Office に LegalSign の操作は無い。
- ［採用時書類を見る］：HR で登録した原本を見るだけ（再アップロード・差し替え・削除の入口は無い）。
- 入社予定の一覧：「HRから引き渡し」の印と、［入社書類］などの段階を先頭に添えた NEXT ACTION（HR を通らない人にも同じ言い方）。
- 入社手続きの詳細に **「HRから引き渡し」タブ**：引き渡された情報 / 採用時書類（HRから引き渡し・閲覧専用）/ 入社・契約書類（既存の段階の状態）。

## 4. 日々の運用（手順）

**HR 担当**
1. オファーを作り、内容（条件通知書PDF）を確認して本人へ送る。履歴書・職務経歴書・スキルシートなどの原本は、HR の「書類」タブに登録しておく。
2. 本人が承諾すると、応募者の詳細の上部に「条件承諾済み」が出る。承諾内容・条件・入社予定日を確認する。
3. 正式契約が「必要」なら、［正式契約へ］：LegalSign の URL を登録 → 本人へ案内 → 署名が終わったら［正式契約済みにする］。
4. ［承諾内容を確認してOfficeへ引き渡す］→ 最終確認 → 引き渡し（社長・管理者・人事。採用担当だけの人は、引き渡せる人へ頼む）。
5. 育成枠は引き渡さず、LMS・育成開始へ。

**Office 担当（人事・労務＝社長・管理者・人事）**
1. 通知「入社準備：HRから引き渡し」か、入退社の「HRから引き渡し」で、引き渡された人を見つける。
2. ［社員登録へ］で社員登録（既存の画面）。入社書類の依頼が始まる。
3. 入社書類 → アカウント・端末 → オリエンテーション の順に進める（詳細の「HRから引き渡し」タブで、採用時書類と入社・契約書類を分けて確認できる）。
4. すべてそろったら入社完了。

## 5. 仕組み（新しい SQL は db/135 だけ）

- 引き渡し：`PATCH /api/hr/offers { id, action: "handoff" }`。`canAdvanceHire`（社長・管理者・人事）。
  承諾済み・取り消し／辞退でない・育成枠でない・正式契約が必要なら署名済み・社員登録前、を確かめてから `handoff_at` / `handoff_by` を一度だけ書く。
  二度押しても変わらない（`already: true`）。タイムライン `office_handoff`・監査ログ `hr.offer_handoff`・Office の人事・労務への通知。
- Office のキュー：`GET /api/hr` の `handoffs`（`handoff_at` の入った版だけ。承諾済みだけの人・育成枠は出さない）。
  出す項目は `lib/hire-handoff.js` の許可した項目だけ。氏名・メール・電話・職種・雇用区分・入社予定日など、入社準備に必要な情報を再入力なしで引き継ぐ。給与・承諾の IP・LegalSign の URL は出さない。
- Office の入社の流れ（4つ）：`lib/hire-flow.js`。既存の段階（`lib/onboard-stage.js` の `computeStage`）の事実を並べ直すだけで、第3の判定は作らない。
- 書類の閲覧専用：`api/hr/documents.js`（応募書類）・`api/hr/offers`（`GET ?id=…&file=notice|accepted`。条件通知書PDF・承諾済みPDF）。
  Office の人事・労務（採用HRの権限が無い人）は、service role で読むため、次を**API で必ず確かめる**：
  ① 同一テナント ② 引き渡し済み（その応募者に `handoff_at` の入った版がある）③ Office の人事権限（`canOfficeHr`）④ 対象の応募者本人の書類だけ。
  PDF は給与・報酬が入るので `canSeeSalary` の人だけ。登録・差し替え・削除・PDF の生成は 403。保管済みのものを読むだけ。見たことは監査ログ（`via: office`）。
- 社員登録（`api/hr/applicants/advance.js`）：Office の人事は採用HRの RLS を持たないことがあるため、認可のあとに service role で読み書きする。その前に、順に確かめる：
  ① 認可（`canAdvanceHire`。通らなければ service role を作らない）② `tenant_id` ③ 二重登録（`employee_id` 済みなら 409）④ 承諾済み
  ⑤ `handoff_at`（409 `handoff_required`）⑥ 正式契約（必要なら署名済み。409 `formal_required`）⑦ 本人が承諾した版がある（409 `acceptance_required`。2026-10-21 PR B）
  ⑧ 早期引き渡しの人は Office の確認（`handoff_at`）が要る。確定は `employee_id` が空のときだけ書く。
  db/133 が無い環境・区分の無い従来の合格通知・育成枠は、承諾した版があれば、これまでどおり進める。

## 早期引き渡し（新フロー。db/143・PR A）

社長が合格を判断した直後に、HR が候補者の希望条件をヒアリングし、［Officeへ引き渡す］で**条件手続きそのもの**を Office へ渡す流れです
（要件定義 2026-10-21「HR→Office への引き継ぎ」）。**引き渡しは本人の条件承諾・正式契約・社員登録ではありません。**

### どちらの流れになるか（自動では移さない）

| 応募者 | 流れ |
|---|---|
| `gw_hr_ceo_decisions` の**最新の社長判断が合格**で、`gw_hr_offers`（オファーの版）が**1つも無い** | **新フロー**（この節） |
| それ以外（既存の「内定」〔例：オファーの版がある3名〕・合格の確定記録が無い人・`accepted`／`done`・`handoff_at` あり） | **旧フロー**（この文書の 1〜5 章と `docs/hr-contract-procedure.md`。HR で契約手続き → `handoff_at`） |

- 過去の合格を `gw_hr_ceo_decisions` へ書き足すこと（backfill）はしない。db/143 は既存の行を1行も変えない。
- 判定は `lib/hr-office-intake.js`（`intakeStateOf`）と db/143 の trigger（`gw_hr_office_intakes_check`）が同じ条件で行う。

### 流れ

1. **社長本人が合格を判断**（CEO REVIEW／応募者の採用判断）。`decision = hired` を書けるのは `canDecideHire`（社長・管理者）だけ。
   **応募者の状態に関係なく**確かめる（フラグに関係なく。以前は「社長判断待ち」以外の状態から採用担当が合格にできた）。
   フラグ ON のとき、判断者・日時・応募者ID を `gw_hr_ceo_decisions`（追記だけ）に記録する。DB でも社長・管理者以外は記録できない。
2. HR の表示は **「社長合格／条件ヒアリング待ち」**（既存の「内定」「条件作成中」「条件承諾待ち」は書き換えない）。NEXT ACTION［条件ヒアリングを記録］。
3. **条件ヒアリング**（`gw_hr_hearings`。給与は `gw_hr_hearing_pay`）：採用区分・職種・予定業務・希望入社日・勤務地・リモート・週の日数・週の時間・
   契約期間・希望報酬（必須）、手当・その他（任意）。分からない項目は **「未確定／Officeで確認」**（値と両方は 400。推測値を入れない）。
   - 希望額は「候補者希望」。会社が決めた額は「社内承認済み」（経営者 `canDecideSalary` だけが入力）。給与は `canSeeSalary` の人だけが入力・閲覧（DB も `gw_can_see_salary`）。
   - 必須項目が足りなければ「条件ヒアリング不足：…」（409）。人事担当の内容確認（`confirmHearing`）が要る。直すと確認は外れる。
   - 未確定の項目を残して渡すには、**社長・管理者の承認と理由**（`approveHearingException`）。
4. **［Officeへ引き渡す］**：確認のモーダル（引き渡す情報・Office担当・未確定項目）で確定。`gw_hr_office_intakes` に**一度だけ**記録
   （部分一意索引。二度目・同時押し・API の直呼びは 409。同じ操作の送り直し＝同じ `clientRequestId` は最初の結果）。
   履歴は `gw_hr_office_intake_events`（追記だけ）・選考タイムライン・監査ログ。
5. HR の一覧は **「Officeへ移動済み」タブ**（選考中・業務委託から外れる。氏名・採用区分・Office の状態・Office担当・引き渡し日時・次アクション）。
   Office で辞退・不成立（`office_status = withdrawn`）になったら「終了」。
6. 引き渡しても `gw_hr_applicants.status`・`decision`・`employee_id`、`gw_hr_offers`（`accepted_at`・`formal_signed_at`・`handoff_at`）は**変わらない**。
   社員登録のガード（`api/hr/applicants/advance.js`）もそのまま（承諾・正式契約・既存の `handoff_at` が無ければ社員登録へ進めない）。
7. 引き渡したあと HR からは：状態の変更（手動・一括）・オファーの作成・削除はできない（409 `moved_to_office`／`has_contract_history`）。参照はできる。

### Office の手続き（PR B）

引き渡しを受けた人は、**Office 人事・労務の「HRからの引き継ぎ」**（入退社 `/admin-hr.html` の上。Office ホームにもカード）で進めます。
HR 内にあった契約手続きの責任画面を Office へ移しました（**新フローの人だけ**。旧フローの人は HR のまま）。

1. 一覧：候補者・採用区分・希望条件・採用担当・Office担当・状態・NEXT ACTION・期限だけ。状態（9つ）で絞り込める。引き渡した人は**1件だけ**
   （旧来の「HRから引き渡し」〔`handoff_at`〕には重ねない）。
2. 詳細（右のドロワー）：上に NEXT ACTION と主ボタン1つ。下は折りたたみ（引き継ぎの内容／希望条件／面談の結果／応募書類／採用条件／契約手続き／履歴／その他の操作）。
   面談の結果・希望条件・履歴書・職務経歴書・スキルシートは**閲覧専用**（HR で登録した原本。再アップロードしない）。
3. ［受領して着手］（一度だけ。担当が無ければ自分）→ **会社の採用条件**（本人へ提示する正式な条件。候補者の希望とは別）を作る
   → **確定は経営者だけ**（給与・報酬を決めるため。`canDecideSalary`。人事は条件の作成・書類の手続きまで）
   → 社労士へ依頼（依頼文の下書き → 自分で送って［依頼済みにする］）→ 正式PDF を受け取る（版・SHA-256）→ 照合して承認（給与を見られる人）
   → LegalSign の登録（または例外ルート）→ **本人専用URLを発行して手で送り［送付済みにする］**（Office からメールは送らない）
   → 本人の同意（本人のページ。既存）→ 締結の記録（証跡。社長・管理者・人事）→ **［社員登録へ進める準備］**（既存の `handoff_at` を書く。HR の［Officeへ引き渡す］と同じ処理）
   → ［社員登録へ］（既存の admin-onboard.html）→ 入社書類・アカウント・端末・オリエンテーション（入退社）→ ［入社完了にする］（社員登録のあとだけ）。
4. **辞退・不成立**：理由が要る。まだ同意していない本人専用URLは無効にする。引き渡し・版・正式PDF・履歴は消さない。HR では「終了」。社員登録へは進めない。
5. **差し戻し**（誤って引き渡したとき）：社長・管理者だけ・理由が要る・**採用条件の版を作る前だけ**。引き渡しの行は消さず `returned_*` を記録。
   ヒアリングは確認前の写しを作り直すので、HR で確かめ直して引き渡し直す（新しい引き渡しの行。履歴は2件になる）。

#### 状態（9つ）は事実から決める

`lib/hr-office-intake.js` の `officeStatusOf`（HR の一覧・詳細と Office が**同じ関数**。画面ごとに手で持たない）。
保存してある `office_status` は、事実から決められない段階（受領・辞退／不成立・完了）の補助と、一覧の絞り込みのための写し（操作のたびにサーバが書く）。

| 状態 | 事実 |
|---|---|
| 未着手 | 受領の前 |
| 条件整理中 | 受領した〜会社の採用条件を確定する前 |
| 社労士依頼中 | 条件を確定した・社労士へ依頼する／差し戻した PDF の修正を依頼する |
| 正式PDF受領待ち | 依頼済み〜受領・照合・承認・LegalSign の登録〜本人へ案内する前 |
| 本人承諾待ち | 本人へ案内した〜同意の前（期限は回答期限） |
| 契約手続き中 | 本人が同意した〜締結の記録・［社員登録へ進める準備］の前 |
| 入社準備中 | `handoff_at` が入った・社員登録した（入社書類・アカウント・端末・オリエンテーション） |
| 完了 | Office が［入社完了にする］（社員登録のあとだけ。DB でも） |
| 辞退・不成立 | Office が理由つきで記録（本人がページで辞退したときも、この状態として出し、記録を促す） |

#### 権限（Office の API `api/hr/office-intakes.js`）

先に確かめてから service role で HR と同じ関数（`lib/hr-offer-ops.js`・`lib/hr-contract-ops.js`）を呼ぶ：
① Office の人事・労務（`canOfficeHr`。採用担当だけ・経理だけ・Office 権限なしは 403）② 二段階認証 ③ 機能フラグ ④ テナント（別の会社は 404）
⑤ 差し戻していない引き渡しがある応募者だけ・版／正式PDF はその応募者のものだけ（別の応募者の ID は 404）⑥ 状態（受領前・辞退／完了のあとは断る）
⑦ 給与：希望額・会社の給与・条件PDF・正式PDF は `canSeeSalary` の人だけ。給与を入れる・条件を確定するのは `canDecideSalary`（経営者）。

| 操作 | 誰が |
|---|---|
| 一覧・詳細・受領・担当・採用条件の作成と修正（給与なし）・社労士への依頼・PDF の受領・LegalSign の登録・本人専用URL・辞退／不成立・入社完了 | Office の人事・労務（`canOfficeHr`） |
| 給与・報酬を入れる・採用条件の確定 | 経営者（`canDecideSalary`） |
| 正式PDF の照合・承認／差し戻し・PDF を開く | 給与を見られる人（`canSeeSalary`） |
| 締結の記録・［社員登録へ進める準備］・社員登録 | 社長・管理者・人事（`canAdvanceHire`） |
| HR への差し戻し | 社長・管理者 |

#### HR からは見るだけ

引き渡したあと、HR の版・契約手続きへの**書き込みは 409 `moved_to_office`**（`api/hr/offers`・`api/hr/offers/contract` の作成・更新・確定・URL・送付・社労士・正式PDF・締結・引き渡し）。
読むのはよい（契約手続きのカードはボタンなしの閲覧専用 `movedToOffice: true`）。DB でも、画面から直接（authenticated）は引き渡し済みの人の版を足せない・変えられない（db/144）。

#### 社員登録のガード（`advance.js`。フラグに関係なく効く）

既存の ①〜⑥ はそのまま。加えて ⑦ **本人が承諾した版（`accepted_at` のあるオファー）が無ければ 409 `acceptance_required`**
（以前は版が無いと ⑤⑥ が素通りし、`status=accepted` だけで社員登録へ進めた）。完了（complete）も `status=accepted` と同じ確かめをする。
⑧ 早期引き渡しの人は、区分に関係なく承諾した版に `handoff_at` と（要るなら）`formal_signed_at` が要る。辞退・不成立のあとは 409。

### 機能フラグ

| 設定 | 内容 |
|---|---|
| 環境変数 `HR_OFFICE_INTAKE=1` | 新フローを使う（一覧の「Officeへ移動済み」タブ・ヒアリング・引き渡し・社長判断の確定記録）。db/143 が要る |
| 未設定（**既定 OFF**） | 画面に新フローは出ない。新しい書き込み（`saveHearing`・`confirmHearing`・`approveHearingException`・`officeHandoff`）は 409 `intake_disabled` |

**PR A・PR B が Preview で通しの動作確認ができるまで、本番では ON にしない**（タブだけ切り替わって Office で契約処理できない状態にしない）。
OFF のときは Office の「HRからの引き継ぎ」（一覧・ホームのカード）も出さず、Office の API は `{ enabled:false }`／409 を返す。

### フラグに関係なく効く安全装置（既存の穴を塞ぐ）

- 合格（`decision = hired`）は `canDecideHire` だけ（API。DB でも画面から直接の書き込みは `gw_hr_applicants_guard` が止める）。
- 一括・手動の状態変更（`api/hr/applicants/bulk.js`・`detail.js` の setStatus・本体の更新）で、承諾済み（accepted）・完了（done）へは変えられない。
  合格の前に合格通知の段階（offer_*）へは進めない（一括では常に不可）。社員登録済み・Office へ引き渡し済みの人は動かさない。
  一括で社長判断待ちを出入りできるのは社長・管理者だけ。社長合格の人は一括では「辞退」「募集終了」へだけ。1人でも当てはまれば何も変えずに 409（`lib/hr-state-guard.js`）。
- 削除：オファーの版（`handoff_at` を含む）・社労士への依頼・正式PDF・社長判断・ヒアリング・早期引き渡しのある応募者は削除できない（409 `has_contract_history`。
  DB でも `gw_hr_applicants_guard` と新しい表の `on delete restrict`）。選考を終えるときは「辞退」「見送り」「募集終了」。
- DB（db/143 適用後）：画面から直接（authenticated）の承諾済み・完了・`employee_id`・社長以外の合格・引き渡し済みの人の状態変更を止める。サーバの流れ（本人の承諾・社員登録＝service role）は止めない。
