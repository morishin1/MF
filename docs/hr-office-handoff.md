# HR → Office 引き渡し（HR で条件承諾・正式契約まで → HR が確認して引き渡す → Office は入社書類から）

採用HR（`/hr`）と Office（`/admin-hr.html` ほか）の境界と、その UI/UX・運用です。
引き渡しは **自動ではなく、HR が承諾内容を確認して押したとき**に起きます（#102 の手動引き渡しの流れのまま）。

## 1. ルール

| # | ルール |
|---|---|
| 1 | 本人が採用条件を承諾しただけでは、Office へは**自動送信しない**。HR が承諾内容・条件・入社予定日を確認して［承諾内容を確認してOfficeへ引き渡す］を押したときに、Office の「HRから引き渡し」に載る。 |
| 2 | **正式契約が必要**（`formal_contract_required = true`）な版は、`accepted_at` と `formal_signed_at` が揃ってから引き渡せる。LegalSign（URL 登録 → 本人へ案内 → 署名済み）は **HR 側**の採用条件・契約フローとして完了させ、完了後に引き渡す。Office には移さない。 |
| 3 | 正式契約が**不要**（`formal_contract_required = false`）な版は、本人の承諾後、HR の確認でそのまま引き渡せる。 |
| 4 | **育成枠（training）は Office へ引き渡さない**。`formal_contract_required` の値に関係なく、LMS・育成開始（HR で進める）。DB でも止める（db/133 の `offer_type <> 'training'`）。 |
| 5 | `handoff_at` / `handoff_by` は「**誰が・いつ**Office へ引き渡したか」の監査記録。一度入ったら変えられない（db/133 のトリガー）。 |
| 6 | Office の「HRから引き渡し」には、`handoff_at` が入った人**だけ**が載る。承諾済みだけでは載らない。 |
| 7 | Office の入社の流れは、**HRで正式契約まで完了 → 入社書類 → アカウント・端末 → オリエンテーション → 入社完了**。「正式契約」は Office のステップではない（HR で完了済み）。 |
| 8 | 書類は**再登録させない・二重管理しない**。履歴書・職務経歴書・スキルシート・内定通知書・労働条件通知書・承諾済みPDF は、HR が登録した原本を Office が**閲覧専用**で参照する（登録・差し替え・削除は HR だけ）。 |
| 9 | HR と Office の両方で、現在のフェーズと次にやること（NEXT ACTION）を表示する。 |

> 添付仕様（HR → Office 切替ルール・UI/UX・運用マニュアル）のうち、「承諾したら Office へ自動引継ぎ」「正式契約からが Office」は採用していません。
> 理由：引き継ぎ忘れ・二重登録を防ぐには自動が良い、という考えもありますが、承諾内容の最終確認と、正式契約（LegalSign）の完了を HR が確かめてから渡す運用にするため。
> 二重登録は、引き渡し（`handoff_at` は一度だけ）・社員登録の確定（`employee_id` が空のときだけ）をサーバで止めて防ぎます。

## 2. 状態の遷移（HR → Office）

| 段階 | HR（応募者の詳細） | Office（入退社） | 引き渡し・社員登録 |
|---|---|---|---|
| 条件承諾待ち（送付済み） | 条件承諾待ち | 載らない | できない |
| **条件承諾済み**（本人が承諾） | 大きく「条件承諾済み」＋承諾日・採用区分・入社予定日・条件通知書確認済み・正式契約 必要／不要・正式契約の状況 | **載らない**（書類も見られない） | できない（社員登録は 409 `handoff_required`） |
| 正式契約が必要：未対応 → 案内済み | NEXT ACTION［正式契約へ］→［正式契約済みにする］ | 載らない | 引き渡せない（409 `formal_required`） |
| 正式契約済み（署名済み） **または** 正式契約が不要 | NEXT ACTION［承諾内容を確認してOfficeへ引き渡す］ | まだ載らない（HR が引き渡すまで） | 引き渡せる |
| **引き渡し済み**（`handoff_at` あり） | 「Office引き渡し済み」・引き渡した日時と人・［Officeで確認する］ | **「HRから引き渡し」に載る**。HRで正式契約まで完了 → 入社書類 …／書類を閲覧専用で見られる | 社員登録へ進める |
| 社員登録済み（`employee_id` あり） | 本採用（社員登録）完了 | 「HRから引き渡し」から外れ、入社手続きに「HRから引き渡し」の印 | 確定は一度だけ（409 `already_advanced`） |
| 育成枠（承諾済み） | 「条件承諾済み」＋ LMS・育成開始（HR） | 載らない（`handoff_at` が入っていても出さない） | 引き渡せない（409 `training`） |

この表は `test/hrhandoffflowapi.mjs`（本物のハンドラをつないだ状態遷移テスト）が各段階で確かめています。

## 3. 画面

### HR（`/hr/applicants.html`）

- 書類タブ：応募書類（履歴書・職務経歴書・スキルシート・その他）と、採用条件書類（内定通知書・労働条件通知書・承諾済みPDF）の状態
  （未登録／登録済み／送付済み／本人確認済み／承諾済み）。
- 条件承諾後は、応募者の詳細の上部に大きく **「条件承諾済み」**：
  承諾日・採用区分・入社予定日・条件通知書 確認済み・正式契約（必要／不要）・正式契約の状況（未対応／案内済み／署名済み）・次の手続き。
  引き渡し済みなら「引き渡し済み」と、引き渡した日時・人。
- 正式契約が不要、または必要で署名済みになったら、NEXT ACTION に［承諾内容を確認してOfficeへ引き渡す］が出る。
  押すと**最終確認**が開く（承諾日・入社予定日・条件通知書・正式契約の内容、「引き渡した人と日時が記録され、あとから取り消せません」、確認のチェック）。チェックして［確認して Office へ引き渡す］で確定。
- 正式契約が必要な間は［正式契約へ］（LegalSign の URL 登録 → 本人へ案内 → 署名済み。HR で完了させる）。育成枠は LMS・育成開始（Office へは渡さない）。

### Office（`/admin-hr.html`、入退社）

- **HRから引き渡し**：引き渡された人だけ。氏名・区分・職種・条件承諾日・入社予定日・労働条件通知書の確認・引き渡した日時と人、
  「HRで正式契約まで完了（正式契約：署名済み／不要）」の印と、入社の流れ（4つ）・NEXT ACTION。
  1. 入社書類 → 2. アカウント・端末 → 3. オリエンテーション → 4. 入社完了
- ［社員登録へ］（既存の社員登録の画面。条件は引き渡した版から事前入力）。Office に LegalSign の操作は無い。
- ［採用時書類を見る］：HR で登録した原本を見るだけ（再アップロード・差し替え・削除の入口は無い）。
- 入社予定の一覧：「HRから引き渡し」の印と、［入社書類］などの段階を先頭に添えた NEXT ACTION（HR を通らない人にも同じ言い方）。
- 入社手続きの詳細に **「HRから引き渡し」タブ**：引き渡された情報 / 採用時書類（HRから引き渡し・閲覧専用）/ 入社・契約書類（既存の段階の状態）。

## 4. 日々の運用（手順）

**HR 担当**
1. オファーを作り、内容（条件通知書PDF）を確認して本人へ送る。履歴書・職務経歴書・スキルシートなどの原本は、HR の「書類」タブに登録しておく。
2. 本人が承諾すると、応募者の詳細の上部に「条件承諾済み」が出る。承諾内容・条件・入社予定日を確認する。
3. 正式契約が「必要」なら、［正式契約へ］：LegalSign の URL を登録 → 本人へ案内 → 署名が終わったら［正式契約済みにする］。
4. ［承諾内容を確認してOfficeへ引き渡す］→ 最終確認 → 引き渡し（社長・管理者・人事。採用担当だけの人は、引き渡せる人へ頼む）。
5. 育成枠は引き渡さず、LMS・育成開始へ。

**Office 担当（人事・労務＝社長・管理者・人事）**
1. 通知「入社準備：HRから引き渡し」か、入退社の「HRから引き渡し」で、引き渡された人を見つける。
2. ［社員登録へ］で社員登録（既存の画面）。入社書類の依頼が始まる。
3. 入社書類 → アカウント・端末 → オリエンテーション の順に進める（詳細の「HRから引き渡し」タブで、採用時書類と入社・契約書類を分けて確認できる）。
4. すべてそろったら入社完了。

## 5. 仕組み（新しい SQL は db/135 だけ）

- 引き渡し：`PATCH /api/hr/offers { id, action: "handoff" }`。`canAdvanceHire`（社長・管理者・人事）。
  承諾済み・取り消し／辞退でない・育成枠でない・正式契約が必要なら署名済み・社員登録前、を確かめてから `handoff_at` / `handoff_by` を一度だけ書く。
  二度押しても変わらない（`already: true`）。タイムライン `office_handoff`・監査ログ `hr.offer_handoff`・Office の人事・労務への通知。
- Office のキュー：`GET /api/hr` の `handoffs`（`handoff_at` の入った版だけ。承諾済みだけの人・育成枠は出さない）。
  出す項目は `lib/hire-handoff.js` の許可した項目だけ。氏名・メール・電話・職種・雇用区分・入社予定日など、入社準備に必要な情報を再入力なしで引き継ぐ。給与・承諾の IP・LegalSign の URL は出さない。
- Office の入社の流れ（4つ）：`lib/hire-flow.js`。既存の段階（`lib/onboard-stage.js` の `computeStage`）の事実を並べ直すだけで、第3の判定は作らない。
- 書類の閲覧専用：`api/hr/documents.js`（応募書類）・`api/hr/offers`（`GET ?id=…&file=notice|accepted`。条件通知書PDF・承諾済みPDF）。
  Office の人事・労務（採用HRの権限が無い人）は、service role で読むため、次を**API で必ず確かめる**：
  ① 同一テナント ② 引き渡し済み（その応募者に `handoff_at` の入った版がある）③ Office の人事権限（`canOfficeHr`）④ 対象の応募者本人の書類だけ。
  PDF は給与・報酬が入るので `canSeeSalary` の人だけ。登録・差し替え・削除・PDF の生成は 403。保管済みのものを読むだけ。見たことは監査ログ（`via: office`）。
- 社員登録（`api/hr/applicants/advance.js`）：Office の人事は採用HRの RLS を持たないことがあるため、認可のあとに service role で読み書きする。その前に、順に確かめる：
  ① 認可（`canAdvanceHire`。通らなければ service role を作らない）② `tenant_id` ③ 二重登録（`employee_id` 済みなら 409）④ 承諾済み
  ⑤ `handoff_at`（409 `handoff_required`）⑥ 正式契約（必要なら署名済み。409 `formal_required`）。確定は `employee_id` が空のときだけ書く。
  db/133 が無い環境・区分の無い従来の合格通知・育成枠は、これまでどおり進める。

## 6. 権限

| 操作 | 誰が |
|---|---|
| オファーの作成・更新・送付、正式契約（LegalSign）の操作、承諾前の確認用PDF | 採用HR（`canRecruit`：経営者・責任者・人事・採用担当） |
| ［承諾内容を確認してOfficeへ引き渡す］ | 社長・管理者・人事（`canAdvanceHire`。採用HRに入れる人のうち） |
| 社員登録（事前入力・手続き開始・完了） | 社長・管理者・人事（`canAdvanceHire`） |
| 引き渡された人の書類を**見る**（応募書類・条件通知書・承諾済みPDF） | 採用HR、または Office の人事・労務（`canOfficeHr`。給与を見られる人だけ PDF） |

## 7. DB

応募書類のスキルシートには `db/135_hr_document_skill_sheet.sql`、オファー通知PDFの分離と「募集終了」には `db/137_hr_finish.sql` を使う。。db/135 はスキルシートの種類を足す。`gw_hr_documents.doc_type` の CHECK を 3 種類 → 4 種類に置き換える）。

- 置き換えるのは「`gw_hr_documents` の CHECK で、見ている列が `doc_type` 1つだけ、許す値がちょうど `resume`・`work_history`・`other`」の制約**だけ**。
  `doc_type` を含む CHECK を広く探して消すことはしない（将来、別の `doc_type` 関連の CHECK が増えても巻き込まない）。1つに特定できなければ何も変えずに止まる。既存データは変えない。
- 適用前チェック・確認・rollback：`db/check_135_hr_document_skill_sheet.sql`／`db/rollback_135_hr_document_skill_sheet.sql`。
- 適用しなくても、履歴書・職務経歴書・その他と、引き渡し・正式契約は動く（スキルシートの登録だけが「db/135 を流してください」になる）。
- 番号：db/135 = スキルシート、db/136 = HR「資料」タブ（予定）。**本番へは、報告・確認のあとに適用する**（このブランチでは適用しない）。
