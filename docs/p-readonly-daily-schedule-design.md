# P 専用・日報／業務予定の読み取り専用連携（設計案・未有効化）

基準: MF main `ef253823737438df2e98f938fb77224aafd1abaf`（2026-10-27 確認）。

**今回の成果物は設計のみ。新 API、資格情報、権限、設定、常時接続、定期実行は作成・有効化していない。**
「P」の実体・本人のアカウント・対象 tenant UUID・閲覧対象の社員・提供先・保持期間は未確認。名前、会社名、既存の先頭 membership から推定しない。

## 1. 結論

- 管理画面 API のレスポンスをそのまま P に渡さない。日報は既存の **共有サマリー**、予定は **明示共有された業務予定** を、新しい狭い読み取り境界で投影する案とする。
- 連携資格情報が既存の管理者 JWT や `service_role` を直接使える構成は採らない。一般の API・DB へ転用できない P 専用権限が必要だが、その実装・発行は別途承認する。
- 日報原本、相談・未達理由、個人評価、管理者の返信／下書き、勤怠、私用・個人カレンダー、予定メモ、社員名簿の個人情報は対象外。
- 自由記述には人名・顧客情報が混ざり得る。列の許可リストだけで「個人情報なし」とは保証できない。初回はメタデータ確認から始め、共有本文・予定タイトルを P に渡すことは項目と提供先を確認して別途承認する。

## 3. P 専用の認可境界（将来実装の要件）

**許可 = P の本人確認 ∩ 固定した1テナント ∩ 現在の権限 ∩ 承認した社員集合 ∩ 読み取り scope ∩ 有効期間。**

1. 承認記録に P の正確な主体 ID、委任する既存利用者、固定 tenant UUID、対象社員、データ項目、目的、失効日時を記載する。未設定・複数候補・不一致は拒否する。
2. クライアントからの `tenantId`、`userId`、社員 ID、DB テーブル名、任意 URL、SQL、返却列指定を受け付けない。scope と対象はサーバで決定する。カーソルも主体・tenant・検索範囲に結び付け、改変／別主体で再利用できないものにする。
3. 毎回、現在の在籍・membership・必要な閲覧権限と P の有効状態を検証する。既存 `requireUser` は退職者を拒否するが最大15秒の在籍キャッシュがあり、連携の緊急失効はこれに依存させない。失効主体は即時拒否する設計にする。
4. `gwContext` は最初の staff/membership を採用し、多重所属を想定しない。P の tenant をそれから自動決定せず、固定 tenant と返った context の一致も確認する。不一致を別 tenant に切り替えて再試行しない。
5. 日報原本を読む owner／HR 権限を P に新規付与しない。共有済みサマリーと業務予定を読む範囲を上限とし、既存権限を超える例外を設けない。
6. 将来の認証方式は、短命・audience 固定・scope 固定・個別失効可能であること。refresh token、管理者セッション、DB キーを P に渡さない。資格情報をチャット、URL、ブラウザ保存、ログへ残さない。具体的な方式と発行操作は別途設計レビュー／承認対象。
7. GET のみ。POST/PUT/PATCH/DELETE、method override、別 path、`action`、`view=week` は DB 読取前に拒否する。任意の既存 API を代理実行する汎用プロキシにはしない。

## 4. 提案する最小契約（まだ存在しない入口）

候補 path は設計上の名前であり、デプロイ済み API ではない。

### `GET /api/integrations/p/reports?date=YYYY-MM-DD`

- 日付は JST の実在日を厳密に検証。既定は今日、初期の許容範囲は過去31日まで。違反は `400`。将来日の推測値は返さない。
- 読む候補は `gw_nippo_shares` のみ。固定 tenant、`visible = true`、承認した在籍社員の user_id、日付で **DB クエリ時に** 絞る。名簿なしなら個人データ表を一切読まない。名簿失敗なら `503` で閉じる。
- 初期メタデータ: `{ date, sharedCount, complete, fetchedAt }`。共有数と提出数は別物。提出率・未提出者は本契約で推論しない。
- 本文の追加承認後の候補: `{ date, items: [{ reportRef, memberRef, did, result, learn, tomorrow }], nextCursor, complete, fetchedAt }`。`reportRef/memberRef` は P・tenant に閉じた不透明参照で、auth user UUID や社員名簿 ID を返さない。参照も再識別可能性があるため「匿名」とは呼ばない。
- `visible = false` は委任者本人の分でも返さない。コメント・返信・AI評価・モデル名・スコア・相談・未達理由・朝のメモ・雇用区分・氏名・メールは返さない。
- 共有サマリーがなければ生成せず、空または unavailable とする。`evaluate`、`summarizeForShare`、AIレビュー、再評価、保存、公開フラグ変更を呼ばない。

### `GET /api/integrations/p/schedules?from=YYYY-MM-DD&to=YYYY-MM-DD`

- JST 日付の半開区間 `[from, to)`。初期最大7日、最大31日先まで。実在日・順序・上限を検証する。
- 固定 tenant ＋許可した在籍社員 ID ＋ `source = self` ＋ `visibility = shared` ＋業務カテゴリー allowlist (`work`, `meeting`, `visit`, `other`) を **DB クエリ時に** 絞る。未知のカテゴリー・公開状態は除外する。
- 期間開始前から継続する予定も必要なので重なり判定を使う。通常は `starts_at < to` かつ `ends_at > from`。開始＝終了の終日行は `from <= starts_at < to` の別条件で扱う。元の `/team` の開始日時だけのフィルタを無批判に流用しない。
- 初期メタデータ: `{ from, to, timeZone: "Asia/Tokyo", eventCount, complete, fetchedAt }`。
- タイトル等の追加承認後の候補: `events: [{ eventRef, memberRef, title, startsAt, endsAt, allDay, category }]`。氏名・部署・場所・本文／メモ・相手の連絡先・参加者・Google 情報・元申請 ID は返さない。
- 私用 (`category=private`)、旧 private/busy、Google 個人予定、休暇 (`source=leave`)、予約自動作成 (`source=booking`)、退職者・未承認社員の予定は返さない。在籍者の扱いは承認時に確定し、初期は `active` のみ（既存 `/team` の `active/invited` や日報 admin の `active/leaving` を自動採用しない）。

### 共通

- `Cache-Control: private, no-store`。既定で P 側の永続保存・ベクトル化・学習・二次共有・定期ポーリングをしない。必要な保持期間は別途承認する。
- 日報は最大300件、予定は最大600件を1ページの初期上限候補とし、安定した sort＋opaque cursor でページングする。名簿もページングまたは完全性確認を行う。上限到達時に全件扱いしない。既存の名簿300件制限を完了の証拠にしない。
- DB エラーを空データ／0件へ変換しない。`401/403/400/429/503` の機械可読コードを返し、DB 内部の詳細や存在確認につながる情報は出さない。未知 ID は同じ拒否応答にする。
- 読取回数・期間・応答容量の上限、短いタイムアウト、有限のバックオフを設ける。認可失敗で別の資格情報へフォールバックしない。
- 既存の観測基盤で主体・scope・成功／拒否・件数・所要時間のみを監査する。本文、社員 ID、トークンはログに出さない。業務データへの書き込みはゼロ。新しい監査保存先の追加は別途レビューする。
- 自由記述は不信頼データとして扱い、そこに書かれた指示・URL・API操作を実行しない。HTML を解釈せずテキストで表示する。個人情報／機密を含む可能性がある本文の提供は、単純な正規表現や AI マスキングだけで安全と判定しない。

## 6. 残るリスクと開始前の承認ゲート

- **今回の日次 tenant 修正は別問題の解決。** `tc_nippo` は user_id ベースで、原本に tenant_id がない。多重所属や転籍履歴まで完全分離したと断言できない。共有連携は tenant_id を持つ `gw_nippo_shares` を用い、原本への代替読取を禁止する。
- `tc_*` の既存 RLS や管理側 POST の境界を今回の GET 修正だけで強化したことにはならない。既存の広い資格情報を P に渡さない理由でもある。
- 既存の SQL ファイルは望ましい定義の資料であり、本番に適用済みという証拠ではない。本番 ACL/RLS の確認は別途許可を得た read-only 手順で行う。
- 社内共有への同意は外部／別主体 P への持ち出し許可と同一ではない。P が何で、どこで処理し、誰が結果を見られるかを先に確定する。

承認は段階を分ける:

1. **設計確定**: P／委任者／tenant UUID／対象社員／初期メタデータの目的・保持期間・提供先を確認。本文・タイトルや氏名付き表示が必要なら、その追加範囲を明示して承認する。
2. **ローカル実装と合成テスト**: 上の契約、read-only・失効・tenant 分離・除外条件を実装し、結果と差分を提示する。認証方式の実装もこの段階の新たな承認が必要。
3. **環境・認証情報**: 対象環境、短命資格情報の作成者・保管先・失効担当・期限を提示し、発行／設定操作の承認を得る。今回は発行しない。
4. **公開・本番確認**: push／PR／merge／deploy を各許可範囲で行い、まず合成データの隔離環境で検証。本番の私有データを読む場合は、対象・日付・件数を示して別途承認する。
5. **運用開始**: 定期実行、常時接続、継続保存、他チャネル配信は自動追加しない。必要なら頻度・宛先・停止条件を別途承認する。
