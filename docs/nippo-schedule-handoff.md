# 時間・内容・数字 → 日報の引継ぎ

## 今回できる範囲

既存の本人カレンダーへ **時間・内容・任意の数字** を保存し、同じ予定IDから日報の下書きへ引き継ぎ、本人は
**実績時間・数字だけ**を記入する。補足は任意の折り畳み。新しい予定台帳は作らない。

- `GET /api/nippo` の `scheduledWork` は、既存認証の `userClient` で同一tenant・本人の
  `source=self` / `visibility=shared` / 業務区分の予定だけを読む。本文、場所、外部同期IDは選択しない。
- JSTの対象日との重なりで取得する。前日開始・複数日・終日も対象だが、予定時間を実測時間にしない。
- 日報未提出かつ端末の復元下書きがない場合だけ自動追加。同じ予定IDは増やさない。
  タスク名が同じという理由で別タスクの完了を予定へ付けない。
- 未計測・未記録は `null`、明示した0は0。数えない仕事に数字を要求しない。
- システム実績は常に `{status:"unconnected", count:null}`。自己申告と別物であり、業務システムの取得済み件数ではない。

カレンダーと週間予定画面を「時間・内容・数字」の3群にし、場所は任意の折り畳みにした。
数字欄は `10件` / `3社` / `0` のような1欄。数えない作業は空欄。値と単位を正式な別列へ保存し、
既存本文へ埋込み・タイトルから件数推測・別台帳作成はしない。
カレンダー予定の複製機能は別差分で、この変更には含めない。

### DB適用条件（未適用）

`db/proposal_calendar_plan_quantity.sql` は担当者用の **DDL案** で、エージェントは適用していない。
`gw_calendar_events.planned_quantity numeric NULL`（0〜1e9）と
`planned_quantity_unit text NULL`（10文字以内）の2列・制約のみ。RLS・権限・既存値を変更しない。
まず `db/check_proposal_calendar_plan_quantity.sql` で対象・型・制約を担当者が確認する。
適用前はAPIが既存列だけの読取へフォールバックし、UIは「数字未準備」として無効化する。
数字の保存成功を偽装せず503にする。権限・通信・無関係な列エラーは握りつぶさない。

P向けの業務実データ照合は未接続。正規認証による継続読取と昨日の助言→今日の変化の比較は
別の接続作業であり、このUI/記録差分だけで完了とは扱わない。認証回避・公開APIは作らない。

## 保存・保護

日報側は既存 `tc_nippo.work_items` JSONを利用する。日報の新規テーブルは作らない。

- `schedule_event_id`：既存予定の参照ID
- `planned_starts_at` / `planned_ends_at` / `planned_all_day`：最初の保存時の予定控え
- `actual_minutes`：対象日の自己申告時間（0〜1440分）。日またぎでも当日分のみ本人が記入
- `target` / `unit`：既存項目を再利用した予定数字・単位の控え
- `actual`：既存項目を再利用した自己申告数字
- `measurement_note`：任意の補足

新しい参照IDは保存時に本人予定として再検証し、タイトル・時刻・目標数字・単位はサーバが読んだ値に置換する。
未確認ID・別人・別tenant・非公開・対象日外は拒否。外部証拠/検証済みフラグは受け取らない。
この控えは**朝に確定した変更不能な証拠ではなく、最初の保存時点の予定**である。
後の予定変更・取消・削除で保存済み控えや実績を自動変更しない。

保存済みの参照行は旧クライアントが省略しても保持し、JSONの未知フィールドは引き継がない。
既存行への更新は本人ID＋`updated_at`の比較で行い、読み取り後の競合は409。
新UIの下書きには読取版を保持し、古い版の提出も409とする。上書き・自動再送はせず入力を保持する。
`updated_at`は同じミリ秒でも前へ進める。行動案の「取り込み直す」でも提出済み/予定控えを消さない。

日報の10行上限、カレンダー取得100件上限は表示する。取得失敗/上限超過は未確認とし、0件とは扱わない。
旧クライアントの省略を削除扱いしないため、保存済み参照行の削除UIは今回用意しない。

## 既存集計との分離

予定参照行は `evaluationItems()` / `isDone()` で従来の完了数・完了率・週月次・自走指標・試用期間・
ランキング・急減検知・日報AI・行動案AI・全員向け共有サマリーから除く。
数字を入れただけで「完了」とせず、空欄を不正/非効率/未達にしない。
品質・割込み・難易度・習熟・契約範囲は必要時に人が確認する。必須入力は増やさない。

既存の日報提出条件（翌営業日予定、週次振り返り等）・権限・通知設定は変更しない。
新しい外部API・AI呼出し・通知は追加しない。既存提出処理の副作用は合成mockのみで検証する。

## 確認版とリリース順序

`node scripts/build-nippo-plan-preview.mjs [出力先]` で自己完結の `index.html` を生成する。
実週間画面と同一の数量・日報ヘルパーを使用し、認証/APIの代わりに架空のメモリ用adapterを差す。
CSPで外部接続を禁止し、再読み込みで消える。実ブラウザ検証とは別物であることを画面内に表示する。

1. 差分レビュー・Node回帰、確認画面を利用者へ共有する。
2. DB担当者が2列の適用可否・型・既存制約を確認し、別途許可されたSQLだけを適用する。
3. 通常の認証済みPreviewで本人/別人/別tenant、スマートフォン、保存→再読込→日報の受入確認。
4. 正規のPR/CI/デプロイ手順を使う。SQL未適用なら数字入力は無効であり、3入力完成とは言わない。
5. Pの継続読取・昨日助言との比較は別担当の認証接続結果を確認する。自己申告を実データ証拠とはしない。

実システム件数は業務種別・期間・実行者・操作ID・状態・取消/再送の定義が確認できる読取元だけを別欄へ出す。
その根拠がない間は未確認のままとし、予定枠やAI候補数を本人完了件数へ読み替えない。
