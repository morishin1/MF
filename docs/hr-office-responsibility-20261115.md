# 採用HRとOffice人事労務の業務境界（2026-11-15）

> **Office保管運用 v1.0 の確定要件：** [office-contract-upload-mvp-20261115.md](office-contract-upload-mvp-20261115.md) を最優先で参照。契約書が主書類、労働条件通知書は別紙がある場合のみ追加。契約書未登録人数は主書類だけで判定する。旧来の公開・署名・入社導線は今回のOffice簡素化画面に表示しない。


## 2026-11-15追記：当面のOffice書類運用（以下の詳細な公開・署名フローより優先）

社内で別途締結した書類を**PDFアップロードして保管する**運用に簡素化する。HRは内定通知まで、Officeは正式な労働条件・契約書類の管理に限定する。

- Office画面の主操作は「対象者を選択 → 書類を選択 → PDFをアップロード」。既存のPDFがあれば「PDFを確認する」「新しい版をアップロード」。1ファイル5MB以下のPDFを既存の保護された書類APIに保存する。
- 書類の見せ方は**「未アップロード」「アップロード済み」**のみ。公開状態や本人同意・署名状態をアップロード状態に混ぜない。ドラフト・公開済のいずれもファイルが存在すれば「アップロード済み」とする。
- 採用予定区分が雇用なら労働条件通知書・雇用契約書、業務委託なら業務委託契約書を表示。区分未設定時は候補3種類を表示する。契約書の確認・アップロードはOfficeの権限を持つ担当者だけ。
- **アップロードでは送信・公開・契約締結・署名確認・入社手続きを一切実行しない。** 契約締結と必要な法定の労働条件明示は、従来どおり社内の別途運用で行う。
- 既存の公開API、署名確認機能、内定決定のHR→Office通知は削除せず維持する。Officeの簡素化画面からは公開・署名・入社操作への導線を外す。Word自動生成PR #358は別案件として保留。
- 新しいテーブルやデータ移行は不要。Office一覧APIが返すuploadedKindsは実際のファイル記録から導出する。
- 既存の候補者書類APIは選考終了/入社済みの場合に新規アップロードを拒否する。入社済みの社員台帳での追加保管は別途設計・検証が必要であり、この画面が対応済みとは言わない。
- QAは2値表示とファイルの保存・確認・新しい版の登録、権限とテナント分離、PDF形式/サイズ、PC・スマホ、前の版の扱いを確認してから本番反映する。


## 結論
**HRは応募受付から採用判断・内定通知まで。Officeは労働条件通知書・契約書・本人の署名/合意・入社/稼働/社会保険・必要書類を管理する。**

ただし「内定時に労働契約が成立する場合」は、その時点で必要な労働条件を明示する必要がある。Officeの正式通知書の発行時期を「入社直前」と決めつけない。HRで内定通知を本人に交付する**前に**、Office人事労務または社労士が必要な労働条件・明示時期を確認する。
参考：厚生労働省「採用時の労働条件の明示」 https://www.mhlw.go.jp/bunya/roudoukijun/faq_kijyunhou_4.html および「採用内定時に労働契約が成立する場合の労働条件明示について」 https://jsite.mhlw.go.jp/miyagi-roudoukyoku/var/rev0/0119/2032/naiteimeiji.pdf

## HR → Office 自動引継ぎ（今回の実装）
1. HRで代表・管理者が `decision=hired` を確定する。応募者の基本情報、採用予定区分、採用判断のタイムラインを原本として保存する。
2. `PATCH /api/hr/applicants/detail` の直接判断と、代表権限のステップ移動の両経路から、Office人事労務へ通知を送る。対象は在籍中の **owner / 管理者 / hr＋Officeアプリ** の人だけで、採用担当のみ・Office経理のみ・退職者・外部専門家は含めない。通知は同じ採用決定ごとに重複しない。
3. 通知から `/office/hiring-documents.html?applicantId=...` を開く。通知が失敗しても、Officeの一覧は採用決定の実データから自動生成され、未処理案件を失わない。
4. Office一覧で、HR内定通知・労働条件通知書・契約書それぞれの **未アップロード／アップロード済み（未公開）／本人公開済み** を表示。移行前の旧オファーが送信済みならその事実も確認し、不明の場合は「HRで確認」とする。
5. Officeが正式PDFを登録し、宛先と内容を確認して本人公開を別操作で行う。本人への公開だけで同意・署名・契約完了にはしない。本人の合意・契約署名は既存の手続きで確認してからOfficeの入社画面へ進む。
6. HR側は内定通知まで。採用決定者の詳細には「Officeへ引継ぎ対象」を表示する。旧契約書の直接操作はOfficeの正式書類画面へ案内する。

**明示の前提：** 内定により労働契約が成立する場合、Officeは内定時点で必要な労働条件を明示できるよう、HRの通知交付より前に条件を確認する。内定決定後にOfficeへ通知が届くことと、法令上の交付時期は別問題である。

## 管理する事実と操作
| 対象 | HR | Office |
| --- | --- | --- |
| 応募者・面談・評価・採用予定区分 | 管理と編集 | 必要時参照 |
| 採用決定 `decision` | 代表/管理者のみ確定 | 参照 |
| 内定通知書 `offer` PDF | HRの給与管理権限者が登録・送信前確認 | 必要条件を事前レビュー |
| 労働条件通知書 `terms` | 状況のみ参照、Officeへ依頼 | 作成・アップロード・正式交付 |
| 雇用契約書 `employment_contract` | 状況のみ参照、Officeへ依頼 | 作成・アップロード・署名/同意確認 |
| 業務委託契約書 `contractor_contract` | 状況のみ参照、Officeへ依頼 | 作成・アップロード・署名/同意確認 |
| 入社・勤務・雇用保険・社会保険・提出書類 | 引継ぎ履歴のみ | 管理 |

**採用予定区分 `offer_type` は契約書ではない。** HRの変更で `employment_type`、給与、契約期間、採否、本人同意、社員レコードを更新しない。正社員・パート/アルバイト・業務委託等の計画を一括選択し、正式な賃金・契約はOfficeが再確認する。
個別の「パート」「アルバイト」「契約社員」の区別は、既存の6区分の分類だけでは表せない。正式な雇用形態はOfficeの個別条件で確定し、将来別の採用予定サブカテゴリを導入する場合は独立したDB列/移行計画を設ける。

## アクセス制御
- `canRecruit`: 応募者管理・社内分類と面談。本人に公開される書類の給与権限は別。
- `canDecideHire`: 代表または管理者による採用判断。採用予定区分の選択だけでは許可しない。
- `canOfficeHr` と `canSeeSalary`: Officeの労働条件通知書・契約書の管理と閲覧。採用HRロールだけで正式書類にアクセスさせない。
- 両方の権限を持つ利用者は両画面で役割を切り替える。書類種類単位のAPIサーバ検証が正で、ボタン非表示だけで保護しない。

## 引継ぎ・必要データ
- HR → Office: 応募者ID・採用決定と日時・採用予定区分・内定通知の版/送信状況・入社予定・承認済み基本条件を参照可能にする
- Office → HR: 「条件通知書未作成/作成済」「契約書未提出/提出済」「確認/署名待ち」「手続き完了」などの進捗を**参照**で返す
- 書類をアップロードしても自動公開・自動送信・合意済み・Office引継ぎ完了にはしない
- 「採用区分を設定」一括変更は既存の `offer_type` を変更するが、発行済みのオファー・契約・入社済みは競合とし、部分失敗した応募者を残す
- 採用内定の前に労働条件明示が必要なケースはOffice確認が完了するまで本人への確定通知を保留する運用とし、正式な適用ルールを社労士レビューで決める
