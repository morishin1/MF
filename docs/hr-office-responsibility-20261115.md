# 採用HRとOffice人事労務の業務境界（2026-11-15）

## 結論
**HRは応募受付から採用判断・内定通知まで。Officeは労働条件通知書・契約書・本人の署名/合意・入社/稼働/社会保険・必要書類を管理する。**

ただし「内定時に労働契約が成立する場合」は、その時点で必要な労働条件を明示する必要がある。Officeの正式通知書の発行時期を「入社直前」と決めつけない。HRで内定通知を本人に交付する**前に**、Office人事労務または社労士が必要な労働条件・明示時期を確認する。
参考：厚生労働省「採用時の労働条件の明示」 https://www.mhlw.go.jp/bunya/roudoukijun/faq_kijyunhou_4.html および「採用内定時に労働契約が成立する場合の労働条件明示について」 https://jsite.mhlw.go.jp/miyagi-roudoukyoku/var/rev0/0119/2032/naiteimeiji.pdf

## 管理する事実と操作
| 対象 | HR | Office |
| --- | --- | --- |
| 応募者・面談・評価・採用予定区分 | 管理と編集 | 必要時参照 |
| 採用決定 `decision` | 代表/管理者のみ確定 | 参照 |
| 内定通知書 `offer` PDF | HRの給与管理権限者が登録・送信前確認 | 必要条件を事前レビュー |
| 労働条件通知書 `terms` | 状況のみ参照、Officeへ依頼 | 作成・アップロード・正式交付 |
| 雇用契約書 `employment_contract` | 状況のみ参照、Officeへ依頼 | 作成・アップロード・署名/同意確認 |
| 業務委託契約書 `contractor_contract` | 状況のみ参照、Officeへ依頼 | 作成・アップロード・署名/同意確認 |
| 入社・勤務・雇用保険・社会保険・提出書類 | 引継ぎ履歴のみ | 管理 |

**採用予定区分 `offer_type` は契約書ではない。** HRの変更で `employment_type`、給与、契約期間、採否、本人同意、社員レコードを更新しない。正社員・パート/アルバイト・業務委託等の計画を一括選択し、正式な賃金・契約はOfficeが再確認する。
個別の「パート」「アルバイト」「契約社員」の区別は、既存の6区分の分類だけでは表せない。正式な雇用形態はOfficeの個別条件で確定し、将来別の採用予定サブカテゴリを導入する場合は独立したDB列/移行計画を設ける。

## アクセス制御
- `canRecruit`: 応募者管理・社内分類と面談。本人に公開される書類の給与権限は別。
- `canDecideHire`: 代表または管理者による採用判断。採用予定区分の選択だけでは許可しない。
- `canOfficeHr` と `canSeeSalary`: Officeの労働条件通知書・契約書の管理と閲覧。採用HRロールだけで正式書類にアクセスさせない。
- 両方の権限を持つ利用者は両画面で役割を切り替える。書類種類単位のAPIサーバ検証が正で、ボタン非表示だけで保護しない。

## 引継ぎ・必要データ
- HR → Office: 応募者ID・採用決定と日時・採用予定区分・内定通知の版/送信状況・入社予定・承認済み基本条件を参照可能にする
- Office → HR: 「条件通知書未作成/作成済」「契約書未提出/提出済」「確認/署名待ち」「手続き完了」などの進捗を**参照**で返す
- 書類をアップロードしても自動公開・自動送信・合意済み・Office引継ぎ完了にはしない
- 「採用区分を設定」一括変更は既存の `offer_type` を変更するが、発行済みのオファー・契約・入社済みは競合とし、部分失敗した応募者を残す
- 採用内定の前に労働条件明示が必要なケースはOffice確認が完了するまで本人への確定通知を保留する運用とし、正式な適用ルールを社労士レビューで決める
