# GWメンバー管理とENGER商談アカウント｜要件定義 v1（2026-11-15）

## 決定
1. HRの雇用・契約区分とメンバー管理を一元化する。画面の主分類は「すべて／正社員／有期雇用／アルバイト・パート／業務委託／スポット／役員・その他」。保存値の「契約社員」は有期雇用として表示する。パートとアルバイトは一覧でまとめるがデータは残す。
2. ENGERで商談するかは雇用区分から推測しない。**個人の業務上の役割**として「社内ENGER営業」「ENGER営業エージェント」を割り当てる。業務委託者でも開発担当なら営業権限を付けない。正社員でもエージェント型営業の対象になり得る。
3. ログインは本人単位（既存Supabase Authの同一user_id）を基本とする。社内営業／営業エージェントの別ID二重発行をしない。担当企業と参照できるデータはサーバ側のロール・スコープで判定する。
4. 取引先企業のログインは、管理者／営業担当者用のアカウントとは区別する。企業マイページ（検索・提案確認・案件人材登録・オファー）だけを利用できる。企業用ID・認証導線の互換性を壊さない。
5. ログイン後は「社内営業」「営業エージェント」「取引先企業」の認可済みロールに応じて、同じENGERデザインの適切なホームへ進む。複数権限を持つ場合のみ明示的な切り替えを表示。既存のSales商談DBとは連携するが、UIをSalesに強制遷移させない。
6. UIはHR/Office/社員名簿と同じワイド幅、見出し、検索、列高さ、詳細モーダルを使う。「外部メンバー／エージェント」を雇用区分のタブにはしない。ゲスト招待（権限付きファイル・タスク等）は別の操作として残す。
7. 各行のチェックボックスとページ全選択を配置。一括更新（区分・部署など）、利用停止、誤登録の削除を管理する。非表示の選択者がいれば人数と氏名を確認できるようにする。契約/商談/給与履歴があるユーザーは物理削除せず利用停止を原則とする。
8. パスワードは新規発行/個別再設定。再発行は管理者のMFA必須。平文をDB・監査ログ・URL・localStorageに置かない。表示は一度だけ。既存パスワードの再表示はしない。
9. HR：選考から内定合意まで。Office：合意済み契約書のアップロード・契約の区分と期間管理。GWメンバー管理：ユーザー作成と役割/利用権限。ENGER：商談・オファー・成果。本人の識別子は重複させない。

## 現在の実装における制約（重要）
- `gw_employees.employment_type` のDB CHECKは `正社員/契約社員/パート/アルバイト/業務委託/役員/その他`。スポットは現時点で独立した保存値ではない。スポットは**雇用区分を捏造せず**、HR/Officeの単発契約データとの紐付けが完成してから実レコードを表示する。
- PR #363 は `department='ENGERエージェント'` を仮の識別に用い、エージェント新規作成は業務委託・アルバイトに限定している。既存社員への追加は同じメール重複検査で拒否される。
- PR #363 は `enger.organization_memberships.user_id` の一意性と既存社内メンバーシップとの衝突を警戒し、安全のため既存社内ユーザーを外部に変換しない。**この制約を外すだけでは実装不可**。ENGER側の認可モデル/多重ロール・組織スコープ・アプリ側認可を整合させる必要がある。
- 企業マイページと社内/エージェント画面は、業務上の責任と情報範囲が違うため、同一の閲覧権限に統合してはならない。
- `GW社員名簿` と `ENGERエージェント名簿` を別の正本として持たない。段階的に既存の画面・APIを共通の個人一覧に寄せる。

## v2 追記（2026-11-15）｜役割の正本を部署名から認可データへ

### 調査で分かったこと（実コード）
- **GW社内営業**：GWには既に「アプリ利用権限」`gw_app_grants`（db/119）の `sales` があり、雇用区分と独立に1人ずつ付与できる。`/sales`（商談6ステップ含む）は `canAccessSales`（owner または apps に sales）で保護。→「ENGER社内営業」はこれを使い、新しいロール値は作らない。
- **ENGER（dx.enger / enger_new）**：`organization_memberships.user_id` は `enger.app_users.id`（Auth の uid ではない）。`membership_type` は `internal|partner`、product は `matching|sales|marketing|sourcing`。`external` と `partner_sales` を読むコードは**存在しない**。
- **enger.jp（enger-lp）**：`/business/login` は `app_metadata.apps` に `business` を持たないアカウントを `business_account_required`(403) で拒否する。PR #363 で作るエージェント（`apps:["partner_sales"]`）は**ログインできない**。エージェント用ホームも未実装。
- **Sales履歴**：`gw_sales_deals.owner_id` / `gw_sales_meetings.owner_id` / `gw_sales_approaches.employee_id` は `gw_employees` を `on delete set null` で参照。名簿を消すと成果の帰属が消える。

### この追記で実装したこと（PR #364 の上に積む）
1. 役割の判定を `lib/enger-agent-role.js` に集約。**役割＝GW形式の外部所属（external/member/組織なし）＋ `partner_sales` の行**。`department='ENGERエージェント'` は使わない（旧方式の人を「役割の付与待ち」で一覧に出すためだけに読む）。
2. 既存メンバーへの役割付与 `PATCH {action:"grant_role"}`。Auth を作らない・雇用区分/部署を変えない・付与直後は閲覧不可。役員・在籍外・ログイン無しは拒否。
3. 衝突時は停止：ENGER社内メンバー（`enger.app_users` の admin/agent）や既存の社内・取引先所属には外部所属を足さない／変換しない（DX は app_users.id → Auth uid の順で所属を引くため、足すと社内権限を意図せず狭める）。
4. 新規登録（名簿にいない人だけ）：雇用区分は役員以外の既存保存値から選択。部署は実部署（`ENGERエージェント` は拒否）。役割は停止中で同時に付与。役割付与に失敗しても名簿とログインは重複発行せず、付与のやり直しで復旧。
5. パスワード：エージェント専用の再発行を廃止し、名簿共通の `/api/employees/account`（MFA・1回表示・GW/無限道場/タイムカード共通の注意）へ誘導。使えない ENGER ログインURLの案内を削除。
6. 退職（left）：部署に関係なく、ログインのある人は ENGER の閲覧権限を先に閉じる（エージェント以外には何もしない）。削除：ENGER所属がある人、Sales の案件・商談・アプローチ履歴がある人は物理削除不可（件数はサーバー権限で数え、RLSで0件に見える誤判定を防ぐ）。
7. 一括更新：役割は部署・雇用区分と独立になったので、部署名で役割を表す変更だけ拒否。
