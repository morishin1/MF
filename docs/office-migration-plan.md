## 4. 売上請求書：ヘッダ＋明細。「客先ごとに1枚」に固定しない（Phase 5）

```
売上請求書ヘッダ
  客先：株式会社ABC ／ 対象月：2026年10月
  ├ 明細  Aさん / 開発案件 / 160h / 700,000円
  ├ 明細  Bさん / 運用案件 / 155h / 650,000円
  └ 明細  Cさん / 開発案件 / 168h / 720,000円
```

- **基本（初期UIの既定）は「客先 × 請求月」でまとめる**。ただし次の3つをすべてできる設計にする：
  1. 客先単位でまとめる
  2. 案件単位で分ける（同じ客先でも、案件ごとに請求書を分ける）
  3. 任意の明細だけまとめる
- **DB 制約で「客先 × 月 = 1枚」に固定しない**。`(customer, billing_month)` に一意制約を置かない。まとめ方は、請求書を作る操作で決める（画面の既定は「客先×月でまとめる」）
- **ヘッダ**：`invoice_no`, `customer_name`（客先。いまは `site_company` の文字列）, `billing_month`, `invoice_date`, `due_date`, `subject`, `tax_rounding`, `status`（draft／created／sent／paid／void）, `file_path`, `sent_at/by/to`。金額（税抜・税・合計）は明細から計算し、税は**請求書単位**で端数処理（要件 §8）
- **明細**：`invoice_id`, `billing_progress_id`（月次レコードの1行＝要員×契約×月）, `description`（案件名など）, `work_minutes`（確定した稼働時間。`gw_timesheets.total_minutes` を写す）, `unit_price`（**計算に使った売上単価のスナップショット**）, `amount`, `terms_id`（使った契約条件）, `voided_at`
- **二重請求の防止**：明細の `billing_progress_id` に、`voided_at is null` の部分ユニーク。制約の相手は**ヘッダではなく明細**（1つの月次レコードが有効な売上明細に載るのは1回だけ。取り消した明細は数えない）
- 明細の金額は、Phase 3 の精算計算（`lib/office-calc.js` の `settle`）の結果を写す。**自動計算できないもの（日給・日割り・月の途中で条件が変わる・条件未設定）は、明細を作らず「要確認」に戻す**
- 実メール送信は入れない（P1）。「送付済みにする」＋送付先・送付者・件名・日時の記録のみ

## 5. 発注：ヘッダ＋明細。「1発注書＝1要員」にしない（Phase 6）

```
発注ヘッダ
  発注先：株式会社XYZ ／ 対象期間：2026/10/1〜2026/10/31
  ├ 明細  Aさん / ○○案件 / 仕入単価
  ├ 明細  Bさん / ○○案件 / 仕入単価
  └ 明細  Cさん / △△案件 / 仕入単価
```

- 1名ずつ発注する運用も、複数名をまとめる運用も、どちらも同じ表で表せる（**発注書1枚の明細数に、上限も下限も置かない**）。`(partner_company_id, 対象期間)` に一意制約を置かない
- **ヘッダ** `gw_purchase_orders`：`order_no`, `partner_company_id`（発注先）, `period_from`, `period_to`, `status`, `payment_terms`, `file_path`, `issued_at/by`
- **明細** `gw_purchase_order_lines`：`order_id`, `employee_id`, `site_contract_id`, `project_name`, `purchase_unit_price`（**発注時の仕入単価のスナップショット**。`gw_site_contract_terms.purchase_unit_price` から写す）, `terms_id`, `note`
- 仕入請求書も、ヘッダ＋明細（`gw_vendor_invoices` / `_lines`）。明細は `purchase_order_line_id`（null 可）と `billing_progress_id` を持つ。BP 会社が複数要員を1枚で請求してくるので、**発注 1通 ↔ 請求書 1枚 も、1対1に固定しない**
- 発注額と請求額の差は**保存せず、明細ごと・請求書ごとに計算**して表示する。自動で否認・修正しない。請求書の合計と明細の合計が合わないときは「要確認」（その請求書だけ）
- **仕入側の精算ルール（BP・外注への支払の、精算幅・超過・控除）は、まだ決まっていない**ので、Phase 3 では計算しない（§8）。単価（`purchase_unit_price`）を持つだけ

支払（Phase 7）：`gw_office_payments`。`vendor_invoice_id`（請求書**ヘッダ**に対して1件。要員ごとではない）, `amount`, `scheduled_on`, `status`, `paid_on`, `paid_by`。BP 会社の振込口座は持たない（機微。入れるときに別途設計）。
月次確定（Phase 8）：`gw_office_month_closes`。`gw_month_closings` とは別。

## 6. Phase 3：勤務表 → 稼働時間の確定（実装済み）

**最優先の目的**は「勤務表から稼働時間を確定するまでの、確認の時間を短くする」こと。KPI は **AI の精度ではなく、人が確認する時間**。

### 6.1 流れ（AI は下書きを作るだけ）

```
勤務表アップロード（外部フォーム or Office）
   ↓ 形式・大きさ・sha256 を確認、同じファイルを検知
AI読取（draft）── 読めなかった所は null。推測で埋めない
   ↓
人が確認・修正（左：勤務表 / 右：日別の読取結果。要対応の日から）
   ↓ 不明な日が0・要確認は確認済み・全日の行がある
confirmed（人が「確定する」を押したときだけ）
   ↓
既存の印（受領・稼働確認）が同期 → 契約条件と照合 → 売上の精算
```

実装の順番（要件どおり）：①提出状態 ②ファイル重複検知 ③AI読取 ④読取結果のプレビュー ⑤人による修正・確定 ⑥日別稼働データ ⑦月間集計 ⑧契約条件との照合 ⑨精算計算。

| 部品 | ファイル |
|---|---|
| 時間の計算（純関数） | `lib/office-time.js`（時刻・休憩の読み方、日別の実働、日跨ぎ・月跨ぎ、丸め、月間集計） |
| 確認・確定の規則（純関数） | `lib/office-timesheet.js`（要確認の印、確定の条件、入力の検査、まとめて直す操作、提出状態、同じファイルの見つけ方） |
| 契約条件・精算（純関数） | `lib/office-calc.js` |
| AI読取 | `lib/office-timesheet-ai.js`（Anthropic SDK 直接。厳密に検査し直す） |
| API | `api/office/timesheet.js`（受領・読取・保存・確定・取消し・差し戻し）、`api/office/terms.js`（契約条件）、`api/office/index.js`（一覧に状態・稼働時間を足す） |
| 画面 | `office/timesheet.html`（確認・確定）、`office/terms.html`（契約条件）、`office/index.html`（一覧・ドロワー） |

### 6.2 時間の規則（決定済み）

時刻は「その日の 0:00 からの分」の整数（540 = 9:00）。終了が 1440 以上なら翌日（1560 = 翌 2:00）。

- 休憩を差し引いてから、月合計する
- **休憩が不明なら、補完しない**（実働を出さず「入力が必要な日」。合計にも入れない）。勤務表に休憩欄が無いときは注意を出し、勤務した日ごとの入力（または人が押す一括入力）が要る
- 単位のない休憩「1」「1.5」は、分か時間か分からないので読まない（1分と読み違えない）
- 日跨ぎ：勤務開始日を勤務日とする。終了が開始より前なら翌日終了とみなし、人に確認してもらう
- 月跨ぎ：月末日の勤務が翌日にかかるぶんは、月境界で分割して翌月へ（休憩は開始側から差し引く）。翌月の合計に「前月からの繰越」として入る
- 深夜・休日の割増は計算しない（実働の分だけ）
- 丸め：精算の単位（5・10・15・30・60分）・方向（切捨て／切上げ／四捨五入）・単位（日ごと／月合計）は、契約条件から読む（コードに固定しない）

### 6.3 AI読取（`lib/office-timesheet-ai.js`）

- 各日について、日付・開始・終了・休憩・実働（勤務表の記載）・備考・**AI confidence（高／中／低）**・**要確認の理由**を返させる
- 返ってきた値は、**こちらで厳密に検査し直す**：数値の時刻・単位のない休憩は受けない／`unreadable` の項目は捨てる／自信度の無い・low の日、書かれていない日（`not_read`）、空白の平日、休み表記と時刻の両方がある日には**要確認の印**／勤務表の年月が違えば取り込まない（`wrong_month`）
- AI が `status`・`confirmed` を返しても取り込まない。確認済み（`reviewed_at`）は、人の操作でだけ付く
- 呼び出し：`tool_choice` は指定しない（Claude 5.5 系で 400 になる）。`thinking`・`temperature`・prefill も指定しない。モデルは `lib/claude.js` の `MODEL`（`ANTHROPIC_MODEL`）。失敗（ツール未呼び出し・途中切れ・拒否・上限・タイムアウト）は、理由つきで返して手入力に進める
- **`api/office/timesheet.js` の `maxDuration` は 60 秒**（`vercel.json`）。AI読取が60秒に収まらない場合は、非同期化を検討（§8）

### 6.4 確認画面（`office/timesheet.html`）

- **左に勤務表（PDF・画像）、右に日別の読取結果**。既定は「要対応のみ」（実働を出せない日・要確認の日）。問題のない日は畳み、「すべての日」で全体を見比べられる
- 欄を離れると、**その日だけ**保存し、実働・合計・確定の条件がその場で更新される（Tab で次の欄へ進んでいても、フォーカスは消えない。Enter で次の日の同じ欄へ）
- 値を直した日は、確認済みになる。**見ただけ**は「確認した」ボタン。要確認をまとめて確認済みにする操作もある（人が押したときだけ）
- まとめて直す操作：読めなかった日を休みに／未確認の土日を休みに／休憩を一括入力（空の勤務日だけ）／要確認をまとめて確認済みに
- **確認にかけた時間**（画面を見ていた秒数）と、**直した回数**を `gw_timesheets.review_seconds` / `edit_count` に残す（KPI 用）
- 勤務表の合計が計算と違うときは、承知（チェック）のうえでだけ確定できる
- 確定後は編集できない。**確定の取消し（理由つき）**：請求書の作成・送付の印があるときは断る。**差し戻し（理由つき）**：再提出を待つ状態にするだけで、**メールは送らない**

### 6.5 既存の5つの印との同期

| 出来事 | 印の変化 | 補足 |
|---|---|---|
| 勤務表が届いた（外部フォーム／Office のアップロード） | `timesheet_received` を立てる | 外部フォームは従来どおり |
| 確定（confirmed） | `work_confirmed` を立てる（`timesheet_received` も） | 履歴に、変えた印の名前を残す |
| 確定の取消し | `work_confirmed` を外す | `board_created`・`sent` が立っていれば、取り消せない |
| 差し戻し | `timesheet_received` を外す | 再提出を待つ |
| 印を手で直す（既存の月初作業管理） | そのまま使える | 勤務表の行が無い稼働確認の印は「確認済（手動）」で、警告にしない。**勤務表が確定していない（下書き・差し戻し）のに印がある／確定しているのに印が無い**ときだけ「要確認」 |

`gw_billing_progress` の列は変えていない。月初作業管理・cron・提出フォームへの影響は §7。

### 6.6 契約条件と精算（`gw_site_contract_terms`・`lib/office-calc.js`）

- 契約条件は**期間つき**。ある月に効く条件が2件以上（月の途中で変わる）なら、**自動で選ばず「要確認」**。同じ契約で期間が重なる条件は、API が登録時に断る
- **自動計算するもの（売上側だけ）**：月額（精算幅の中は固定／外は超過・控除の単価で増減）／時給（時間 × 単価）。金額は**整数（銭×分）の演算**で出し、円未満は契約条件の指定（切捨て／切上げ／四捨五入）で丸める
- **計算せず「要確認」にして理由を返すもの**：日給、月の一部だけ有効な条件（日割り。`prorate` は記録するだけ）、単価・精算幅・超過／控除の単価・円未満の丸めが未設定（超過／控除は、空＝未設定、0＝精算しない）、条件が1件も無い、稼働時間が未確定
- 稼働を確定したのに精算できない行は、一覧で「契約条件の確認」（絞り込み・今日やること）。**「要確認」（警告）とは分けて出す**（初回は条件が未登録の行が多いので、警告が埋もれないように）
- 確定した合計は、契約条件があとで変わっても**動かさない**（確定時の丸め条件・条件の id を控える）。変わったことは画面に出す

### 6.7 同じファイルの検知

- 中身の sha256 で見つける。同じ人・月・契約に同じ中身が2つ → 二重提出（Office のアップロードでは登録しない）。別の人・別の月・別の契約にも同じ中身 → 流用の疑い（承知のうえで登録し、両方に警告）
- 外部フォームの行は sha256 が空（未確認）で届く。**勤務表の画面を開いたとき**（AI読取の前）と、AI読取のときに、中身を確かめて埋める（同じ月の未確認の勤務表を、1回に10件まで。確かめたものは読み直さない）。これで、費用のかかる AI読取の前に、二重提出・流用に気づける
- 外部フォームは「行を作ってからアップロードする」順なので、ファイルが届いていない行もあり得る（そのまま未確認。読取のとき `file_missing` と案内）
- 一覧では、その月に届いたものの中だけで判定する（月をまたぐ照合は、勤務表の画面で行う）

### 6.8 対応するファイル

**PDF・JPEG・PNG だけ**（外部提出フォームと同じ。**HEIC などには対応せず、増やさない**）。形式は拡張子ではなく先頭のバイト列で決める。登録は 10MB まで。AI読取は、PDF は `document`、JPEG・PNG は `image` として渡す（画像は 5MB まで＝AI 側の上限。超えると案内して手入力へ）。

## 8. 既存 `unit_price` の調査結果（意味は決めていない）

**結論：コード・画面・DB・テスト・文書のどこにも、売上単価か仕入単価かを決めている記述は無い。実データでの確認が要る。**

- 列は `unit_price numeric(12,2)` と `unit_price_type`（月額／時給／日給）だけ（`db/076_site_contracts.sql:55-57`）
- 登録フォーム（`admin-members.html`）は「単価」「単価の種類」の2項目だけ。**PP と BP で表記も扱いも同じ**
- 検証（`lib/site-contracts.js`）は「0以上の数値」と種類の3値だけ。売上／仕入の区別なし
- 契約行の相手は「所属会社（常駐先）」＝客先と上位会社。BP 会社は契約行ではなく要員にぶら下がる。BP 契約の単価が「客先への売上単価」か「BP 会社への仕入単価」かは、構造からは決まらない
- 契約によって意味が混在していても、**システムには検出する列が無い**

**したがって**：Phase 3 の計算は `unit_price` を使わない（一覧・確認画面・契約条件の API のどれも select しない。`test/accessparity.mjs` が、105〜107 の SQL が `gw_site_contracts` に触れないことを、`test/officeapi.mjs` などが読まないことを固定している）。
新しい条件は `sales_unit_price` / `purchase_unit_price`（106）。既存値からの移行は、**実データで意味が特定できたものだけ、後から**行う。

確認のための SQL（Supabase の SQL Editor。読み取りのみ。件数と分布だけで、氏名は出さない）：

```sql
-- 区分ごとの単価の分布
select engagement_kind                                         as 区分,
       unit_price_type                                         as 種類,
       count(*)                                                as 件数,
       count(*) filter (where unit_price is null)              as 単価未入力,
       min(unit_price)                                         as 最小,
       percentile_cont(0.5) within group (order by unit_price) as 中央値,
       max(unit_price)                                         as 最大,
       count(*) filter (where coalesce(settlement_condition, '') <> '') as 精算条件あり
  from public.gw_site_contracts
 group by 1, 2 order by 1, 2;

-- 同じ客先に PP と BP の契約があるとき、単価の水準を比べる（BP が売上なら PP と近く、
-- 仕入なら PP より低くなるはず。あくまで手がかり）
select site_company                                   as 客先,
       round(avg(unit_price) filter (where engagement_kind = 'pp')) as PP平均,
       round(avg(unit_price) filter (where engagement_kind = 'bp')) as BP平均,
       count(*) filter (where engagement_kind = 'pp')  as PP件数,
       count(*) filter (where engagement_kind = 'bp')  as BP件数
  from public.gw_site_contracts
 where unit_price_type = '月額'
 group by 1
having count(*) filter (where engagement_kind = 'pp') > 0
   and count(*) filter (where engagement_kind = 'bp') > 0;
```

最終的には、**登録している人・運用している人に「BP の単価欄に何を入れているか」を聞くのが確実**。

## 9. これから

**Office の最終ゴール**：勤務表回収 → 稼働確定 → 案件・契約照合 → 売上請求 → 仕入請求確認 → 支払 → 完了。`/office` を開けば「誰の何が止まっているか」が分かる。
Phase 3 までで、勤務表回収 → 稼働確定 → 契約照合（精算の計算）が動く。残りは売上請求（Phase 5）・発注と仕入請求（Phase 6）・支払（Phase 7）・月次確定（Phase 8）。
支払の記録が無いので、BP は「支払準備」までで「完了」にしない。

## 10. 決めてほしいこと

1. **`unit_price` の意味**（§8）。SQL の結果、または運用している人の回答。実データで特定できたものだけ、`sales_unit_price` / `purchase_unit_price` へ移行する
2. **経理・責任者の MFA の扱い**：Office は MFA を要求しなくなったので、登録は要らない。ただし、経理・責任者・経営者は MFA の対象ロール（`lib/mfa.js` の `REQUIRED_ROLES`）のままなので、画面上部に登録の案内の帯が出る。案内を残すか・対象から外すかは、支払・給与などの機能を作る前に決める
3. **仕入側（BP・外注）の精算ルール**：売上側と同じ幅・単価で精算するのか、別の条件か。決まるまで、仕入側の精算は計算しない
4. **月の途中で条件が変わる月・日割り・日給**の計算方法。決まるまで「要確認」にして、自動計算しない
5. **締め日が月末ではない勤務表**（例：前月21日〜当月20日）の扱い。いまは対象月の暦日だけを取り込み、月違いの行は「対象月ではない日付」として人に直してもらう
6. **確認時間の目標**：`review_seconds`・`edit_count` を、月ごとに見る画面をいつ作るか（Phase 3 では記録まで）
7. **本番の Vercel のプランと実行時間**（`maxDuration` 60 秒で足りるか）、**本番の `ANTHROPIC_MODEL`**。`lib/ai.js`（仕訳）は `tool_choice` を強制しているため、`ANTHROPIC_MODEL` が Claude 5.5 系だと、そちらが 400 になる（勤務表の読取は強制していないので影響しない）。`.env.example` は `claude-sonnet-4-5`、コードの既定は `claude-opus-5` で食い違っている
