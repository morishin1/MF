# Sales改善v1.0 実装と受入条件

案件ID：SALES-20261117-1794903145。2026年11月17日の代表指示「すすめて」に基づく調査・実装・テスト。元の合意は https://8grp.slack.com/archives/C0CCQHQN3SM/p1794903145738739 。本番反映と実顧客へのメール送信は今回実施しない。

## 画面と既存開発の統合

| 利用者 | 画面 | 今回の扱い |
| --- | --- | --- |
| 社内Sales | GWの商談ナビゲーター | 新規商談を会社説明・企業ページ案内、目的・条件確認、商談結果・お礼の3段階に整理 |
| 営業エージェント | ENGERのagent-login、agent-meeting | enger-lp PR #314の6ステップ・自動保存・本人の成果管理を維持 |
| 企業担当者 | ENGERのbusiness/login、portal、offers | 本人認証による検索・候補確認・案件と複数人材の受付を既存機能で行う |

MF PR #384の明示的パスワード再発行UIとプレビューの実企業アカウント変更防止を取り込む。既存のSales権限・企業スコープ・確認・表示時間・レート制限を使い、既存パスワードを取得しない。MF PR #379のSTEP5・6統合案は旧フロー向けであり、新しい3段階画面へ重ねて適用しない。企業属性の同期など同PRの別機能は今回に混ぜない。

## 商談の保存

新規セッションの既存step_detailsにlayout=compact_v1を記録する。会社説明は旧stage=0、目的確認は旧stage=1、結果・お礼は旧stage=5を使う。既存DB構造とstage値を変えない。旧3〜5の課題・予算・開始時期はstage=0の入力へ、検索・候補選択は企業ページへ、結果確認は最後の画面へまとめる。

旧商談とエージェント商談にはlayoutを付けず6ステップを維持する。過去のstaff_notes・step_checks・preparationを削除・上書きしない。保存は版番号で競合を検出する。3段階の画面移動も既存の隣接stage履歴として記録するが、非表示の確認項目を確認済みにはしない。

## メール

件名と本文は編集可能。宛先・件名・本文・次回対応を変えたら確認チェックを外す。確認した文字列をそのまま送信し、本文の企業URL・ログインIDをサーバーで照合する。件名200文字、本文12000文字まで。パスワードは編集用定型文に含めず、送信時のアカウント新規作成や再発行も行わない。

既存の営業メール送信設定を使用する。v1の送信元はits@gw.8grp.co.jpと一致する場合だけ有効。設定変更や送信の有効化は実施しない。プレビューの実送信はAPIで拒否し、コピーは利用できる。既存closeoutの一意制約・送信状態・プロバイダー受付記録を使い、処理中・失敗・送信済み履歴から自動再送しない。

## 企業側の既存機能

人材検索の複数スキルは現行ENGER APIの全指定スキル一致を維持する。表示名は匿名化された公開情報。年代・国籍の公開範囲や認証権限を拡張しない。

案件名だけの新規案件は既存dx2_company_partner_submissionsのpending_reviewへ保存し、スタッフが補完する。案件・複数人材の受付は既存dx2_company_job_offersとgw_sales_company_job_offer_createを使い、Salesの提案・コンタクト履歴へ対応付ける。今回のメール終了判定では旧portal_offersと新job_offersの両方を確認する。

PR #314の「候補を保存した状態」と企業本人の正式オファーを区別する。企業ホームからの正式オファーにある本人認証・自社情報・一致率70%以上の既存条件は変更しない。案件名のみの受付は担当者確認前の相談記録であり、契約や支払の承諾ではない。

## 受入と本番反映

認証・企業境界、入力保存と再表示、競合、旧商談の維持、メール本文の一致、重複送信防止、失敗時の保存、PCと390pxの画面操作を検証する。UI検証は合成データと模擬APIを使用する。

専用の検証企業・営業／企業アカウントで、候補選択→企業ホーム→本人の正式オファー→Salesの記録を実DBで確認する工程が残る。必要な既存DB関数・送信元設定の本番確認、プレビューとテスト結果の確認後に本番反映を判断する。
