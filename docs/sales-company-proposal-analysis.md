# 企業別の提案分析

`/sales/proposals.html` の初期表示は企業分析。ENGERが提案の送付・回答・合否・失注理由の記録を担い、Salesは同じ提案の履歴を企業ごとに集計する。分析画面とAPIには業務データを変更する処理を置かない。

## 表示と確認先

- 企業一覧：送信から面談への移行、合否判明分の合格率、結果確認率、全履歴の合格・稼働・見送り、主な理由。
- 企業詳細：提案履歴、見送り理由、やり取りの3タブ。各提案から元のENGER画面へ進める。
- 失注の内訳：理由、段階（接触前・接触後・提案後・面談後）、案件側／人材側／双方／外部要因。記録がなければ未確認。
- 過去の手入力Sales記録は既存のSales詳細へ案内する。
- `?view=list` と既存の `?id=`・担当等のリンクは個別提案の表示を保つ。企業分析の絞り込みは `companyPeriod` / `companyQ` 等の別パラメータで保持する。

## 集計の意味

| 項目 | 定義 |
| --- | --- |
| 全履歴 | 検索・担当・事業条件に合う提案の全期間。送信期間を変えても過去実績を消さない |
| 送信確認 | 企業側の送付を確認できる最初の日時が、選んだJST期間に入る提案。再送で提案件数を増やさない |
| 送信 → 面談 | 上記の送信確認件数のうち、面談実施の証拠がある件数 ÷ 送信確認件数 |
| 面談後の合格 | 送信対象のうち、明示された合格 ÷ 明示された合格・不合格 |
| 結果の確認 | 送信対象のうち、合否判明件数 ÷ 現在の面談実施確認件数 |
| 結果待ち | 現在の面談実施を確認できるが、現在の合否が未確認の件数 |
| 過去の合格 | 現在のENGER合格、構造化された合格へのステージ遷移、または明示された合格記録 |
| 稼働・受注 | ENGERの稼働実績と手入力Salesの受注実績。合格には置き換えない |

送信日時にはSalesの `sent_at` / 送信履歴、ENGERの `mail_sent_at` / 案件側メールラウンドを使用する。`proposed_at` や人材側の送信を代用しない。送信日不明の過去成果は全履歴には含め、率の分子・分母には含めない。分母0は `null` として返し、画面では「— / 対象なし」と表示する。

面談予定から実施を推測しない。面談後失注は面談の証拠にはなるが、それだけで不合格にはしない。無回答・辞退・条件不一致を面談不合格に変換しない。メール回答の `pass` は「見送り」であり、面談合格とは別の値。

## ENGERとの対応

1. ENGER提案IDでSalesとの二重計上を防ぐ。Salesに取り込まれていないENGERの過去成果も対象。
2. 現在のENGERステージ・失注情報を優先し、古いSalesの進行中表示を集計に流用しない。
3. 削除された元提案は除外する。元提案が見つからないSales履歴は現在状態を未確認として明示する。アーカイブを失注とは扱わない。
4. `activity_logs` の既知のJSON `from` / `to` のみをステージ遷移として解釈する。自由記述の「合格」という単語から結果を生成しない。
5. 再開した提案は、再開前の結果を現在の合否に使わない。assessmentの結果はrevisionと記録日時を取得し、再開後の結果だけ反映する。以前の合格実績・見送り理由は履歴として区別する。

## 企業の照合

企業ID、確認済みの履歴リンク、SalesとENGERの企業リンクを優先する。IDがない場合は前後の空白を除いた企業名の完全一致で、ENGER企業マスターの候補が1社のときだけ表示上で照合する。この場合は「企業名の完全一致」と表示する。

同名の複数企業、異なる明示ID、未登録企業を曖昧に統合しない。照合は読み取り時のみで、企業データやリンクを書き換えない。

## API・権限・取得

`GET /api/sales/proposals/company-analysis` はSales権限、Eightテナント、有効な社員、既存のENGER内部メンバー判定を確認した後に読み取る。外部・パートナー・無効メンバーは拒否する。既存のreadiness APIと同じく、旧社内ユーザーのメンバー行未作成は許容する。

Salesテーブルは呼出者のクライアント・テナント・RLSを維持する。service-role専用assessmentも、呼出者が読めた提案IDに限定し、結果・revision・日時だけを取得する。ENGER側の全履歴は上記の権限確認後に読み取り、削除されていない提案に関係する履歴だけをモデルへ渡す。メール本文や連絡先は返さない。

各データソースを上限付きで最後まで取得する。サーバーの行数制限で短いページが返っても終端とみなさず、空ページまで進む。上限超過・読取失敗・不正なページは503にし、一部のデータから確定的な率を表示しない。レスポンスは `private, no-store`。

企業詳細の提案はページ分割、やり取りは直近30件と省略の有無を返す。確認先URLは既知のENGER/Sales URLと検証済みIDから組み立てる。

## 検証

```sh
node --experimental-test-module-mocks --test test/sales-proposal-company-analysis*.mjs
node --experimental-test-module-mocks test/ui/salescompanyanalysisui.mjs
node --experimental-test-module-mocks test/ui/salesproposalsui.mjs
node test/assethash.mjs
```

集計の回帰試験は重複、旧履歴、再開、日時、JST境界、失注・合否の区別、企業照合、権限とページ上限を扱う。画面試験は実際のJS/CSSで元提案リンク、エスケープ、詳細ページ、キーボード操作、390px表示、読取失敗からの回復を確認する。`salesproposalsui` は企業分析が初期表示になることと既存の個別提案操作を合わせて確認する。
