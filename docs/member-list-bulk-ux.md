## 2. 一括登録

既存の `POST /api/employees/bulk`（最大200行）を使う。一覧の下の「まとめて追加」は、上の「一括登録」へ移した。

1. **入力**：貼り付け（Excel・スプレッドシートのタブ区切り）か CSV ファイル。
   列は 氏名（必須）/ メール / 部署 / 役職 / 雇用区分 / 入社日。1行目が見出しなら見出しで列を読む（順番が違ってもよい）。
   CSV は引用符・セルの中のカンマと改行・`""`・BOM・CRLF を読む。ファイルは UTF-8、読めなければ Shift_JIS（Excel の既定）として読み、そう出す。
   読めない形（閉じていない引用符など）はプレビューを出さず、行番号つきで止める（列をずらしたまま登録しない）。
2. **プレビュー**（まだ登録しない）：行ごとに「登録できる／入力エラー／登録済み（追加しない）／ファイル内で重複（追加しない）」。
   入力エラーは、氏名なし・メールの形・雇用区分・入社日（実在する日付。2026/4/1 は 2026-04-01 にそろえる）・列が多すぎる・セルの中の改行。
   登録済みとファイル内の重複は、サーバと同じ見分け方（氏名は完全一致、メールは小文字で一致）。**いまの名簿は書き換えない。**
3. **名簿への登録とログインアカウントを分けた**
   - 既定は「名簿に登録するだけ」。基本区分「入社準備」として入る。メールは送らない。本人はまだログインできない。
   - 「ログインアカウントも作る」を選ぶと、次の画面で対象（メールがある人）と起きることを出し、確認のチェックのあとで登録する。
     起きること＝そのメールでログインを新しく作る（同じメールが既にあれば紐づける・パスワードは変えない）／無限道場・タイムカード・会計にも登録／**メールは送らない**／初回パスワードは1回だけ表示。
   - これまでの画面は「メールがある人はログインアカウントも作る」が最初から ON だった。サーバも省略時に作っていた。**どちらも明示したときだけに変えた**（下の 4.）。
4. **結果**：名簿に追加／重複で追加しなかった／失敗 と、アカウントの 新しく作成／既存に紐づけ／作れなかった／メールなし を分けて出す。行番号は元のファイルの行。
   - 失敗した行だけを入力欄に戻せる（直してもう一度プレビュー）。成功した人は次のプレビューで「登録済み」になり、送られない。
   - 名簿には入ったがアカウントだけ作れなかった人は、その人だけ「アカウント作成を再試行」（既存の `POST /api/employees/link`。名簿は増えない）。
   - 二度押しでも1回しか送らない（送信中は押せない）。

## 3. 一括の退職／削除

### 退職にする（利用停止）

既存の在籍状態の変更（`PATCH /api/employees { status: "left" }`）を1人ずつ呼ぶ。新しい処理は作っていない。

- 対象外：自分自身・すでに退職・（経営者でない人が開いたとき）経営者。サーバも経営者・最後の経営者を止める（lib/owner-guard.js）。
- 確認の窓：起きること（入れなくなる・ログインと記録は残る・名簿から消えない・基本区分を戻せば開け直す＝元に戻せる）と、確認のチェック。
- 結果は人ごと（各システムを止めた結果も）。成功した人は選択から外れる。

### 名簿から削除（誤登録）

既存の `DELETE /api/employees?id=` は**名簿の行の物理削除**。ログインアカウント（auth.users）は残すが、無限道場・タイムカードを止め、会計の権限を外す。復元できるアーカイブではない、と窓にそのまま書いた。

1. まず1人ずつ「消せるか」を確かめる（**まだ消さない**）：新しい `GET /api/employees?deleteCheck=<id>`。DELETE と同じ判定を、同じ関数（`checkDeletable`）で返す。
2. 人ごとに「削除できる／削除できない（理由）／確認できない・見つからない」。確認できない人は消さない。
3. 削除する人数を半角数字で入れて確定（強い確認）。退職とは別の窓・別のボタン。
4. 実行は1人ずつ。サーバが毎回同じ判定をし直す。結果は人ごと（一部失敗を全件成功にしない）。成功した人は選択から外れ、二度と送らない。
5. 「失敗した人を確かめ直す」は、失敗した人と確認できなかった人だけを確かめ直す。

## 4. サーバの変更（理由つき）

| ファイル | 変更 | 理由 |
|---|---|---|
| `api/employees/index.js` | `relatedRecords()` で数えられなかった表があれば、削除を止める（503 `related_lookup_failed`） | これまで読めない表を「記録なし」として飛ばしていた（`if (error) continue`）。経費・申請などが道連れで消えうる。表そのものが無い（PGRST205・42P01＝未適用）だけは、その表に記録が無いので続ける。列が無い（42703）は「読めなかった」に入れる |
| 同上 | `GET ?deleteCheck=<id>`（消さずに判定だけ） | 確認の窓で「消せる／消せない」を実行前に出すため。DELETE と同じ関数を使う |
| 同上 | 止めた削除を記録（`employee.delete_blocked`）。見つからない（二重送信・消えた後）は 404 で記録しない | 監査。二度押し・再送で何も起きないことを確かめられる |
| 同上 | 対象の人を読めなかったら 500（「いない」404 にしない） | 読めないのを「いない」と言わない |
| `api/employees/bulk.js` | `createAccounts === true` のときだけアカウントを作る | 省略時に黙って作っていた |
| 同上 | 追加した行に `account`（created / linked / failed / no_email / not_requested） | 「名簿は成功・アカウントは失敗」を画面が推測しないで済むように |
| 同上 | アカウントの作成・紐づけを1人ずつ記録（`account.create` / `account.link`）。まとめの記録に件数 | 1人ずつの追加（POST /api/employees）と同じ記録を残す |
| 同上 | いまの名簿を読めなかったら取り込まない（500） | 「誰もいない」として全員を足すと、二重に登録される |
| 同上 | メールの形・入社日（実在する日付）をサーバでも確かめる | 画面を通らない呼び出しでも、壊れた行を足さない |

同時に二人が同じ内容を一括登録した場合の二重登録は、DB に一意の制約が無いため、完全には防げない（画面は二度押しを止め、サーバは送信のたびに氏名・メールで飛ばす）。
