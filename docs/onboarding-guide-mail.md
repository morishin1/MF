# 入社案内・案内URL・案内メール・本人の入社準備（`/onboarding/`）

経営者が入社案内を作り、期限つきのURLで（またはメールで）本人へ渡し、本人が6ステップで入社準備を進める。
**新しい状態判定は作っていない。** 6ステップは、既存の判定（段階 `computeStage`・キャリア `careerStatus`・契約・提出の事実）を並べ替えたもの。
足りなかった事実（案内を発行したか・本人が確認したか・URL・メールの履歴）だけを、表（`db/104`）として持つ。

> 状態: 実装済み・テスト済み。**本番DBへの適用・本番のメール送信は、まだ行っていない。**
> メールは、環境変数を設定するまで送られない（設定しても、`MAIL_SEND_ENABLED=1` にするまで送られない）。

## 1. 流れ

```
経営者（/keiei → 入社準備 → 人を選ぶ）
  ① 入社案内を書く（集合時間・場所・持ち物・連絡先…）→ 下書き保存
  ② 発行する（確定版が残る。版1）
  ③ 案内URLを発行 →（メール未設定）URLをコピーして、チャット等で本人へ
                 →（メール設定済み）文面を見る → テスト送信（自分あて）→ 本人へ送信
本人
  ④ 案内URL（/onboarding/?t=…）を開く → ログイン前に、入社案内を読める
  ⑤ ログイン → /onboarding/ で6ステップ。①「入社案内を確認しました」を押す（日時が残る）
  ⑥ 雇用契約・入社情報・必要書類は、これまでの画面（contracts.html / onboarding.html）で行う
  ⑦ すべて済むと「入社準備完了」
経営者
  ⑧ 一覧・詳細で、いまどこか・次に誰が何をするか・URLを開いたか・メールの履歴を見る
```

## 2. 6ステップ（経営者の一覧と、本人の画面で同じ）

判定は `lib/onboard-six.js` の1つ。違うのは言い方（`audience`）だけで、状態は同じ（テストで確認）。

| # | ステップ | 元になる既存の事実 | 担当 |
|---|---|---|---|
| ① | 入社案内確認 | 経営者が発行した案内を、本人が確認したか（`gw_onboarding_guides`）。**案内が無ければ「対象外」**（数えず、ほかを止めない） | 本人 |
| ② | 雇用契約 | 段階 `conditions` → `advisor_review` → `signing`。締結と誓約書の同意で完了 | 会社 → 社労士 → 本人 |
| ③ | 入社情報入力 | 段階 `intake`。入社情報の提出 | 本人 |
| ④ | 必要書類提出 | 段階 `intake`。必須書類・オリエンテーションの確認 | 本人 |
| ⑤ | 会社確認 | 段階 `intake`。社内準備（チェックリストの社内項目）。③④ と並行 | 会社 |
| ⑥ | 入社準備完了 | 段階 `complete`。案内が発行されていれば、確認済みであること | — |

- キャリア設計はステップに入れず、**完了のあとの「次の一手」**として添える（`careerStatus`。上長の設定待ち・本人の確認待ち）。
- **本人に、給与・手当などの金額は出さない。** 社内準備の内訳（PC・アカウントなど）も出さず、「会社が準備・確認しています」だけ。
- 表が読めないとき（`db/104` 未適用など）は、完了とも要対応とも言わず「データ未連携」。

## 3. 画面とAPI

| 対象 | 場所 | 誰が |
|---|---|---|
| 本人の入社準備 | `/onboarding/`（`onboarding/index.html`）・`GET/POST /api/onboarding/start` | ログインした本人（自分の分だけ） |
| 案内を読む（ログイン前） | `GET /api/onboarding/guide?t=…` | 案内URLを持つ人。開くだけ（確認・入力はログイン後） |
| 経営者の一覧 | `/keiei#onboarding`・`GET /api/keiei?view=onboarding` | 経営者のみ |
| 経営者の詳細（案内・URL・メール） | `/keiei#onboarding/<社員ID>`・`/api/keiei/onboarding` | 経営者のみ・二段階認証つき |

`/api/keiei/onboarding` の操作: `save_guide` / `issue_guide` / `create_invite` / `revoke_invite` / `preview_mail` / `test_mail` / `send_mail`（履歴は GET）。
入口は `lib/keiei-gate.js`（`canKeiei` → `requireMfaStrict`）。HR・人事・管理者は、案内も履歴も見られない（DB も同じ）。

## 4. データ（`db/104_onboarding_guide.sql`）

| 表 | 内容 |
|---|---|
| `gw_onboarding_guides` | 入社案内（1人1つ）。下書きの8項目・いまの版・本人が確認した版と日時 |
| `gw_onboarding_guide_issues` | 発行した確定版（版ごと）。あとから直しても、送った内容は残る |
| `gw_onboarding_invites` | 案内URL。**トークンは平文で持たず、ハッシュだけ**。期限・失効・開いた回数 |
| `gw_mail_messages` | メールの履歴。本文の確定版・宛先・送信者・時刻・提供元・結果（sent / failed / skipped） |

すべて RLS は経営者のみ（`gw_is_owner`）。本人は、APIを通して、自分の発行済みの案内だけを読む・確認する。
既存の表・列は変えない。`db/099` が前提。元に戻す SQL・確認 SQL は、ファイル冒頭にある。

## 5. 案内URL

- 形: `https://<ホスト>/onboarding/?t=<43文字のトークン>`。基準は `PUBLIC_BASE_URL`（無ければ、開いているホスト）。
- 有効期限は既定7日（1〜30日）。新しいURLを作ると、前のURLは失効する（テスト送信用のURLは別扱いで、失効させない）。
- **URLは、発行した応答にだけ出る。** あとから取り出せない（必要なら発行し直す）。DB・操作ログにも平文は残らない（メール履歴の本文も、トークン部分だけは保存しない）。
- **開くだけ。** パスワードの代わりにならない。確認・契約・入力・書類は、ログインしてから。別の人のURLでログインしたら止まる（`wrong_account`）。
- 無効・失効・案内なしは、理由を問わず「開けません」（404）。期限切れだけ区別する（410。本人が担当者へ連絡できるように）。
- ページは `no-referrer`（URLを外部のフォント配信元などへ渡さない）。API は `no-store`。
- ログイン後の戻り先は `?next=`。このサイトの中のパスだけ（外へは行かない。`index.html` の `nextPath`）。

## 6. 案内メール

### 方針（決定）

- **送信サービスは Resend で進める。** 今の抽象化（`lib/mail/index.js` の `ADAPTERS` ＋ `lib/mail/resend.js`）は**そのまま維持**する。
- 送信元は環境変数 `HR_ONBOARDING_FROM`（コードに直接書かない）。
- **本番では `MAIL_SEND_ENABLED=1` にしない。本番からのメール送信はしない**（§7 の手順を、承認のうえで行うまで）。
- Google Workspace（Gmail API など）への切り替えは、いまは不要。必要になったときに送信サービスを足せるよう、**部品を足すだけの構造**（下の「送信サービスの交換」）を残してある。

### 環境変数（コードに送信元を直接書かない）

| 変数 | 内容 |
|---|---|
| `HR_ONBOARDING_FROM` | 送信元。`エイト 人事 <hr@example.com>` か `hr@example.com` |
| `MAIL_PROVIDER` | 使う送信サービス（いまは `resend`）。空なら実送信しない |
| `MAIL_SEND_ENABLED` | `1` のときだけ実送信する。**既定は止まっている** |
| `MAIL_REPLY_TO` | 返信先（任意） |
| `RESEND_API_KEY` | Resend を使うとき |
| `PUBLIC_BASE_URL` | 案内URLの基準（任意） |

### 未設定のとき

どれかが欠けている・`MAIL_SEND_ENABLED` が `1` でない、のどれでも「未設定」。
**実送信せず、履歴も作らず**、画面は理由を出して、「案内URLを発行」から、URLをコピーして渡す形になる（送信・テスト送信のボタンは押せない）。
文面の確認（プレビュー）と、URLの発行は、未設定でもできる。

### 文面（自動作成。金額・パスワードは書かない）

件名 `【会社名】ご入社にあたってのご案内`。本文は、宛名・入社日（確定済みの日付だけ。無ければ書かない）・
「入社準備を始める」のURL・有効期限・「ログイン情報は、このメールには書いていません。担当者から別の方法でお伝えします」。
AI は使っていない（日付・条件・期限を作らない）。

### 送信サービスの交換

呼ぶ側（`api/keiei/onboarding.js`）は `sendMail()` と `mailConfig()`（`lib/mail/index.js`）だけを使う。
別のサービス（Gmail API・SES・SendGrid・SMTP など）へ替えるには、同じ形の部品を1つ足して `ADAPTERS` に1行加える。

```js
// lib/mail/<name>.js
export const name = "<name>";
export function ready(env) { return env.<KEY> ? { ok: true } : { ok: false, reason: "<KEY> が設定されていません" }; }
export async function send({ from, to, subject, text, replyTo }, { env, fetchImpl }) { /* 失敗は throw */ return { id: "…" }; }
```

宛先・件名の検査（形式・改行）と、失敗を履歴に残す処理は、窓口が持つ。自動の再試行はしない（二重送信を避ける）。

### 履歴

送信・再送・テスト送信は、1通ずつ `gw_mail_messages` に残る（本文の確定版・宛先・送信者・時刻・提供元・結果）。本文のうち、案内URLの**トークン部分だけは保存しない**（どのURLかは `invite_id` で分かる）。
一覧は本文を出さず、「本文」ボタンで開く。失敗（`failed`）も残り、そのURLは有効のまま（届いている可能性があるため）。

## 7. 本番でメールを有効にする前に（まだ行わない）

1. `db/104` を適用する（`docs/keiei-production-rollout.md` の手順に従う）。
2. 送信元のドメインで、SPF・DKIM・DMARC を設定する（送信サービスの指示どおり）。
3. **まず、本番以外の環境**（Preview など）で `HR_ONBOARDING_FROM`・`MAIL_PROVIDER`・鍵を設定し、`MAIL_SEND_ENABLED=1` にして、
   「テスト送信（自分あて）」で届き方・文面・URLを確認する。
4. 本番に同じ設定を入れ、`MAIL_SEND_ENABLED=1` は**最後**に入れる。最初は、自分たちの誰かあてに1通だけ「本人へ送信」して確認する。
5. 異常があれば、`MAIL_SEND_ENABLED` を外すだけで、送信は止まる（案内URLのコピーは使える）。

  メールには書かない。期限つきの設定用URL（Supabase のリンクで、パスワード設定画面を作る）は、別の段階で作る。
