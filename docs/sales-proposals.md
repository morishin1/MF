## 1. 役割分担と正本

| 項目 | dx.enger | /sales（グループウェア） |
|---|---|---|
| 案件・人材・マッチング・提案の作成と送信 | **正本**（`enger.proposals`） | 持たない（提案ID・社名・案件名・人材のイニシャルの写しだけ） |
| 提案後の営業担当・電話・メール・回答確認・次の行動・期限 | 参照（状態 API） | **正本**（`gw_sales_proposals` ほか） |
| 面談・見送り・成約・再提案依頼（営業の結果） | 状態 API で表示 | **記録の正本** |
| 人材の差し替え・再マッチング | **正本** | 「再提案依頼」の状態で返す |

- **DB は別プロジェクト**：dx.enger は Supabase `htglvascsuqkixpmclwr`（LMS と同居）、グループウェアは
  `vuqzsuhwuznclqxxtgfn`（`docs/SETUP_APP.md`）。表を直接つなげないので、**署名付きのサーバー間 HTTP** で連携する
  （先例：無限道場 LP → 採用HR `docs/hr-leads.md`）。
  ※ `db/021` のコメントに「この Supabase は ENGER と共用」とあるが、`.env.example`・`docs/SETUP_APP.md`・
  dx.enger の `docs/supabase.md` はどれも別プロジェクトを指している。本番の Vercel の値は**未確認**。
- **提案を二重に作らない**：dx.enger の提案ID（`enger.proposals.id`）を `source_proposal_id` にして1件だけ持つ。
- **人材の氏名・スキルシートは持たない**：案件名と人材のイニシャル（`c_init`）だけ。

## 2. 営業フロー（初期値。管理者が「フォローの設定」で変えられる）

| いつ | 何が起きる | 期限 |
|---|---|---|
| 提案送信（T0。dx.enger で**企業向けの提案メールを送った**とき） | 提案を起票・電話タスク | 営業時間内なら送信から **30分**。始業前はその日の始業＋30分、終業後・土日祝・自社休業日は次の営業日の始業＋30分 |
| 電話「不通」「担当者不在」 | 確認メールのタスク・状態「メール待ち」 | **その営業日の終業**まで（終業後・休日なら次の営業日の終業） |
| 電話「折り返し予定」「再連絡希望」 | 電話のタスク（先方の日時） | 入力した日時 |
| 電話「通話できた」 | 内容（必須）で分ける：面談調整へ／検討中／見送り／別候補希望 | 面談調整→翌営業日の終業までに日程確定。検討中→3営業日後に確認 |
| 電話「連絡不可・連絡停止希望」 | 状態「連絡停止」・開いているタスクを取り消し・**自動の追客を作らない** | — |
| メール送信 | 回答確認のタスク・状態「回答待ち」 | **翌営業日の終業** |
| 回答確認「返信なし」（1回目） | 再フォロー（再電話／再メール） | **提案から3営業日後**の終業（過ぎていればいまの営業日） |
| 回答確認「返信なし」（2回目） | 管理者確認（継続・保留・クローズ）。担当は営業担当の上長（`gw_employees.manager_id`。いなければ未定＝管理側の一覧） | **提案から5営業日後**の終業 |
| 企業から返信 | 電話・メール・回答確認・再フォロー・管理者確認を完了にする。内容で状態を進める | — |
| 面談 日程確定／実施／取りやめ | 面談調整（面談日時）／面談実施（成約・見送りの確定タスク）／日程の決め直し | — |
| 成約・見送り・連絡停止・クローズ | 開いているタスクは**取り消し**（完了にはしない） | — |

- 営業時間：9:00〜18:00、土日・祝日・年末年始は `lib/holidays.js`、自社休業日は設定（`extra_holidays`）。
- 自動のタスクは **提案ごとに同じものを1つだけ**（`source_event` の一意索引）。開いている同じ種類のタスクがあれば作らない。
- 終業間際（17:50 など）に送った提案の初回電話の期限は、送信から30分（18:20）。翌朝に回さない。

### 状態と理由コード

`電話待ち → メール待ち → 回答待ち → 面談調整 → 面談実施 → 成約／見送り`、分岐に `継続検討` `再提案依頼` `連絡停止` `クローズ（無回答）`。

| 状態 | 理由コード（企業側・人材側・営業判断を分ける） |
|---|---|
| 見送り | 企業側の見送り／人材側の辞退／他で充足・募集終了／その他（**必須**。無回答は見送りの理由にしない） |
| 連絡停止 | 連絡停止の希望（必須） |
| クローズ（無回答） | 無回答（必須） |
| 継続検討 | 営業判断の保留／企業が検討中（任意） |
| 再提案依頼 | 別の候補を希望／人材側の辞退（任意） |

### 「完了」の決まり

- 電話の記録は **結果・実施者・実施日時が必須**（API と DB の CHECK の両方で止める）。チェックだけでは記録にならない。
- 自動のタスク（電話・メール・回答確認…）は、**記録をすると完了**になる。チェックで完了にはできない（`needs_record`）。
- 手動のタスクの完了は「何をしたか」が必須。完了・取り消し・期限変更はすべて行動の履歴に残す（タスクも消さない）。
- メールはまだ /sales から送らない。テンプレートを出し、送ったことを **自己申告**として記録する（画面・履歴に明示）。

## 3. 画面（`/sales/proposals.html`）

- **今日やること**：今日の電話・メール・回答確認・面談調整・期限超過（赤）・（管理側）担当未割当
- **絞り込み**：対応中／本日対応／期限超過／電話未実施／メール待ち／返信待ち／面談調整／再提案待ち／担当未割当（管理側）／企業未紐付け／完了／すべて。サービス・担当・検索・並べ替え（期限超過・期限が近い順／経過が長い順／提案日）
- **一覧の列**：提案日時・企業・種別・提案（案件／イニシャル）・マッチング担当・営業担当・進捗・次の行動と期限・経過日数・電話・メール・連携
- **詳細（右）**：次の行動と記録ボタン／先方の窓口（電話は `tel:`）／チェックリスト（電話→不通時メール→回答確認→再フォロー→結果確定）／タスク（期限変更・完了・取り消し、完了と取り消しの履歴）／提案の情報（dx.enger へのリンク・営業担当の変更・企業の紐付け）／行動の履歴
- **スマホ（760px 未満）**：表の代わりにカード（企業・次の行動・期限・電話の状況・担当）
- **管理側だけ**：担当別の KPI・dx.enger 連携の確認（エラー・要確認）・フォローの設定

## 4. 見える範囲と権限

| 人 | 見える提案 | できること |
|---|---|---|
| 営業担当（Sales のアプリ権限） | **自分が担当の提案だけ** | 電話・メール・返信・面談・結果の記録、手動タスク、期限変更（理由必須）、窓口・企業の紐付け、自分が担当の提案の手入力 |
| 管理側（経営者・マネージャー・会計の管理者で、Sales を使える人） | テナントの全件・担当未割当 | 上に加えて 担当の割り当て・変更、管理者確認（継続・保留・クローズ・再開）、自動タスクの取り消し、設定、連携エラーの確認 |
| Sales を使えない社員・退職者・別テナント・ログインなし | 見えない | — |

- 判定は DB の RLS（`gw_sales_proposal_visible`）と API（`canManageProposals`・担当の確認）の**両方**で止める。URL の `owner=all` で範囲は広がらない。
- 担当を変えても、過去の記録（誰が電話したか）は書き換えない。開いているタスクだけ新しい担当へ移す。

## 5. 企業との関係

- 提案は**提案単位**、連絡の履歴は**企業単位**にも集約する：提案が /sales の企業に紐付いていれば、電話・メール・返信・面談を
  企業の営業履歴（`gw_sales_events`）に「提案フォロー：電話：不通」のように写し、企業の最終連絡日時を進める。
  企業のステータスは提案では動かさない（案件と企業の関係を混同しない）。
- **社名だけでは紐付けない**。dx.enger の企業ID（`proposals.company_id`。dx.enger 側で未設定のことが多い）の紐付け
  （`gw_sales_company_links`）→ サイトのドメインがちょうど1社一致、の順で決め、決まらなければ「企業未紐付け」で出して人が選ぶ。
  手で紐付け・付け替え・解除・提案から企業を登録したときは、行動の履歴と監査ログ（`sales.proposal_link`）に残す。

## 6. 連携 API

鍵 `ENGER_SALES_SECRET`（両方に同じ値・32文字以上）。テナントは `SALES_PROPOSAL_TENANT_ID` で固定（リクエストからは決めない）。

| ヘッダー | 値 |
|---|---|
| `x-gw-timestamp` | UNIX 秒（前後5分まで） |
| `x-gw-signature` | `v1=` + hex(HMAC-SHA256(secret, `${用途}.${timestamp}.${canonicalJson(body)}`)) |

用途は起票 `proposal`、状態 `proposal-status`。`canonicalJson` は `lib/hr-leads.js` と同じ（キーを並べ替えた JSON）。
HR リード（用途なし）・自治体 LP（`sales.`）の署名とは混ざらない。

### `POST /api/sales/proposals/intake`（dx.enger → Sales）

```json
{
  "event_id": "enger:proposal.sent:<提案ID>:<送信ごとの値>",
  "event_type": "proposal.sent",          // または proposal.updated（ステージの更新・担当の補完）
  "occurred_at": "2026-10-19T01:00:00Z",
  "proposal": {
    "id": "<enger.proposals.id>", "code": "P-0001", "url": "https://agent.enger.jp/proposals/<id>", "stage": "提案中",
    "sent_at": "2026-10-19T01:00:00Z", "service": "ENGER", "job_title": "Java 開発", "talent_initials": "T.K.",
    "company": { "id": "<enger.companies.id か null>", "name": "株式会社〇〇", "website": "https://…", "phone": "03-…" },
    "contact": { "name": null, "email": "<提案メールの宛先>", "phone": null },
    "matching_owner": { "name": "<提案者>", "email": "…" },
    "sales_owner": { "name": "<CL担当>", "email": "…" }
  }
}
```

- まとめて送るときは `{ "events": [ … 50件まで ] }`。
- 返り値：200 `{ ok, results: [{ event_id, result: created|updated|replayed|skipped|error, proposal_id, warnings }] }`。
  400 `invalid_body`（`field`。**直さない限り同じなので再送しない**）／401／503 `not_configured`・`not_ready`／500（**再送してよい**）。
- 冪等：同じ `event_id` は1回だけ（`replayed`）。同じ提案は1件だけ。送り直し（別の `event_id`）は「再送」の記録だけで、タスクは増えない。
  下書き（`sent_at` が無い）・まだ無い提案の `proposal.updated` は起票しない。終わった提案は再開しない。
- 営業担当：`sales_owner.email` → 社員名簿のメール（小文字・在籍中・同じテナント）→ 表示名（空白を除いてちょうど1人）。
  決まらなければ担当未割当で起票し、管理側へ通知・「連携の確認」に `owner_unmatched`。

### `POST /api/sales/proposals/status`（dx.enger → Sales の読み取り）

本文 `{ "source_proposal_ids": [ … 100件まで ] }` → `{ ok, items: [{ source_proposal_id, status, status_label, close_reason,
close_reason_label, closed, contact_stop, sales_owner_name, last_call, last_mail_at, replied_at, meeting_at, next_task, overdue,
reproposal_requested, url, updated_at }], missing: [...] }`。窓口の連絡先・記録のメモは返さない。

## 7. KPI の定義（提案管理の「KPI」・担当別）

対象は **直近30日に送信した提案**（`days` で変更可）。営業担当は自分の分、管理側は全体と担当別。

| KPI | 定義 | 初期目標 |
|---|---|---|
| 提案後の電話実施率 | 電話を1回以上記録した提案 ÷ 対象の提案（**電話の前に連絡停止の希望が来た提案は分母から外す**） | 100% |
| 電話の期限内実施率 | 初回電話タスクのうち期限までに完了 ÷（完了＋期限を過ぎて開いている）。取り消しは外す | 90% |
| 初回電話までの時間 | 提案送信 → 最初の電話の記録（分）の中央値 | — |
| 不通時のメール実施率 | 不通・不在のあとに作ったメールのタスクのうち完了 ÷（完了＋期限を過ぎて開いている） | 100% |
| 提案→面談率 | 面談調整以降に進んだ提案（または面談の記録がある提案）÷ 対象の提案 | 20% |
| 面談→成約率 | 成約 ÷ 面談調整以降に進んだ提案 | 30% |
| 期限超過 | 開いていて期限を過ぎたタスクの数 | 0 |

- 担当は「いまの営業担当」で数える。電話・メールの実施は「記録した人」（`employee_id`）のまま。
- **自社が電話・メールしていない無回答は、企業の応答に数えない**（企業応答スコアは Phase 3。§9）。
- 取り消し：提案は消さない（消すポリシーが無い）。見送り・クローズは状態と理由コードで分ける。

## 操作マニュアル（ヘルプ用）

### 営業担当

1. ヘッダーの **「提案」** を開く。上の「今日の電話」「期限超過」を押すと、その提案だけに絞れる
2. 提案を押すと右に詳細が出る。**電話番号を押して電話**し、「電話の結果を記録」で結果を選ぶ
   - 不通・不在 → 「確認メールを送る」タスクができる。テンプレートをコピー（またはメールソフトで開く）して送り、「確認メールを送った」を押す
   - 折り返し予定・再連絡希望 → 日時を入れる（その日時に電話のタスク）
   - 通話できた → 面談調整・検討中・見送り・別候補希望のどれかを選ぶ
   - 連絡停止を希望された → 「連絡不可・連絡停止希望」（以後、自動で追客しない）
3. 翌営業日に「返信を確認する」タスク。返信があれば「企業から返信あり」、無ければ「返信なし（回答確認）」
4. 面談が決まったら「面談」→ 日程確定。実施したら「面談実施」。最後に「結果・状態」で成約・見送り（理由を選ぶ）
5. 期限を変えるときは理由を入れる。タスクはチェックだけでは完了にならない（記録すると完了になる）

### 管理者（経営者・マネージャー）

- 「担当未割当」の提案に営業担当を割り当てる（詳細の「営業担当 → 変更」）
- 「期限超過」と下の KPI（担当別）で滞留を確認する
- 5営業日で返信の無い提案には「管理者確認」タスクが来る。「管理者の判断」で 継続（次の連絡日時）・保留・クローズ を決める
- 「dx.enger 連携の確認」：担当を決められなかった提案・受け付けに失敗した連携が出る。対応したら「確認済みにする」
- 「フォローの設定」：営業時間・初回電話の期限（分）・再フォロー／管理者確認の営業日数・自社休業日
