## 2. 最小の制作・公開フロー

1. 事業と目的、campaign、原稿種別（press / column / youtube_reference）を選び、正本原稿を作成。
2. 原稿の版を固定し、選んだ媒体ごとの派生文を作る。タイトル、本文、画像参照、CTA、リンク、文字数を媒体に合わせる。自動生成案も未承認の下書き。
3. サイト/SNSごとに公開先を明示選択。未接続先は選べず、接続/費用承認待ちの理由を表示。
4. 媒体別プレビューで実際の公開文、事業/アカウント、宛先URL、リンク計測、画像、公開予定日時を確認。複数媒体の一括確認だけで個別差分を隠さない。
5. 公開対象と承認済み版を確認し、本人が明示的に公開操作。確認後に正本/派生文が変わったら承認を無効化し再確認。
6. 媒体ごとの結果/外部投稿ID/URLを公開履歴へ記録。成功した公開は後続失敗で取り消した扱いにしない。
7. 公開後は指標の取得範囲・更新日時とともに確認し、次回原稿/CTA/対象媒体を改善。

YouTubeは既存の公開URLと動画IDを再利用する。動画アップロード、新チャンネル作成、再アップロードは対象外。公開済み動画の確認と各サイトへの掲載を区別する。
press原稿のサイト掲載と、外部プレス配信サービスへの有料配信は別機能。後者の契約・費用・実行承認は今回に含めない。

## 4. 正本・ID・履歴（論理モデル案）

- `content_id`：原稿を一意に識別する不変ID。事業/tenant、種別、正本原稿、版、担当を持つ。既存制作予定を拡張できるか先に確認し、独立台帳を重複作成しない。
- `campaign_id`：目的/期間/対象事業の施策ID。原稿と別。単発も明示的な単発campaignへ紐付け、未分類を別扱いにする。
- `variant_id`：contentの版×公開先アカウント×媒体の派生文。原稿変更後の既公開文は上書きせず履歴として保持。
- `publication_id`：1媒体への公開試行を識別。content/variant/campaign、承認版、実行者、公開先、状態、外部ID/URL、確認時刻、失敗分類を保持。
- 変更/承認/公開/結果照合履歴は追記。秘密token、不要な問い合わせ本文、個人連絡先を履歴へ複製しない。
- 編集権限と公開権限は別判定。Marketing利用権限だけで元サイト/SNSの権限を得ない。

## 5. 二重投稿・部分成功・不確実結果

公開操作ごとの冪等キーに加え、tenant＋variantの承認版＋公開先の一意性を持たせる。複数回クリック、タイムアウト後の同一操作再送で二重公開しない。公開前に保存済み状態/外部IDを再確認。

状態例：下書き → 確認待ち → 承認済み → 実行中 → 公開確認済み / 失敗確定 / 結果不明。
外部が受け付けたが公開確認できない場合は結果不明とし、成功にも失敗にも決めつけない。読取照合・公開先管理画面で確認し、確定前に盲目的再試行しない。実装上の一意制約・ロック・版比較と、外部サービスの冪等対応を別々に検証する。

複数媒体は個別結果表示。例：サイト成功/SNS失敗でも「全部失敗」「全部成功」にしない。再試行は失敗確定した媒体だけを再確認・明示選択。外部投稿削除や差替えは別承認操作で、ロールバックとして自動実行しない。

## 6. 計測・原本帰属

UTM候補：source=媒体、medium=配信種別、campaign=campaignの公開用識別子、content=variantの公開用識別子。氏名/email/電話/内部機密をURLへ含めない。公開先ドメインとリンク先を検証し、既存クエリを破壊しない。

フォーム原本は既存IDを正本とし、許可された計測メタデータだけを受信時に関連付ける。予約も元の予約IDで関連付ける。本文をMarketingへ複製しない。追跡値は利用者が変更できるため、本人認証/権限証明として使わない。

- 初期の帰属候補は「問い合わせ/予約前の最後の確認済みcampaign接触」。計測期間/失効時間と採用モデルは代表確認後に固定する。
- first-touch、last-touch、補助接触を同じ成果として加算しない。モデル変更後も旧集計の条件を追跡可能にする。
- UTM欠落・別端末・電話・手動紹介などは帰属不明/自己申告。推測で媒体へ割り振らない。
- 電話受付は本人が確認したきっかけを任意の自己申告として別記録可能。ただしデジタルの確認済み接触と同精度に扱わない。
- 問い合わせ→予約→売上の変換は、許可された原本ID連携がある場合だけ。名寄せだけで自動結合しない。
- 同じ原本IDの再送を除外し、媒体またぎ重複は識別できる範囲だけ重複除外。未解消なら合算しない。
- 分析用集計もtenant/事業/原本の読取権限を守る。担当付与やグラフクリックで権限を増やさない。権限剥奪時に原本・関連集計へのアクセスを再評価する。

## 7. KGI / KPIの区別

| 指標 | 意味 / 原本 | 注意 |
|---|---|---|
| PV | 計測対象ページの閲覧イベント | 人数ではない。bot/社内除外・期間・同意範囲を明示 |
| 反応 | 媒体別のいいね/コメント/保存等 | 媒体ごとに定義が違う。単一の「反応合計」を無条件に作らない |
| クリック | CTA/リンクの確認できたクリック | PV/投稿表示回数とは別。CTRは同じ対象/期間の分母がある場合のみ |
| 問い合わせ | 権限内の問い合わせ原本 | 重複/無効除外ルールと新規受付期間を固定。対応待ち数と混ぜない |
| 予約 | 予約原本の確認済み状態 | 申込/仮予約/承認済み/キャンセルを分離 |
| 売上 | 売上の正本で確定した金額 | 問い合わせ・予約金額から推定しない。入金、売上計上、税込/税抜、取消を分ける |

KGI候補は事業ごとの「有効問い合わせ」「確定予約」「帰属が確認できる売上」から代表が選ぶ。未連携の売上を仮のKGI達成実績にしない。
KPIは発信数/公開までの日数/期限超過/担当未定、媒体別クリックや反応、原本連携できた段階転換率。制作量だけを成果と呼ばない。
目標差は同じ事業・期間・定義の実績−目標、達成率は目標>0のときのみ。目標0は率算出対象外。期間途中の比較は同経過日数等の条件を明示。

## 8. ダッシュボード・グラフ仕様

最上段：対象事業/期間/最終更新/計測範囲、KGI実績・目標差・帰属不明割合と課題。
次段：今の課題から改善行動へ。各グラフをクリックすると同じ条件の権限内根拠一覧へ移動。

- 棒：比較可能な同定義/期間の媒体別クリック、問い合わせ、制作期限超過。定義差がある媒体は別系列/別図で比較限界を明記。
- 折線：連続した計測期間の推移。欠測日はnullの切れ目、取得確認済み0だけ0点。前期間比較も同条件がある場合だけ。
- 円/ドーナツ：相互排他的で網羅性が確認できる構成比のみ。不明を分母から隠さず一分類として出す。媒体重複を除去できない成果には使わない。
- ファネル：同一母集団のクリック→問い合わせ→予約等がID連携できる場合だけ。連携不能な件数を並べて転換率にしない。
- 全グラフに数値ラベル/表の代替、色以外の区別、期間/定義/更新時刻。小画面とキーボードの根拠遷移を検証する。

表示状態：
- **0**：対象期間・権限・範囲を正常取得して該当なし。
- **未計測/未接続**：取得経路/イベントなし。0にしない。
- **未設定**：目標/期間/帰属ルールが未決。実績欠落とは別。
- **取得失敗/権限なし**：再取得/本人権限確認が必要。成功空配列に変換しない。
- **一部取得/上限あり/遅延**：集計範囲の制約を目立たせ、全体の率や合計を確定値扱いしない。

既存APIだけの現在のローカルグラフ候補は、対応待ち原本の比較と制作の期限超過/担当未定まで。PV/反応/目標差/売上の実計測完成ではない。

## 9. 最小受入条件

1. 制作原稿/版/派生文/公開先選択/プレビュー/明示公開の一貫性。確認後変更は再確認。
2. 権限なし・剥奪・異tenant、取得失敗、未接続をfail-closedで検証。
3. 連打・同一キー再送・競合・部分成功・外部タイムアウトの結果不明を合成環境で検証。
4. UTM付与と原本への取込、欠測、重複、帰属不明、予約取消、売上未連携を検証。
5. 同じ期間の根拠原本と集計値を本人権限で照合。合成試験を実績表示へ流用しない。
6. 実公開/実送信テストは対象・内容・宛先・費用を明示して別承認。SQL/外部接続/本番変更も別承認。

## 10. 代表が次に決めること（3点）

1. **最初の対象と担当**：どの事業・サイトから始め、誰が原稿作成/承認/公開を担当するか（ECは延期）。
2. **成果目標**：その事業で何をKGIにするか、目標値と期間、問い合わせ/予約の有効条件。
3. **外部発信の承認範囲**：どのSNS/アカウントを使うか、接続権限の管理者、API費用上限。未承認の間はサイト下書き/プレビューと手動文案まで。

### 原本権限をそのまま守る

- `space_releases`：authenticated、staffまたは本人memberかつ有効会員が読取/作成/編集。会員本人の状態遷移と承認後編集はtriggerが制限。削除はstaffまたは本人の許可された草案状態。管理RPCは内部でspace_is_staffを検査。
- `space_articles`：公開記事のみ一般読取、全件読取/作成/更新/削除はspace_is_staff。Marketing grantや担当者選択でこれを緩めない。
- `space_article_social`：社内の非公開表。読取/作成/更新はspace_is_staff。公開記事に未公開文案を埋め込まない。
- `api/social.js`：BearerをSupabaseで検証し、active admin会員または既存の事務共有アカウント条件で許可後、サーバ側で記事/文案を扱う。既存コードがservice_roleで書くため、Marketingから汎用の管理鍵アクセスとして流用しない。本人tokenで既存認可を通す接続仕様を先にレビューする。共有アカウントになりすます導線は作らない。

### 独立Marketing内に集約する最小案

1. Marketingの原稿一覧に `source_type=space_release|space_article` と既存source_idを参照する項目を表示する。本文正本を複製しない。canonical content IDは参照を束ねる識別子であり、既存Space原稿の置換先にしない。
2. 原稿詳細内で既存Spaceの入力/草案組立/記事検査/プレビューを再利用するアダプターを設計する。UIはMarketing、保存先は同じSpace原本。既存IDと版/更新時刻を保持して競合確認する。
3. 記事のSNS派生は `space_article_social.article_id` を使う。独自の重複SNS文案表を作らない。press→記事化は元release IDと派生article IDの明示的な対応関係を記録し、同じ本文を利用者に再入力させない。現在この対応付けは未実装で、既存APIを呼ぶだけで自動成立しない。
4. ユーザーの理想はMarketing画面内で全操作。安全な本人読取/保存/公開アダプターができるまで、確認用UIは実行操作を無効化し、不足を表示する。権限不足を隠すiframe/共有ログイン/管理鍵迂回は使わない。
5. PR TIMESへの貼付・画像アップロード、Instagram/Xへの投稿は現コード上で人の外部操作。Marketingからコピー/外部画面へ移る必要を明示し、「直接配信済み」と表示しない。将来のAPI連携はアカウント/契約/費用/権限承認後。

### 再利用できても残る不足

- Space releaseとarticleの対応付け、campaign/canonical参照、横断的な承認版・公開試行履歴・冪等性・部分成功/不確実結果処理は統合設計が必要。
- 既存記事UIは直接REST PATCH/POST。安全な公開APIが存在するという意味ではあるが、Marketing本人sessionでの到達・CORS/接続先・競合制御・最新権限検査は未検証。呼び出しを有効化する前に検証する。
- `api/social`はOpenAIを呼び、DBへ生成文を保存する**課金を伴う書込操作**。現在の鍵/費用設定は確認していない。読取調査や画面プレビューで自動呼出ししない。新SNS投稿API費用とAI生成費用は別。
- SNS posted_atは担当者の手動チェックであり、外部投稿ID/到達/反応の自動検証ではない。
- PV、SNS反応、クリック、問い合わせ/予約への帰属、売上、目標設定はこの既存原稿機能で計測できるとは確認していない。既存グラフの未計測表示を維持。
- newsletterは未確認。ECは引き続き延期。HR機能はこの発信UIへ混ぜない。

### 次のローカル確認UIの推奨範囲（実装は別段）

原稿種別/事業/原本IDの選択、Space既存草案・記事・SNS文案の流用関係表示、媒体別プレビュー領域、未接続/権限未確認/課金未承認による無効ボタン、公開結果状態の説明まで。
実データ取得が未接続なら合成原稿を実データと見せず未接続空状態。実読取アダプターが検証できた原本だけ表示。公開/AI生成/状態変更は今段階では実行しない。

## 12. サイト更新履歴・PR展開・記事別PVのUI/UX実装計画（2026-10-25）

### 確認用UI（このPRの範囲）
- マーケティング初期画面は「サイト別公開・更新状況」→「成果（計測範囲）」→「制作一覧（折り畳み）」の順に変更。

### 本実装に必要なデータと動線
1. 各サイトで原稿ID、公開先URL、公開先アカウント、編集日時、承認版、サイト反映確認日時、実行者と結果状態を紐付ける。公開予定／DBのpublished／サイト反映確認を別々に記録。

4. GA4など既存分析のread-onlyアクセスをサイト単位で確認。各記事の正規URL、計測プロパティ、日付・PV、最終同期時刻を取り込む。内部アクセスやbot、欠測、サイト毎の集計条件を区別。
5. 各記事の公開前7日と公開後7日の同URL PV、公開後1/7/30日、記事ランキング、サイト全体の推移を表示。新規記事で比較基準が無い場合は『比較なし』、基準が0の場合は伸長率を出さず絶対増分を表示。
6. UTMとキャンペーンIDで確認できるクリック・フォーム原本・予約を紐付ける。公開前後のサイト全体PV増をPR単独の効果と断定しない。帰属不能も明示する。
7. PDCAでは担当・改善仮説・記事の変更点・期限・7日後/30日後の結果を一覧化し、クリックで対象記事へ戻れるようにする。

## 13. SNS・ブラストメールを横断する成果ダッシュボード（2026-10-25）

参考: https://start-link.jp/hubspot-ai/btob-marketing/marketing-org-kpi/marketing-dashboard-design
参考記事の要点「主要指標は7以内」「次の行動につながる」「対象者別に粒度を変える」「リアルタイムと定点観測を分離」を採用。

### 画面構成
- 最上段は6指標：発信数、WebサイトPV、SNSからのサイト流入、メールクリック、有効問い合わせ、商談・成約。期間は過去7/30/90日。
- 下段は媒体別比較表（Web、X、Instagram、Facebook、LINE、YouTube、ブラストメール）と、今週改善すること。
- 既存のサイト公開状況を続けて見せ、計測ソースの設定状況・制作一覧・原本別グラフは折り畳む。
- 新設計のKPIは実データ未接続。未計測は0件ではない。グラフ・前期比・率・媒体比較は定義/期間の整ったデータだけ表示。

### 主なソースと取得計画
| 媒体 | 管理画面/媒体指標 | Web・売上の指標 | 初期接続案 |
| --- | --- | --- | --- |
| 自社サイト群 | 記事ID・公開確認URL・担当/日時 | GA4のPV、セッション、フォーム | サイト別のGA4 Data API（読み取り専用） |
| X | 投稿数、表示数、反応 | utm_source=x からのサイト流入 | 利用アカウントの分析レポート提供範囲・費用を確認 |
| Instagram | 投稿、リーチ、保存、反応 | utm_source=instagram の流入 | Professionalアカウント＋Meta権限の確認 |
| Facebook | ページ・投稿の反応 | utm_source=facebook の流入 | Meta Pageの閲覧権限確認 |
| LINE公式 | 配信・反応（提供範囲に従う） | utm_source=line の流入 | 管理画面のレポートと利用可能なAPIを確認 |
| YouTube | 再生数、視聴時間など | utm_source=youtube の流入 | YouTube Analytics APIのread-onlyアクセス |
| ブラストメール | 成功/失敗配信、HTML開封、クリック | utm_source=blastmail、medium=email のサイト流入 | 配信履歴・開封API。クリックのAPI提供範囲は未確定、必要なら個人情報を除いた集計CSV |
| その他SNS | Threads/TikTok/note/LinkedIn等の媒体別反応 | 各utm_sourceの流入 | 利用アカウント確定後にアダプタ追加 |

ブラストメールのHTML開封率はApple MPPなどの影響で実際の読了率と異なる。重要KPIは到達・リンククリック・サイト流入・有効問い合わせ。
プラットフォーム側の『表示・反応』と、GA4で計測する『サイトへの訪問』、Salesで確認する『商談・成約』は別の数値。

### 計測URLと帰属
- 公開原稿にはcontent_id/campaign_id、媒体別にはvariant_id/publication_id、公開先URL・公開確認日を紐付ける。
- 配信先URLに utm_source（媒体）、utm_medium（social/video/email）、utm_campaign（キャンペーンID）、utm_content（投稿・版ID）を付与。
- URLへメールアドレス、電話番号、氏名、社内秘密、認証トークンを入れない。既存クエリ・ハッシュを保持する。
- UTMはユーザー入力可能な識別子であり、本人確認や権限判定に使わない。問い合わせは既存の原本IDに関連付け、重複を除外する。

### 指標定義・実際に可視化する条件
- 発信数：実際の公開URLで照合済みの投稿と、送信履歴で確認済みのメール配信。下書き・予約状態を公開実績に混ぜない。
- WebサイトPV：同一定義・タイムゾーンのページビュー。複数サイトのユーザー数を単純合算しない。
- SNSサイト流入：GA4が識別したSNS起点セッション。媒体の投稿表示数やリンククリックとは別。
- メールクリック：クリック計測の提供する回数・ユニーク数を定義とともに表示。GA4のメール流入とは別。
- 問い合わせ：原本で有効と判定され重複除外したもの。施策帰属が確認できた分と不明分を分離。
- 商談/成約：Sales原本の連携が確認できたものだけ。閲覧できない個人情報をMarketingへ複製しない。
- 正常取得ゼロは0。未接続・権限なし・一部取得・取得失敗は0にしない。異なる取得範囲を足し算しない。

### 実装順
1. GA4の計測プロパティと各サイトの公開IDを棚卸し（本人閲覧権限・実反映URLを確認）。
2. 媒体別UTMを統一。現UIではブラウザ内でURLを作成できる。URL生成だけでは計測開始にならない。
3. ブラストメールは先に成功・失敗/HTML開封の配信履歴APIをread-only確認。クリックは管理画面レポートの集計出力も確認。宛先別の個人メール情報は蓄積しない。
4. SNSは各サービスの公式指標、アカウント権限、利用コスト・API制約を検証し、取得できるものから接続。
5. タグ/公開記事IDと問い合わせ・Sales原本の対応、経過7日/30日での改善実績と担当タスクを追加。

計測集計はテナント・元原本権限を保持し、source/account/content/campaign/date/metric と値/定義/取得時刻/対象範囲を記録。二重集計を防止。実配信・本番SQL適用・API費用を伴う処理は別承認。
このPRは確認用画面とUTMリンク生成のみで、外部の実データは未接続。
