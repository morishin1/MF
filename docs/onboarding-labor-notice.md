# 入社処理：労働条件通知書のアップロードと本人確認

> **状態: 実装済み・本番未適用。** 本番DBへの SQL の適用・`main` へのマージは、承認のあとに行う。
> 電子署名の拡張・給与マスタとの連動・Board 連携は、この変更に含めない。

人事（owner ロール・hr ロールの人）が労働条件通知書のPDFをアップロードして本人に公開し、
入社予定者が `/onboarding/` で内容を見て「確認しました」を押す。
会社側は、確認済みかどうか・確認した日時を見られる。**電子署名ではない。**

## 1. 全体の流れ

```
人事（入社管理 admin-hr.html）            入社予定者（/onboarding/）
 ① PDFをアップロード（第1版・下書き）
 ② プレビューで中身を確かめる
 ③ 「本人に公開する」 ────────────────▶ ④ STEP2「労働条件通知書を確認してください」
                                          ⑤ 「書類を見る」（別タブ・署名付きURL）
                                          ⑥ 「確認しました」
 ⑦ 「確認済み 2026/10/01 14:05」 ◀──────── （確認した日時・本人が記録される）
 ⑧ 差し替え = 新しい版（第2版）を足す
 ⑨ 公開すると、第2版は「本人未確認」から始まる（第1版の確認は履歴に残る）
```

## 2. どこに何を置いたか

| 場所 | 内容 |
|---|---|
| **入社管理**（`admin-hr.html` → 入社予定の1人を開く → 「労働条件通知書」） | アップロード・プレビュー・公開・差し替え・版の履歴・確認状況。**owner ロール・hr ロールの人だけ**（それ以外の人には、欄そのものを出さない） |
| **`/onboarding/`**（本人） | STEP2 に、通知書の3つの状態（準備中／確認してください／確認済み）。最上部の「次にやること」にも反映 |
| **`/keiei`**（経営ハブ・owner） | 件数と状況だけ（「労働条件通知書 未公開」「本人未確認」）。押すと入社管理へ。**アップロードの操作は置かない** |
| `onboarding/notice.html` | 別タブで開くPDFビューア。本人は `?v=<版>`、会社側は `?file=<版のid>` |

`/keiei` はowner専用なので、人事がそこに入れない。操作を `/keiei` だけに置くと人事が使えないため、操作は入社管理に置いた。

### 本人の画面（STEP2）の3状態

| 状態 | 表示 | ボタン |
|---|---|---|
| 公開された通知書が無い | 「会社が準備中です」 | なし |
| 公開済み・未確認 | 「労働条件通知書を確認してください」 | 書類を見る / 確認しました |
| 確認済み | 「確認済み　YYYY/MM/DD」 | もう一度見る |

「次にやること」は、確認待ちのあいだは「労働条件通知書の確認」になる。

## 3. 「確認した」と「電子署名した」は、別の事実

| | 通知書の確認 | 電子署名 |
|---|---|---|
| 保存先 | `gw_labor_notices.confirmed_at` | `gw_sign_requests.status = 'signed'` |
| 操作する人 | 本人（確認しました） | 本人（署名） |

- **電子署名の依頼（`gw_sign_requests`・キャンセル以外）がある人は、電子署名を優先する。**
  STEP2 は従来どおり「締結」で、通知書の確認の入口（カード・ボタン・API）は出さない。
  API（`view_notice` / `confirm_notice`）も `409 esign_in_progress` で断る。
- **`gw_sign_requests` は、通知書のどの操作でも書き換えない**（読むだけ）。確認ボタンで「署名済み」にはならない。
- 電子署名の依頼を後から出した場合も、その人は電子署名側に戻る（通知書の確認は事実として残るが、段階判定には使わない）。
- 電子署名の流れの途中（`gw_doc_orders` が進行中）の人に通知書をアップロード・公開しようとしたときは、管理画面に警告を出す（止めはしない。段階判定を変えるのは `gw_sign_requests` だけ）。
- `/keiei` の件数は、電子署名の流れにいる人を数えない。

### 誓約書などの同意

STEP2 の完了には、これまでどおり、誓約書などの同意（`consentsOk`）も要る。
通知書を確認しても同意が残っていれば、STEP2 は「あなたの番です」のまま、
「誓約書などを確認してください」と出る（ボタンは `/onboarding.html#consents-card` へ）。

## 4. データ（`db/110_labor_notices.sql`）

新しい表 `gw_labor_notices` を1つだけ作る。**1行＝1版。**

| 列 | 内容 |
|---|---|
| `tenant_id` / `employee_id` / `version` | 会社・社員・版（`unique(employee_id, version)`、1以上） |
| `storage_path` / `filename` / `size_bytes` / `sha256` | 非公開バケット `hr` の `<tenant>/labor-notice/<employee>/<uuid>.pdf`。SHA-256 は中身から計算 |
| `uploaded_by` / `uploaded_at` | アップロードした人・日時 |
| `published_by` / `published_at` | 本人に公開した人・日時（null＝下書き） |
| `confirmed_by` / `confirmed_at` | 確認した人（本人）・日時（null＝未確認） |

- **差し替えは新しい版の INSERT。古い行も、古いファイルも消さない。UPDATE での上書きもしない。**
- 確認（`confirmed_at`）が付くのは、公開済みの**いちばん新しい版**だけ。新しい版を公開すると、その版は未確認から始まる。
- 「確認しました」を2回押しても、記録は1回（確認の日時は最初のまま）。
- 守りはトリガ `gw_labor_notices_guard` でも掛けてある（`service_role` の API からでも同じ）。
  - 版の中身（場所・名前・サイズ・ハッシュ・版番号・アップロード日時）は、あとから書き換えられない。
  - 公開・確認の日時は、一度入ったら、書き換えも消去もできない。
  - 公開していない版は、確認できない。
  - 例外: 人が退職してアカウントが消えたとき、外部キー（`on delete set null`）で `*_by` が null になるのは許す。
- RLS（`gw_labor_notices_read`）: 直接読めるのは **owner ロール・hr ロールの人だけ**（`gw_has_role(tenant_id, 'owner') or gw_has_role(tenant_id, 'hr')`）。
  `gw_is_hr` は、会計側の管理者（admin / staff）も含む定義（db/041）なので使わない。書き込みの方針は無い（書くのは API だけ）。
  本人は API 経由で、自分の公開済みの最新版だけを見る。

## 5. API

| API | 誰が | 内容 |
|---|---|---|
| `GET /api/onboarding/notice?employeeId=` | owner・hr ロール（`canManageNotice`） | 状態・版の履歴・警告。ファイルの場所・URLは返さない |
| `GET /api/onboarding/notice?file=<id>` | 同上 | プレビュー用の署名付きURL（300秒）。閲覧の記録を残す |
| `POST /api/onboarding/notice` `upload` / `attach` / `publish` | 同上 | アップロード用URLの発行 → 実体の検査・登録 → 公開 |
| `POST /api/onboarding/start` `view_notice` | 本人 | 自分の公開済み最新版の署名付きURL（300秒） |
| `POST /api/onboarding/start` `confirm_notice` | 本人 | 「確認しました」。表示中の版が最新でなければ `409 version_changed` |

- 既存のしくみを再利用: 非公開 Storage `hr`・PDF の中身の検査（先頭 `%PDF-`）・SHA-256・短い署名付きURL・別タブのプレビュー・社員／会社の突き合わせ。
- 署名付きURL・トークンは、DB・監査ログ・通知・console のどこにも残さない（テストで確かめている）。
- 操作の記録（`gw_activity_log`）: `labor_notice.upload` / `publish` / `confirm` / `view`（ファイル名・版・サイズのみ。URLは入れない）。
  人事・owner が本人の通知書を開いたときは、機微情報の閲覧記録（`gw_sensitive_access_log`）も残る（本人が自分のものを開いたときは残さない）。
- 二段階認証（MFA）は要らない（任意）。

### 権限（給与・個人情報を含む書類なので、絞る）

管理できるのは **owner ロール・hr ロールを持つ人だけ**。API（`lib/labor-notice.js` の `canManageNotice`＝`ctx.roles` に `owner` か `hr`）と、
DB の RLS（`gw_has_role`）の、両方で同じ条件。`canManageHr`（会計側の管理者を含む）は使わない。

| 誰 | 結果 |
|---|---|
| owner ロール・hr ロールの人 | アップロード・プレビュー・公開・差し替え・確認状況の閲覧ができる |
| 会計側の管理者（admin / staff）で、owner・hr のロールを持たない人 | `403`。入社管理にも、通知書の欄そのものを出さない |
| 経理（finance）・責任者（manager）・採用担当（recruiter）・営業（sales）・社労士（labor_advisor）・IT・一般の社員 | `403`（取得・プレビュー・アップロード・登録・公開、どれも） |
| 他の社員 | `403`（他人の通知書は取れない） |
| 他の会社の owner・hr | `404`（この会社の人・版・置き場所は、無いものとして扱う） |
| 本人 | 自分の「公開済みの最新版」を見る・確認する（本人の入口 `start.js`）。下書きと古い版は見られない |

- 管理者が owner・hr のロールも持っていれば（兼務）、ロールのほうを見て使える。
- **入社手続きの進み具合**（STEP2 が「確認待ち」か「完了」か、という状態の表示）は、通知書の中身ではないので、これまでどおり、その人の手続きを見られる人
  （管理者・社労士を含む）に出る。ファイル名・版・日時・ファイルそのものは、owner・hr と本人にだけ出る。
  進み具合を読む `api/onboarding/status.js` は、通知書の表を service_role で読み（RLS は owner・hr だけのため）、「公開済みか・確認済みか」の事実だけを使う。

## 6. 差し替えたときの動き（仕様どおり）

- 第2版を**アップロードしただけ**では、本人には何も起きない（第1版の確認のまま）。
- 第2版を**公開**した瞬間、本人は「確認してください」に戻る。入社準備の段階も、締結待ち（`signing`）に戻る。
  通知書が変わったので、もう一度見てもらうための動き。公開の前に、管理画面が「本人は確認し直します」と確認を出す。
- 第1版を開いたままの画面で「確認しました」を押すと、`409 version_changed`。「更新されました」と出て、読み込み直す。

## 7. 本番への反映

**`db/110` は本番適用済み。アプリのコードは未デプロイ（#58 までを main にマージした。デプロイは別）。**

> **先に、入社管理に要る DB を確かめる。** `db/110` が入っていても、`gw_procedures`（入社手続き）ほかが無いと、
> 入社管理の画面（`GET /api/hr` が 503）も、本人の `/onboarding/` の通知書も、**使えない**。
> `db/check_onboarding_ready.sql`（読み取り専用）を Run して、「必須の不足」を見る。不足したときの最小の流し方は **`docs/onboarding-db-prereq.md`**。
> （前の版の `check_labor_notice.sql` は、`gw_procedures` を「任意」としていた。誤りだったので、NG に直した。）

以下は、110 を最初に流すときの順番（記録として残す）。

1. **読み取り専用の確認**: `db/check_labor_notice.sql` を Supabase の SQL Editor に貼って Run。
   何も書き換えない。前提（`tenants`・`gw_employees`・`gw_has_role` と `gw_role_grants`・`gw_activity_log`・Storage の非公開バケット `hr`・`gw_sign_requests`・`gw_doc_orders` ほか）を、
   **番号ではなく、実際の表・列・関数があるかで**判定する（結果: OK / NG / 任意（無い）/ 未適用）。
   NG があれば、そこで止まる。
2. **`db/110_labor_notices.sql` を流す**（べき等）。**適用してよいのは、1 が通ってから。**
   前の版（`gw_is_hr` で読める）を、すでに流してしまっていたら、もう一度流す。ポリシーが owner・hr だけのものに置き換わる。
   確認 SQL は、古いポリシー（管理者も読める）を **NG** と言う（行 94）。
3. SQL 冒頭の「B. 確認」で、表・RLS・トリガができていることを確かめる。
4. アプリを再デプロイ。（表が無いあいだは、画面は「データ未連携」と出して止まらない。API は `503 NOT_READY`。）

### マイグレーションの番号について

同じ番号が系統ごとに別の内容で使われている（例: `097_sales_company_list.sql` と `097_sign_contract_link.sql`）。
**番号ではなくファイル名と、実際のオブジェクトで確かめる。**

| ファイル | 内容 | 通知書との関係 |
|---|---|---|
| `056_doc_orders.sql` | 書類の作成依頼（`gw_doc_orders`。社労士に頼む → 署名依頼） | 電子署名の流れにいる人かを見分ける。読むだけ |
| `071_onboarding_stage2.sql` | 社労士の確認・承認（`gw_doc_orders` に承認の記録）ほか | 同上（段階判定の元データ） |
| `087_hr_offer_contract_check.sql` | 契約書作成依頼と、採用承諾条件の突き合わせ | 直接は使わない（作成依頼の経路） |
| `097_sign_contract_link.sql` | `gw_sign_requests.contract_id`（署名依頼と契約の明示的な結び付き） | 電子署名の有無の判定は `gw_sign_requests` の行の有無・状態だけ。この列は使わない |

056・071・087・097 が本番に当たっているかは、**この調査では確認できていない**（本番に接続できないため）。
`db/check_labor_notice.sql` が、電子署名・作成依頼まわりの表・列の有無を「任意」として出す。
これらが無くても、通知書の機能は動く（無い表は読み取りが空になり、電子署名の流れは「無い」扱い）。

`110` は、`main`（最大 109）と、給与管理の系統（最大 105）のどちらにも当たらない番号として選んだ。

### 元に戻す

`db/110_labor_notices.sql` 冒頭の「A. 元に戻す」（表とトリガ関数を落とす）。**版・確認の記録は消える**ので、実行の前に書き出しておく。
Storage の `hr/<tenant>/labor-notice/…` のファイルは、別に残る（必要なら手で消す）。
