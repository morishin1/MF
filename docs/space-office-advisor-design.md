## 1. Space ボタン（ヘッダーの HR／Sales の並びに「Space」）

### いまの仕組み（調査結果）

- GW 共通のヘッダー（ホーム・Office・経営の画面）は `js/layout.js` の `TOOLS`（HR／Sales／Office／経営）から入口ボタンを出す。出すかどうかは `/api/me` の `access`（サーバの判定）で決まる（`showsFor`）。
- `/hr` と `/sales` は**自前のヘッダー**（`js/hr-layout.js`・`js/sales-layout.js`）で、「GWへ戻る」だけ。`TOOLS` に足しても、HR・Sales の画面の中には出ない。
- MF には 8sp への接続が無い（URL・環境変数・DB 参照なし）。`api/spaces`・`api/bookings` は **MF 社内の会議室予約**で、8sp とは別物。
- 別システムへのリンクは、すでに「環境変数で URL を持ち、未設定なら出さない」型がある（`LMS_URL`・`TIMECARD_URL` を `api/public-config.js` が返す）。
- 入口の権限（`gw_app_grants.app_key`）は `hr/sales/office` だけに CHECK で絞られている（db/119）。`space` を足すには SQL の変更が要る。

### 案（推奨：段階1だけ先に）

| 段階 | 内容 | 必要な承認 |
|---|---|---|
| 1 | `SPACE_ADMIN_URL`（例：8sp の管理画面 URL）を `api/public-config.js` で返し、`TOOLS` に「Space」を足す。未設定なら出さない。出す相手は **Office に入れる人（`access.officeApp`）** に限る（新しい権限は作らない）。8sp の中の権限は **8sp 側のログインと権限がそのまま正**（MF のボタンは入口だけ） | 環境変数の設定、表示対象を Office 利用者にしてよいか |
| 2 | 付与できるアプリとして `space` を足す（db/119 の CHECK・`APP_KEYS`・社員管理の画面・`accessOf`・権限の一致テスト） | SQL 変更（CHECK の差し替え）と、誰に付与するか |

- 問い合わせ・予約・請求の**正本は 8sp**。MF に台帳を作らない・コピーしない。
- 既存テスト `test/ui/headershortcutui.mjs` は入口が4つであることを確かめているので、段階1で更新が要る。

## 2. Office への集約（8sp の未対応・期限）

### いまの状態

- Office の確認用 PR（https://github.com/morishin1/MF/pull/186 ）は**未マージ**。2026-10-24 時点の main に競合なしで載る（`git merge-tree` で確認）。「今日やること」に申請・本人タスク・期限をまとめる。8sp の集約は入っていない。
- **注意（既存の不具合）**：`GET /api/office-tasks/calendar` は、読むだけのつもりで呼んでも、繰り返し予定を作る（`api/office-tasks/calendar.js` 78〜81行、`lib/office-recurring-db.js` の `generate`）。Office のホームを開くたびに走る。実データ環境で「読むだけの確認」に使わないこと。GET から作成を外す修正を別 PR で提案したい。

### 案

- 8sp に**件数だけ**を返すサーバー間の読み取り口を作る（例：未返信／仮押さえ期限／見積承諾待ち／署名待ち／支払い待ち／利用後精算待ち の件数と、いちばん近い期限。氏名・本文・金額は返さない）。署名付き（共有の秘密鍵＋時刻）で MF のサーバーからだけ呼ぶ。
- Office の「今日やること」には**件数・期限・担当・8sp の該当画面へのリンク**だけを出す。詳細は 8sp の画面で、8sp の権限で見る（二重台帳を作らない）。
- 取得に失敗したら「取得できません」と出す（0件と出さない）。PR186 の「未確認」表示の型に合わせる。
- 8sp 側の件数の作り方は、8sp の予約フロー作業（`docs/booking-flow.md`、8sp リポジトリ）の「管理画面の優先表示」と同じ判定を使う。

**必要な承認**：8sp に新しい API を公開すること、秘密鍵の発行と置き場所（Vercel 環境変数）、Office で誰に見せるか。

## 3. 社労士・税理士と Office の連携ポータル

### いまの状態（調査結果）

- 社労士は `gw_role_grants.role = 'labor_advisor'`（画面上は `sr`）。`advisor.html` は、労働条件通知書の依頼の確認・修正・**承認・発行**、共有された手続き書類、マイナンバー提出状況、給与 CSV。
- 「確認しました」・質問と回答の仕組みは**無い**。社労士が書けるのは依頼ごとの `advisor_note` だけ。
- **税理士の役割は無い**（`memberships.role` は admin/staff/client のみ。税理士の言葉は旧 KessanPilot のデモ画面だけ）。
- `share_with_advisor`（db/008、手続き項目ごと）は **RLS で効いている**（手続き項目・ファイル）。ただし次の2点は共有の印で絞られていない。仕様なのか確認したい（**本番データに対する否定テストが必要**）：
  - 労働条件通知書の依頼一覧（`GET /api/sign/orders`）は、テナント内の雇用契約の依頼を**すべて**社労士に返す
  - マイナンバー提出状況の更新（`/api/hr` の PATCH）は、テナントだけを確かめて共有かどうかを見ていない
- 社労士の［承認・発行］は副作用が大きい：PDF の保存、署名依頼の作成、本人へ「署名をお願いします」の通知、人事・経営者への通知、Slack、入社手続きの段階を進める。**「確認しました」とは別の操作にする**（押し間違えで発行されない画面にする）。

### 案

- **役割を分ける**：税理士は新しい役割（例 `tax_advisor`）。経営者権限を渡して代用しない。社労士と税理士で見えるものを分ける。
- **共有は1人ずつ、明示的に**：共有の表（例 `gw_expert_shares`：テナント・専門家・対象の種類と ID・**版（ハッシュ）**・共有した人・日時・取り消し日時）。専門家は自分に共有された行だけ読める（RLS）。他社・他の専門家・不要な給与情報は返さない。
- **確認履歴は版ごと**：`gw_expert_acks`（共有・版・確認した人・日時）。文書が更新されたら旧版の「確認済み」を新版に引き継がない。
- **質問・回答**：スレッド（質問・回答・担当・状態：返答待ち（専門家）／返答待ち（Office）／解決／再開（理由必須））。解決・再開は履歴に残す。
- **画面**：専門家は「自分宛ての確認待ち・質問」だけの1画面。Office 側は「専門家の返答待ち」を「今日やること」に件数で出す。
- **テスト**：画面ではなく API と RLS の否定テスト（別の専門家・別テナント・取り消し後・旧版で読めない／確認できないこと）。

**未決定（決めてもらうこと）**：共有・取り消しをしてよい人、Office 側で誰がどこまで見るか、質問を「解決」にできる人、税理士に見せる範囲（試算表・仕訳・証憑など）。権限の拡張・DB 適用・実文書の共有は、それぞれ別の承認にする。

ローカル試作（別端末）は受け取っていないので、この案は既存コードの調査だけから作った。
