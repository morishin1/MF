# 給与管理（`/keiei`）— 調査・設計・移行方針

`/keiei` を、給与情報の**正式な管理場所**にする。給与は「いまの値を上書き」せず、適用開始日つきの行を**追記**していく。
履歴は消えない。修正も監査できる。

> **本番DBへの SQL の適用・`main` へのマージ・本番のメール送信は、まだ行っていない。**
> この工程では、**給与の段階2（人事・管理者から既存の給与閲覧権限を外す）は行わない**。既存データの**移行もしない**。
> 反映の手順は `docs/keiei-production-rollout.md`（`105` は、給与の作業から独立した、最後のステップ）。

## 1. できること

| 要件 | 場所 |
|---|---|
| 社員一覧・現在の給与情報（基本給・手当・通勤手当・月額の見立て・適用開始日） | `/keiei#pay` |
| 契約上の賃金（参照）・内定時の給与（参照）・本人が届け出た定期代（参照）と、食い違いの表示 | `/keiei#pay/<社員>` の「参照」 |
| 適用開始日つきの記録（いつからこの給与か） | 記録フォーム（`適用開始日` は必ず自分で入れる） |
| 過去の給与履歴（適用開始日ごと・新しい順。訂正の版も残る） | 「給与の履歴」 |
| 変更前 / 変更後・変更者・変更日時・変更理由（必須） | 履歴の各行・記録の前の「確認」 |
| 監査ログ（記録の追加・訂正・開いた人と日時） | 「この人の監査ログ」・`/keiei#pay-audit` |
| 人件費への接続（記録がある人は記録、無い人は契約で数える） | `/keiei#payroll` |

権限は**経営者（owner）専用**（二段階認証つき）。人事・管理者・責任者・採用担当・経理などは、`/keiei` も `/api/keiei/pay` も 403。

## 2. 給与データの所在（調査結果）

給与に関わる情報が、次の場所に**別々に**あった。「いつから、いくらか」を追える表は無かった。

| 場所 | 中身 | 書く人 | 読める人（現状） | 性質 |
|---|---|---|---|---|
| 雇用契約 `gw_contracts`（`db/029`） | `wage_type`（月給・時給・日給・年俸・その他）・`wage_amount`・`wage_note`（手当・控除などの**文章**）。状態 `draft / active / superseded`。契約書PDFを読み取って人が確定 | 人事（契約画面） | 給与を見られる人＋本人（`db/102` のあと） | **契約上の賃金**（署名した書面が言っていること）。手当は文章の中にしかない |
| 内定・応募者 `gw_hr_applicants` / `gw_hr_offers` の `wage_type`・`wage_amount`（`db/081`） | 入社前の条件 | 採用担当・人事 | 分離前は採用担当も読めた。`db/100`〜`101` のあと、列は空になる | 入社前の条件。社員の給与の正ではない |
| `gw_hr_pay`（`db/100`） | 上の給与の移し先（`HR_PAY_SPLIT=1` で有効） | サーバ（`lib/hr-pay.js`） | 給与を見られる人だけ | 内定の給与。同上 |
| 入社情報の届出 `gw_onboard_profiles.commute_cost`（`db/037`） | 本人が届け出た「1か月の定期代」 | 本人 | 人事など | **本人の申告**。会社が決めた通勤手当ではない |
| 労働条件通知書 `gw_doc_orders` ・署名 `gw_sign_requests`・`lib/esign.js` | 通知書の「賃金」欄（契約の賃金を文字にしたもの）・署名済みPDF | 契約から自動 | 人事・本人 | 過去の書面は**不変の証跡** |
| 給与CSV（`lib/payroll-csv.js`・`api/hr/payroll.js`） | MF給与の取込用。`基本給` は**契約**から、`通勤手当（月額）` は**届出**から | 出力するだけ | 人事・社労士（共有済みの人） | 出力（書き込み先ではない） |
| キャリア `gw_career_levels.salary_min/max`・`gw_career_reviews.salary_decision/salary_note`（`db/092`） | 昇給レンジ・昇給の判断の記録 | 責任者・人事 | — | 目安と判断。給与額の正ではない |
| PP・BP の `unit_price`（`gw_site_contracts`） | 現場単価 | — | — | **給与ではない。変更禁止**（`docs/keiei-unit-price.md`） |

見つけた問題:

1. 「いま」の基本給が、契約・内定・CSV の3か所に散り、変えても**いつから**かが残らない。
2. 手当は文章（`wage_note`）にしかなく、金額として扱えない。通勤手当は本人の申告だけ。
3. 契約の賃金が「現在の給与」と食い違っても、気づく仕組みが無い。

## 3. Single Source of Truth（決定）

| 項目 | 正 / 参照 / 出力 | 場所 |
|---|---|---|
| **現在の給与額**（基本給・手当・通勤手当）と、その履歴 | **正** | `gw_compensations`（`db/105`）。書けるのは `/keiei` だけ |
| 契約上の賃金 | 参照 | `gw_contracts`・署名済みPDF。記録のたびに**その時点の写し**を記録に残し、食い違いを見せる。`/keiei` は契約へ書かない |
| 内定時の給与 | 参照 | `gw_hr_pay`（または元の列）。**自動では移さない**。入社時に経営者が確認して、入力欄に写す |
| 本人が届け出た定期代 | 参照 | `gw_onboard_profiles.commute_cost` |
| 労働条件通知書・署名済みPDF | 参照（不変の証跡） | 契約から作られる。給与管理には合わせない（過去の書面を書き換えない） |
| 給与CSV | 出力 | いまは契約・届出を読む。**切り替えは、突き合わせのあとの別の工程**（§8） |
| 昇給レンジ・昇給の判断 | 別 | キャリア。給与額の正ではない |
| `unit_price` | 対象外 | 混ぜない |

**同じ給与を、複数の場所で別々に編集できる状態にしない**ための約束:

- `/keiei` の給与管理は、`gw_contracts`・`gw_hr_*`・`gw_onboard_profiles` に**書かない**（テストが、書いた表が `gw_compensations` と `gw_pay_audit` だけであることを確かめる）。
- 給与の額を直す場所は、ここだけ。契約と違うときは、契約書を更新するか、記録を見直すかを**経営者が判断**する。画面は食い違いを見せるだけで、自動では直さない。
- 参照からの取り込みは、**入力欄に写すだけ**。内容を確かめ、理由を書き、記録して初めて給与になる。写した値をあとで書き換えたら、元は「経営者の入力」になる（元と違う値に、元の名前を付けない）。
- 給与管理の監査ログを、管理者も読める `gw_activity_log` に書かない。

## 4. DB 設計（`db/105_compensation.sql`）

既存の表・列・ポリシーは変えない。流しても、既存の画面・API の動きは変わらない。表が無いあいだ、アプリは「給与管理がまだ使えません」と案内して止まらない。

### `gw_compensations`（給与の履歴。追記だけ）

| 列 | 意味 |
|---|---|
| `effective_from` | **適用開始日**（いつからこの給与か） |
| `revision` | 同じ適用開始日の**訂正の版**（1, 2, …） |
| `kind` | `initial`（初回）/ `change`（変更）/ `correction`（訂正）。`revision=1` なら初回か変更、`revision>1` なら訂正（`check` で固定） |
| `wage_type` / `base_amount` | 月給・年俸・時給・日給 / 基本給（円の整数。月給は月額・年俸は年額・時給は1時間・日給は1日） |
| `allowances` | 手当 `[{name, amount}]`（月額・円）。形も DB で検査（名前は空でなく40字まで、金額は 0 以上、20行まで） |
| `commute_amount` / `commute_note` | 通勤手当（月額・円）・メモ |
| `contract_id` / `contract_wage_type` / `contract_wage_amount` | 記録した時点の**契約の賃金の写し**（食い違いを見つけるための記録。給与の正ではない） |
| `source` | `owner`（経営者の入力）/ `contract_import`（契約から）/ `offer_import`（内定から） |
| `reason` | **変更理由・メモ（必須、1〜500字）** |
| `before` | **変更前**（記録した時点で有効だった値の写し。初回は null） |
| `created_by` / `created_by_name` / `created_at` | 変更者・変更日時 |

`unique (employee_id, effective_from, revision)`。

### 履歴が必ず残る

- **変更も削除も、トリガが止める**（`UPDATE` / `DELETE` / `TRUNCATE`。SQL Editor の権限の高い接続でも）。例外は、テナントごと消えるとき（親の行が既に無い）だけ。
- **社員の削除は、外部キーが止める**（履歴を残す。名簿では「退職」にする。`api/employees` は、技術的なエラーではなく「退職にしてください」と案内する。何の記録かは言わない）。
- API に、**更新・削除の入口が無い**（`preview_record` と `record` だけ。テストがコードを検査する）。

### 「いま」と「いつから」

- 給与を変える＝**新しい適用開始日の行を足す**（`change`）。前の行は、そのまま残る。
- 入力の誤りを直す＝**同じ適用開始日の次の版を足す**（`correction`、`revision+1`）。前の版も残り、訂正の前後が監査できる。
- 「いまの給与」＝適用開始日が今日（日本時間）以前でいちばん新しい日付の、**最新の版**。
- 過去の日付から適用する（遡及）・これからの日付（予定）も記録できる。確認の画面に注意が出る。
- 変更前と同じ内容は記録できない（`no_change`）。同じ適用開始日に「変更」で二重に入れることもできない（`exists_at_date`。訂正として入れる）。

### `gw_pay_audit`（監査ログ。追記だけ）

- 記録の追加・訂正は、`gw_compensations` への **INSERT トリガが自動で書く**（API を通らない INSERT でも残る。記録と同じトランザクションなので、片方だけ残ることは無い）。
- 開いた（一覧・個人・監査ログ・**人件費**）は、API が書く。**書けなければ、給与は返さない**（`503 audit_unavailable`）。「見せたのに、残っていない」を作らない。
- 金額は写さない（記録そのものにある）。`employee_id` に外部キーは張らない（社員の行が変わっても、ログは残る）。

### RLS

| 誰が | `gw_compensations` | `gw_pay_audit` |
|---|---|---|
| 経営者（`gw_is_owner`） | 読める | 読める |
| 本人 | **自分の行だけ**読める | 読めない |
| 人事・管理者・責任者・採用担当・経理・その他 | **0 件** | 0 件 |
| 書き込み | ポリシーなし（サーバ＝service_role だけ） | 同左 |

## 5. API（`/api/keiei/pay`）

経営者のみ（`lib/keiei-gate.js` の `requireKeiei`。`test/accessparity.mjs` が、`api/keiei/*` すべてがこの入口を通ることを見張る）。

| 呼び方 | 内容 |
|---|---|
| `GET ?view=list` | 社員ごとの、いまの給与・予定・状態（未登録 / 適用前 / 変更予定 / 契約と不一致）・契約上の賃金（参照）・集計。BP は対象外。**1000 件を超えても切り捨てない**（読み切れなければ、一部だけを返さず 500） |
| `GET ?view=detail&employeeId=` | 現在・予定・履歴（適用開始日ごと、各版の変更前後）・参照（契約・内定・届出）・その人の監査ログ |
| `GET ?view=audit[&employeeId=][&before=]` | 監査ログ（新しい順・200 件ずつ） |
| `POST {action:"preview_record"}` | 記録したらどうなるか（種別・版・変更前後・注意・契約との食い違い）。**書かない** |
| `POST {action:"record"}` | 記録する。`correct:true` で訂正。`basisId`（画面が見ていた「いまの記録」）が違えば `409 stale_basis`（別の人が先に記録した）。一意制約の競合は `409 conflict` |

読み込み時、「契約から」「内定から」と名乗る記録は、元が実在しなければ断る（`409`）。理由が空・日付や金額の不正は `400`（何も書かれない）。

## 6. 画面（`/keiei#pay`）

- 一覧: 集計（在籍・未登録/適用前・契約と不一致・変更予定・月額の合計＝**暫定**。時給・日給は月額に直せないので合計に入れない）／表示（在籍中・入社準備中・退職者・全員）／状態・氏名で絞り込み。
- 1人: いまの給与 → 参照（書き換わらない） → **給与を記録する**（変更 / 訂正） → 履歴 → その人の監査ログ。
- 記録は「**内容を確認する**」を通る（変更前 → 変更後・月額の見立て・注意）。確認のあとに入力を変えると、確認は消える（見たものと違うものを記録しない）。
- 履歴の中に、消す・書き換えるボタンは無い。訂正前の版は薄い行で残る。

## 7. 人件費（`/keiei#payroll`）への接続

- 給与管理に**いま適用中の記録がある人**は、その記録（基本給＋手当＋通勤手当）で数える。記録がない人・適用がまだ始まっていない人は、これまでどおり**契約の基本給**。同じ人の金額を**足し合わせない**。
- どちらで数えたかを「元」に出す（給与管理 / 契約）。
- 給与管理の表が無ければ、これまでと同じ（契約だけ）。**表があるのに読めなければ、黙って契約だけに切り替えず**「データ未連携」（違う合計を出さない）。
- 全員の給与を返すので、給与管理の監査ログに残す（書けなければ返さない）。合計だけのダッシュボードは、対象にしない。

## 8. 移行方針（**既存データは、いま移行しない**）

自動の移行は**しない**。手当は文章の中、種別は「その他」や契約が2件など、推測で埋められない場合が現実にあるため。

1. **`db/105` を流す**（空の表ができるだけ。既存の動きは変わらない）。
2. **読み取り専用の差分確認**: `db/check_pay_reconcile.sql`（SQL Editor に貼って Run するだけ。何も書き換えない。氏名は出るが金額は出さない）。
   - 区分 A: 給与が入っている場所と件数（契約の賃金・契約が2件以上・種別が取り込めないもの・手当の文章・届出の定期代・内定の給与・給与管理の行数）。
   - 区分 B: 給与管理と既存の表の食い違い（契約に賃金があるのに記録がない／基本給が契約と違う／通勤手当が届出と違う／未来の記録だけ）。**B の2・3は、給与CSVが出す値（基本給＝契約、通勤手当＝届出）との食い違いでもある**。
   - 区分 C: どれを正とするかの一覧（§3）。
3. **経営者が1人ずつ記録する**: `/keiei#pay` の個人画面で「契約の賃金を入力欄に写す」→ 適用開始日・手当・通勤手当を入れる → 確認 → 記録。契約と食い違えば、契約書を更新するか、記録を見直すかを判断する。
4. **差分が 0 になったこと**を、`check_pay_reconcile.sql` で確かめる（B が ✅ 0 件。A の「取り込めない」「文章の手当」は、経営者が個別に確認済みであること）。
5. **給与CSV を、給与管理から読む形に切り替える**（別の変更・別の承認。**この工程には含めない**）。これをしないあいだ、CSV は契約・届出を読み続ける（＝3で契約を更新しない限り、CSV と給与管理は食い違いうる。B が見張る）。
6. そのあとに、**給与の段階2**（人事・管理者から給与閲覧権限を外す。`docs/keiei-salary-separation.md`）を、別工程として行う。

**移行しないもの（する場合も別の承認）:** 過去の労働条件通知書・署名済みPDF（不変の証跡）／内定時の給与（入社前の条件。自動では移さない）／昇給レンジ・キャリアの判断（別の目的）／`unit_price`（給与ではない）。

## 9. 権限

- `/keiei` の給与管理は**経営者専用**（画面・API・DB の3層）。
- **既存の人事・管理者の給与の権限は、この工程では変えない**（`gw_can_see_salary`・`SALARY_OWNER_ONLY` は触らない）。給与の段階2は、`/keiei` の完成と、既存の給与業務との突き合わせ（§8）が終わってから、別工程で行う。
- 経営者自身の給与も、この画面で記録する。本人は、自分の行だけ DB から読める（本人向けの画面は、いまは未提供）。

## 11. やっていないこと（非目標）

- 給与の段階2（人事・管理者から給与閲覧権限を外す）。
- 既存の契約・内定・給与CSV のデータ移行、給与CSV の読み先の切り替え。
- 社会保険料・賞与・残業割増・実際の支給額の計算（このアプリに無い。実績は会計側）。
- 本人が自分の給与を見る画面（DB は本人の行を読める。画面は未提供）。
- `unit_price` の変更・改名・移行。
- 本番DBへの SQL の適用・`main` へのマージ・本番のメール送信。
