# 端末管理 設計

**どの端末から社内システムに入っているか**を台帳にして、
会社のパソコン以外から社内の情報が見られていないかを確かめるための仕組み。
mf.8grp.co.jp（グループウェア）の一機能。

---

## 0. 方針が変わった経緯（読み飛ばさないこと）

最初の設計は **常駐エージェント（Windowsサービス）**を前提にしていた。
USB接続・インストールされたソフト・アプリ別の利用時間・PCの起動終了まで取る前提で、
Go の2プロセス構成・MSI・Authenticode 署名・自動更新まで設計してあった。

その後、**「Windows エージェントはいらない。グループウェアからメンバーが
インストールする形で、管理者が管理できればよい」**という判断になった。

これは規模の話ではなく、**取れるものが変わる**話になる。
ブラウザからは次のものが取れない。仕様を削ったのではなく、技術的に不可能。

| 取れなくなったもの | なぜ |
|---|---|
| USBメモリの接続 | ブラウザはOSのデバイス通知を受け取れない |
| インストールされているソフト | 同上 |
| アプリ別の利用時間 | 前面のウィンドウはブラウザの外 |
| PCの起動・終了・ロック | OSのセッション通知はブラウザに届かない |
| 社内システム以外で見たページ | 他サイトの閲覧は取れない（取れたらそれはスパイウェア） |

**残ったもの**は次のとおり。これで何ができるかは §1。

| 取れるもの | どうやって |
|---|---|
| どの端末から社内システムに入ったか | ブラウザの localStorage に置くID |
| 端末の種類（OS・ブラウザ・画面の大きさ） | User-Agent Client Hints |
| 社内システムを開いていた時間 | 5分ごとの合図をつなぎ合わせる |
| そのうち深夜・休日にあたる時間 | 同上 |

> **数字の意味が変わったことに注意。**
> 前の設計の「稼働時間」は**パソコンの稼働時間**だった。
> いまの「利用時間」は**社内システムを開いていた時間**。別のものを数えている。
> 画面の文言もすべてそう書き換えてある。ここを取り違えると、
> 「6時間しか働いていない」のような誤読が起きる。

## 1. これで何ができて、何ができないか

### できること

- **会社のパソコン以外から社内システムに入られたら気づける。**
  自宅のPC、私物のスマホ、退職者が持っている端末。
  その人が今まで使っていなかった端末から入ると、アラートが出る。
- **貸与端末の台帳が、実態と合ったまま保てる。**
  貸与品台帳（`gw_assets`）は人が更新するので、いつか実態とずれる。
  こちらは使われた時点で自動で載るのでずれない。
- **働きすぎに気づける。** 深夜・休日に社内システムを使っていた時間。
- **使われていない端末が分かる。** 退職者のアカウントが生きたまま、といった状態。

### できないこと

- **パソコンで何をしていたかは分からない。** ブラウザを閉じているあいだのことは何も。
- **情報の持ち出しそのものは止められない。** USBにコピーされても分からない。
  それは Intune / Defender / DLP の担当で、ここでは追わない。
- **端末を偽ることを防げない。** localStorage を消せば別の端末に見える。
  それでよい。防ぎたいのは「見慣れない端末から入られること」で、
  本人が自分の端末を隠すことではない。本気で塞ぐなら証明書（mTLS）が要り、
  それは Intune の仕事になる。

### 他の仕組みとの分担

| | 担当 |
|---|---|
| **Intune** | 端末の構成管理・ポリシー配布・リモートワイプ・BitLocker・OS更新 |
| **Defender for Endpoint** | マルウェア検知・EDR |
| **この機能** | **社内システムに入ってくる端末の台帳**と、見慣れない端末・深夜休日の検知 |

## 2. 先に決めておくこと（実装より前）

### 2-1. 就業規則への明記

会社が業務端末の利用状況を継続的に記録する場合、
**就業規則（または情報セキュリティ規程）への明記と、本人への周知**が要る。
根拠は個人情報保護法（利用目的の特定・通知）と、労働契約法上の合理性。

エージェント前提だったときより取る範囲は狭いが、**明記は依然として要る**。
「社内システムを開いていた時間」は労働時間そのものではないが、
そう読めてしまう数字なので、目的をはっきりさせておく必要がある。

| 項目 | 書く内容 |
|---|---|
| 目的 | 会社の端末以外からの社内システム利用の検知、貸与端末の適正管理 |
| 取得する項目 | 端末の種類（OS・ブラウザ・画面の大きさ）／社内システムに入った日時／社内システムを開いていた時間の日別合計／そのうち深夜・休日にあたる分 |
| **取得しないもの** | キー入力・パスワード・メール本文・チャット本文・画面録画・社内システム以外で見たページ・端末に入っているソフト・USB・ファイル・PCの電源が入っていた時間 |
| 保存期間 | できごと400日 / 日別の集計13か月（設定で短くできる） |
| 見られる人 | 人事・経営者と、**本人** |
| 私用端末 | 私用端末から社内システムに入った場合、その端末も台帳に載る（載ることが目的） |

### 2-2. 本人が確認するまで、利用時間は数えない

`gw_devices.notified_at` が null のあいだ、日別の集計には**1分も入らない**。
本人が `device-consent.html` で告知を読んで「このパソコンです」を押して、はじめて数えはじめる。

これは建前ではなく、**API がそうなっている**（`api/devices/me.js` の `beat`）。
規程が間に合っていない状態で運用しても、利用時間は溜まらない。

ただし**「その端末から社内システムに入った」ことは、確認前でも残る。**
これはログインの記録であって、働き方の記録ではない。
これを残さないと「見慣れない端末から入られた」を拾えない。

### 3-2. 管理者：設定タブ

- 見慣れない端末から入られたら知らせるか
- 深夜・休日の利用を知らせるか、それぞれ何分から
- 何日で「使われていない」とするか
- 保存期間（できごと・日別）

### 3-3. メンバー：`device-consent.html`

**ここが「グループウェアからインストールする」入口。**

1. いま使っている端末（自動で載っている）が上に出る
2. 記録していること／していないことを読む
3. 「このパソコンです」を押す → ここから利用時間を数えはじめる
4. 名前を変えられる（「Windows 11 の Chrome」→「事務所のノート」）
5. **アプリとして入れる（PWA）**
6. 自分のほかの端末を見て、使わなくなったものを外す

PWA の入口は `beforeinstallprompt` を捕まえてボタンにする。
ブラウザが出してくれないとき（Safari、設定によっては Chrome）は
**手順を文章で書く。**「入れられません」で終わらせない。

### 3-4. メンバー：`mypage.html`

自分の端末・自分の利用時間・**誰がいつ自分の記録を見たか**。
見せないと「何を見られているか分からない」状態になり、それは監視になる。

## 4. DB設計（`db/053_devices.sql`）

| 表 | 中身 |
|---|---|
| `gw_devices` | 端末台帳。`device_uid`（ブラウザのID）で一意。`notified_at` が収集の門 |
| `gw_device_events` | この端末に起きたこと（はじめて使った・確認した・入れた・名前を変えた・停止・使用終了・外した） |
| `gw_device_usage` | 日別の利用時間（`active_min` / `night_min` / `holiday_min` / `beats`） |
| `gw_device_alerts` | 対応の状態を持つ。`unique (device_id, dedupe_key)` で同じものを増やさない |
| `gw_device_policies` | 会社ごとに1行。閾値と保存期間 |
| `gw_device_views` | **管理者が誰の記録を見たか。** 本人も読める |

前の版（常駐エージェント前提）で作った
`gw_device_app_usage` / `gw_device_web_usage` / `gw_device_enrollments` は、
**空のときだけ**落とすようにしてある。1行でも入っていれば残して警告を出す。

RLS は全表 select のみ。書き込みは `api/devices/*`（service_role）だけ。
本人は自分の端末ぶん、人事・経営者は全件。

## 5. API設計

### 5-1. 本人向け（`api/devices/me.js`）

社員の JWT で呼ぶ。端末専用の資格情報は要らなくなった
（ブラウザから呼ぶので、ログインしている本人が誰かはサーバが知っている）。

| メソッド | 中身 |
|---|---|
| GET | 自分の端末・自分の利用時間・自分の記録を見た人 |
| POST `{action:"beat"}` | 5分ごとの合図。**端末の入口でもある**（初回はここで台帳に載る） |
| POST `{action:"confirm"}` | 告知を読んだ（`notified_at`）。ここから利用時間を数えはじめる |
| POST `{action:"installed"}` | アプリとして入れた |
| POST `{action:"rename"}` | 端末の名前を変える |
| POST `{action:"forget"}` | 使わなくなった端末を外す（`retired`。記録は消さない） |

**beat が送るもの**

```jsonc
{
  "action": "beat",
  "deviceUid": "aaaaBBBBccccDDDD11",
  "hints": {
    "platform": "Windows", "platformVersion": "15.0.0",
    "model": null, "browser": "Chrome",
    "screen": "1920x1080", "mobile": false
  }
}
```

**どの画面を開いていたかは送らない。** 送ると、それは行動の記録になる。

**利用時間の数え方**（`lib/devices.js` の `applyBeat`）

- 前の合図から **12分以内**なら、そのあいだはずっと開いていたとみなして足す
- それより空いていたら、閉じていた時間なので **1分だけ**足す
- 巻き戻った合図（端末の時計がずれている）は数えない
- 1日 1440分を超えない

粗い。5分刻みなので±5分はずれる。**そう書いてある画面にしてある。**

### 5-2. 管理者向け（`gw_is_hr`）

| メソッド | パス | 中身 |
|---|---|---|
| GET | `/api/devices` | 一覧とサマリ。`?deviceId=` で1台 |
| GET | `/api/devices?csv=1` | 書き出し（**書き出しも閲覧履歴に残す**） |
| PATCH | `/api/devices` | `assign` / `rename` / `suspend` / `resume` / `retire` / `note` |
| GET/PATCH | `/api/devices/alerts` | アラート一覧と、`ack` / `resolve` / `ignore` / `reopen` |
| GET/PATCH | `/api/devices/policy` | 設定 |

**GET のたびに `gw_device_views` に1行入れる。** これを忘れると片側だけ透明になる。

### 5-3. 定期処理（`api/cron/devices.js`、毎日 03:20 JST）

1. しばらく使われていない端末を `no_access` で知らせる（1台につき1回）
2. 保存期間を過ぎた `gw_device_events` / `gw_device_usage` を消す
3. 使用終了から90日を過ぎた端末を、記録ごと消す

## 6. ブラウザ側（`js/device.js`）

全ページで読み込む（`js/layout.js` の `renderChrome()` の最後で `KPDevice.start()`）。

```
1. localStorage の kp_device_uid を読む。無ければ乱数で作る
2. 画面を開いた時点で1回、そのあと5分ごとに beat
3. 画面が裏に回っているあいだは送らない（visibilitychange）
4. 表がまだ無い環境（notReady）なら止める
5. 失敗しても黙って次に回す。合図が届かないことより、画面が止まるほうが困る
```

localStorage が使えないとき（プライベートウィンドウ、保存を止めている設定）は
毎回ちがう端末に見える。動きは止めない。

### アラートの判定

| ルール | 重さ | 条件 |
|---|---|---|
| `unknown_device` | 要確認 | その人が今まで使っていなかった端末から入った（既に別の端末を持っている場合のみ） |
| `night_access` | 要確認 | 深夜の利用が60分を超えた（設定で変えられる） |
| `holiday_access` | 要確認 | 休日の利用が120分を超えた（同上） |
| `no_access` | 情報 | 60日以上使われていない（同上） |

> **深夜・休日を出すのは、働かせすぎを見つけるため**であって、
> サボりを見つけるためではない。画面の文言もそう書く。
> ここを取り違えると、この機能は社内で嫌われて終わる。

## 7. 保存期間と削除

| データ | 期間 | 消し方 |
|---|---|---|
| `gw_device_events` | 400日 | cron で日次削除 |
| `gw_device_usage` | 13か月 | cron で日次削除 |
| `gw_device_alerts` | 消さない | 対応の記録として残す |
| `gw_device_views` | 消さない | 監査のため残す |
| 使用終了の端末 | 使用終了+90日 | cron で本体ごと削除（記録も cascade で消える） |

## 9. 決めていただきたいこと

1. **就業規則の改定はいつ行うか。** ここが決まらないと運用を始められない
2. **私用端末から社内システムに入ることを、認めるか禁じるか。**
   いまは「入れるが台帳に載る」。禁じるなら、入口で止める作りが別に要る
3. **深夜・休日のアラートを、本人にも通知するか**
   （働かせすぎの是正が目的なら、本人にも出すのが筋）
4. **「使われていない」を何日にするか**（既定60日）

## 10. 前の設計（常駐エージェント）について

作らないことになったが、判断の記録として残す。

- **言語**は Go（単一バイナリ・依存なし・更新が exe 差し替えだけ）
- **2プロセス構成が必須だった。** Windows の Session 0 Isolation により、
  サービス（SYSTEM）から対話セッションのフォアグラウンドウィンドウが取れない。
  「いま何のアプリを使っているか」はサービスからは分からないので、
  ユーザーセッション側にもう1つプロセスを置き、名前付きパイプでつなぐ必要があった
- **URL→カテゴリの変換は端末の中でやる**設計だった。
  サーバに送ってから落とすと、送信経路とログに一度は全文が乗るため
- **自動更新は署名の検証を省けない。** 更新の口は、そのまま
  「全PCで任意のコードを動かせる口」になる
- 配布は MSI（WiX）、サービスは `SERVICE_AUTO_START`、
  端末シークレットは DPAPI（マシンスコープ）で保存し90日ごとに入れ替え

これを再開する判断になった場合、上の制約は変わらない。
またその場合、いまの `device_uid`（ブラウザのID）とエージェントの端末IDを
**同じ台帳の同じ行に寄せるか、別の行にするか**を先に決める必要がある。
