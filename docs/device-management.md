# 端末管理 設計

**どの端末から社内システムに入っているか**を台帳にして、
会社のパソコン以外から社内の情報が見られていないかを確かめるための仕組み。
mf.8grp.co.jp（グループウェア）の一機能。

---

## 0. 台帳は1つ、載り方は2つ

**メンバーが自分のパソコンに入れて、管理画面で一覧できる。**
IT側からの一斉配布（Intune / GPO）は要らない。

`gw_devices` の1つの表に、2通りの載り方がある。

| `source` | 何 | 分かること |
|---|---|---|
| `browser` | ブラウザの localStorage が持つID | 社内システムを開いた事実と、開いていた時間 |
| `agent` | パソコンに入れた会社のソフト | 起動終了・稼働・アプリ・サイトの種類・USB・ソフトの出入り |

**同じパソコンで両方が載る。これは重複ではない。**
「そのパソコンで何が動いているか」と
「そのパソコンから誰が社内システムに入ったか」は別のこと。
`linked_device_id` でブラウザの行からエージェントの行を指し、
管理画面ではエージェントの行の下にたたんで出す。

> **2つの「稼働時間」は別のものを数えている。**
> `source=agent` の `active_min` は**パソコンを使っていた時間**。
> `source=browser` の `active_min` は**社内システムを開いていた時間**。
> 行が別なので混ざらないが、画面では毎回どちらなのか書いてある。
> ここを取り違えると「6時間しか働いていない」のような誤読が起きる。

### なぜ両方あるのか

エージェントだけにすると、**入れていない端末から入られたことに気づけない。**
私物のスマホ、自宅のPC、退職者が持っている端末。
そこにエージェントは入っていないので、エージェントだけでは見えない。

ブラウザだけにすると、**パソコンで何が起きたかが何も分からない。**
USBにコピーされても、勝手にソフトを入れられても分からない。

両方あって、はじめて「会社の情報がどこから見られているか」と
「会社のパソコンで何が起きているか」の両方が見える。

## 1. これで何ができて、何ができないか

### できること

- **会社のパソコン以外から社内システムに入られたら気づける。**
  自宅のPC、私物のスマホ、退職者が持っている端末。
  その人が今まで使っていなかった端末から入ると、アラートが出る。
- **貸与端末の台帳が、実態と合ったまま保てる。**
  貸与品台帳（`gw_assets`）は人が更新するので、いつか実態とずれる。
  こちらは使われた時点で自動で載るのでずれない。
- **働きすぎに気づける。** 深夜・休日に社内システムを使っていた時間。
- **使われていない端末が分かる。** 退職者のアカウントが生きたまま、といった状態。

### できないこと

- **エージェントを入れていないパソコンの中身は分からない。**
  ブラウザの行から分かるのは、社内システムを開いているあいだのことだけ。
- **持ち出しそのものは止められない。** USBに挿したことは分かるが、止められない。
  止めるのは Intune / Defender / DLP の担当で、ここでは追わない。
- **ブラウザの端末を偽ることは防げない。** localStorage を消せば別の端末に見える。
  それでよい。防ぎたいのは「見慣れない端末から入られること」で、
  本人が自分の端末を隠すことではない。本気で塞ぐなら証明書（mTLS）が要り、
  それは Intune の仕事になる。
- **エージェントを消されたことは、その場では分からない。**
  24時間届かなければ `agent_silent` が出る（`api/cron/devices.js`）。
  「消したらすぐ分かる」ようにするには、消せない権限で入れる必要があり、
  それは本人が自分で入れる形とは両立しない。

### 他の仕組みとの分担

| | 担当 |
|---|---|
| **Intune** | 端末の構成管理・ポリシー配布・リモートワイプ・BitLocker・OS更新 |
| **Defender for Endpoint** | マルウェア検知・EDR |
| **この機能** | **社内システムに入ってくる端末の台帳**と、見慣れない端末・深夜休日の検知 |

## 2. 先に決めておくこと（実装より前）

### 2-1. 就業規則への明記

会社が業務端末の利用状況を継続的に記録する場合、
**就業規則（または情報セキュリティ規程）への明記と、本人への周知**が要る。
根拠は個人情報保護法（利用目的の特定・通知）と、労働契約法上の合理性。

エージェント前提だったときより取る範囲は狭いが、**明記は依然として要る**。
「社内システムを開いていた時間」は労働時間そのものではないが、
そう読めてしまう数字なので、目的をはっきりさせておく必要がある。

| 項目 | 書く内容 |
|---|---|
| 目的 | 会社の端末以外からの社内システム利用の検知、貸与端末の適正管理 |
| 取得する項目 | 端末の種類（OS・ブラウザ・画面の大きさ）／社内システムに入った日時／社内システムを開いていた時間の日別合計／そのうち深夜・休日にあたる分 |
| **取得しないもの** | キー入力・パスワード・メール本文・チャット本文・画面録画・社内システム以外で見たページ・端末に入っているソフト・USB・ファイル・PCの電源が入っていた時間 |
| 保存期間 | できごと400日 / 日別の集計13か月（設定で短くできる） |
| 見られる人 | 人事・経営者と、**本人** |
| 私用端末 | 私用端末から社内システムに入った場合、その端末も台帳に載る（載ることが目的） |

### 2-2. 本人が確認するまで、利用時間は数えない

`gw_devices.notified_at` が null のあいだ、日別の集計には**1分も入らない**。
本人が `device-consent.html` で告知を読んで「このパソコンです」を押して、はじめて数えはじめる。

これは建前ではなく、**API がそうなっている**（`api/devices/me.js` の `beat`）。
規程が間に合っていない状態で運用しても、利用時間は溜まらない。

ただし**「その端末から社内システムに入った」ことは、確認前でも残る。**
これはログインの記録であって、働き方の記録ではない。
これを残さないと「見慣れない端末から入られた」を拾えない。

### 3-2. 管理者：設定タブ

- 見慣れない端末から入られたら知らせるか
- 深夜・休日の利用を知らせるか、それぞれ何分から
- USBメモリの接続を知らせるか（エージェントのみ）
- 入れてはいけないソフト（名前の部分一致。エージェントのみ）
- 何日で「使われていない」とするか／離席とみなす時間／送信の間隔
- 保存期間（できごと・日別）

### 3-3. メンバー：`device-consent.html`

**ここが入口。** 開き方が2通りある。

**(a) ブラウザだけの人** … マイページから開く
1. いま使っている端末が上に出る（自動で載っている）
2. 記録していること／していないことを読む
3. 「このパソコンです」を押す → ここから利用時間を数えはじめる
4. 名前を変える／アプリとして入れる（PWA）／使わない端末を外す

**(b) 会社のソフトを入れた人** … エージェントが既定のブラウザで自動で開く
`device-consent.html?link=<合言葉>` が開き、その場で
- そのパソコンが**いまログインしている人のもの**になる
- そのブラウザの行から、そのパソコンを指す（`linked_device_id`）
- **追加で記録すること**（USB・アプリ・サイトの種類）が表示される
- 「このパソコンです」を押すと、そこから収集が始まる

人事が名簿から割り当てる手間が要らない。入れた本人が持ち主になる。

> **告知の文は、入れている人と入れていない人で変える。**
> 基本の告知には「パソコンに入っているソフト、USBメモリ、ファイルは取りません」
> と書いてある。エージェントを入れた人にこれをそのまま見せると**嘘になる**ので、
> `api/devices/me.js` の `noticeFor()` がその3行を外し、
> 代わりに `AGENT_NOTICE`（追加で取るもの）を出す。

### 3-4. メンバー：`mypage.html`

自分の端末・自分の利用時間・**誰がいつ自分の記録を見たか**。
見せないと「何を見られているか分からない」状態になり、それは監視になる。

## 4. DB設計

**053 → 054 の順で流す。**

### `db/053_devices.sql`（ブラウザ側）

| 表 | 中身 |
|---|---|
| `gw_devices` | 端末台帳。`device_uid` で一意。`notified_at` が収集の門 |
| `gw_device_events` | この端末に起きたこと |
| `gw_device_usage` | 日別（`active_min` / `night_min` / `holiday_min` / `beats`） |
| `gw_device_alerts` | 対応の状態を持つ。`unique (device_id, dedupe_key)` |
| `gw_device_policies` | 会社ごとに1行 |
| `gw_device_views` | **管理者が誰の記録を見たか。** 本人も読める |

### `db/054_device_agent.sql`（エージェント側）

`gw_devices` に足すもの：
`source` / `hostname` / `serial` / `os_build` / `agent_version` /
`secret_hash` / `secret_set_at` / `enrolled_by` / `enrolled_at` /
`linked_device_id` / `link_code_hash` / `link_expires_at`

新しい表：

| 表 | 中身 |
|---|---|
| `gw_device_enrollments` | 登録コード（sha256。平文は発行時に1度だけ画面に出す） |
| `gw_device_app_usage` | アプリ別。実行ファイル名だけ（パスは持たない） |
| `gw_device_web_usage` | サイト別。**カテゴリだけ**（URLもホスト名も届かない） |
| `gw_device_releases` | 配布物の版・URL・SHA256 |

`gw_device_usage` に `idle_min` / `locked_min`、
`gw_device_events` に `seq`（端末側の連番。`unique(device_id, seq)`）も足す。

> **053 は何も落とさない。**
> 一時期 053 が「使わなくなった表」を落としていたが、
> 054 でそれらが戻ってきたので、その処理は外した。
> 053 を流し直してもエージェントの列と表は消えない（PG16 で確認済み）。

RLS は全表 select のみ。書き込みは `api/devices/*`（service_role）だけ。
本人は自分の端末ぶん、人事・経営者は全件。

## 5. API設計

### 5-1. 本人向け（`api/devices/me.js`）— 社員の JWT

| メソッド | 中身 |
|---|---|
| GET | 自分の端末（両方）・利用時間・自分の記録を見た人・告知 |
| POST `{action:"beat"}` | 5分ごとの合図。**ブラウザの端末の入口でもある** |
| POST `{action:"link"}` | エージェントの案内から来たとき。パソコンと持ち主とブラウザをつなぐ |
| POST `{action:"confirm"}` | 告知を読んだ。`deviceUid`（ブラウザ）か `deviceId`（エージェント） |
| POST `{action:"installed"}` | アプリとして入れた（PWA） |
| POST `{action:"rename"}` | 端末の名前を変える |
| POST `{action:"forget"}` | 使わなくなった端末を外す（`retired`。記録は消さない） |

**利用時間の数え方**（`lib/devices.js` の `applyBeat`）

- 前の合図から **12分以内**なら、そのあいだはずっと開いていたとみなして足す
- それより空いていたら、閉じていた時間なので **1分だけ**足す
- 巻き戻った合図（端末の時計がずれている）は数えない
- 1日 1440分を超えない

粗い。5分刻みなので±5分はずれる。**そう書いてある画面にしてある。**

### 5-2. エージェント向け — 端末専用の資格情報

```
Authorization: Device <deviceId>:<secret>
```

社員のアカウントをPCに置かない。置くと、PCが盗まれた人が社員として全部できてしまう。
サーバは `sha256(secret)` を `gw_devices.secret_hash` と比べる。平文は持たない。
`source='browser'` の行はシークレットを持たないので、この口は通らない。

| メソッド | パス | 中身 |
|---|---|---|
| POST | `/api/devices/enroll` | 登録コード → `{deviceId, secret, linkUrl}`。コードは1回で失効 |
| GET | `/api/devices/config` | 収集の可否・間隔・カテゴリ表・禁止ソフト。**`notified_at` が null なら `{collect:false}`** |
| POST | `/api/devices/ingest` | まとめて送る |
| POST | `/api/devices/rotate` | シークレットの入れ替え（90日ごと） |
| GET | `/api/devices/manifest` | 最新版の版・URL・SHA256（3つそろうまで「更新なし」） |

**ingest のサーバ側の扱い**

- `events` は `seq` で重複を落とす（`upsert ... ignoreDuplicates`）
- `usage` / `apps` / `web` は**その日の値で上書き**（端末が持っている合計が正）
- 受け取ったら `last_seen_at` と `agent_version` を更新
- **判定はサーバでやる。** 端末が「重大です」と言ってきても使わない。
  休日ぶんも土日かどうかで数え直す

### 5-3. 管理者向け（`gw_is_hr`）

| メソッド | パス | 中身 |
|---|---|---|
| GET | `/api/devices` | 一覧とサマリ。`?deviceId=` で1台 |
| GET | `/api/devices?csv=1` | 書き出し（**書き出しも閲覧履歴に残す**） |
| GET | `/api/devices?enrollments=1` | 登録コードの発行・使用の履歴（監査） |
| PATCH | `/api/devices` | `issue_token` / `revoke_token` / `assign` / **`unlink`** / `rename` / `suspend` / `resume` / `retire` / `note` |
| GET/PATCH | `/api/devices/alerts` | `ack` / `resolve` / `ignore` / `reopen` |
| GET/PATCH | `/api/devices/policy` | 設定 |

**GET のたびに `gw_device_views` に1行入れる。** これを忘れると片側だけ透明になる。

**所有者変更（`assign`）**
使う人が変わったら `notified_at` を消して「本人の確認待ち」に戻す。
前の人が読んだことを、次の人の承認にはしない。
同じ人に付け直したときは、やり直させない。

**紐付け解除（`unlink`）**
パソコンとブラウザの結びつきだけを外す。**記録は何も消さない。**
間違って繋いだのを直すための操作で、消すためのものではない。
パソコン側から外すと、ぶら下がっているブラウザをまとめて外す。

**登録コード（`issue_token` / `revoke_token`）**
有効期限は発行するときに選ぶ（1・3・7・30日。既定7日）。
**発行も使用も監査ログに残す。**

| ログ | いつ | 中身 |
|---|---|---|
| `device.token_issued` | 発行したとき | 発行者（actor）・宛先・期限・日数 |
| `device.token_used` | 端末が使ったとき | どの端末・ホスト名・発行者・発行日時 |
| `device.token_revoked` | 取り消したとき | 取り消した人（actor） |

**使ったコードも取り消したコードも、行は消さない。**
消すと「誰がいつ何に使ったか」まで消えて、監査の役に立たなくなる。
使われてしまったコードは取り消せない（`409`）。
そのときは端末のほうを停止する、と画面にもそう書いてある。

管理者が触った操作は、`gw_devices.admin_touched_*` にも残る。
一覧を見たときに「最近誰かが動かした」と分かるようにするため。
くわしい経緯は `gw_activity_log`。

### 5-4. 定期処理（`api/cron/devices.js`、毎日 03:20 JST）

1. 24時間届かないエージェントを `agent_silent` で知らせる（1日1件）。
   管理画面では **「未通信」** として一覧のいちばん上に出て、タブで絞り込める
2. しばらく使われていないブラウザを `no_access` で知らせる（1台1回）
3. 保存期間を過ぎた記録を消す
4. 使用終了から90日を過ぎた端末を、記録ごと消す

## 6. ブラウザ側（`js/device.js`）

全ページで読み込む（`js/layout.js` の `renderChrome()` の最後で `KPDevice.start()`）。

```
1. localStorage の kp_device_uid を読む。無ければ乱数で作る
2. 画面を開いた時点で1回、そのあと5分ごとに beat
3. 画面が裏に回っているあいだは送らない（visibilitychange）
4. 表がまだ無い環境（notReady）なら止める
5. 失敗しても黙って次に回す。合図が届かないことより、画面が止まるほうが困る
```

**どの画面を開いていたかは送らない。** 送ると、それは行動の記録になる。

## 7. エージェント（`agent/`）

くわしくは `agent/README.md`。要点だけ。

- **Go。単一バイナリ。** 依存が無いので、更新は exe の差し替えだけで済む
- **2プロセス構成が必須。** Windows の Session 0 Isolation により、
  サービス（SYSTEM）からは対話セッションのフォアグラウンドウィンドウが取れない
- **URL→カテゴリの変換は UI プロセスの中で終わらせる。**
  サーバに送ってから落とすと、送信経路とログに一度は全文が乗る
- **待ち行列は1行1JSONの追記ファイル。** SQLite を使うと cgo が要る。
  溜めるのは未送信のできごとだけで、多くても数千件
- 上限を超えたら**古いほうから**捨てる。新しいほうが対応に要る
- シークレットは DPAPI（マシンスコープ）で包んで `%ProgramData%\EIGHT\`
- **取ってはいけないAPIを呼んでいないことを、テストで確かめている**
  （`internal/collect/forbidden_test.go`）

### アラートの判定（すべてサーバ側）

| ルール | 重さ | 条件 | どちらから |
|---|---|---|---|
| `unapproved_software` | 重大 | 禁止ソフトが入った | エージェント |
| `usb_attach` | 要確認 | USB大容量記憶装置が接続された | エージェント |
| `night_work` / `holiday_work` | 要確認 | 深夜60分／休日120分を超えた | エージェント |
| `agent_error` | 要確認 | エージェントがエラーを報告 | エージェント |
| `agent_silent` | 要確認 | 24時間以上届かない（＝止められた／起動していない／通信できない） | cron |
| `unknown_device` | 要確認 | その人が使っていなかった端末から入った | ブラウザ |
| `night_access` / `holiday_access` | 要確認 | 深夜60分／休日120分を超えた | ブラウザ |
| `no_access` | 情報 | 60日以上使われていない | cron |

> **深夜・休日を出すのは、働かせすぎを見つけるため**であって、
> サボりを見つけるためではない。画面の文言もそう書く。
> ここを取り違えると、この機能は社内で嫌われて終わる。
