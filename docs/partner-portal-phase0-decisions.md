# ENGER パートナー営業ポータル — Phase 0 意思決定・既存Sales起点の確定要件

- 決定日：2026-11-15
- 関連：`docs/partner-portal-phase0.md` および「ENGER パートナー営業ポータル 要件定義書」
- 実装状況：決定事項の記録のみ（コード・DBの変更なし）

## 最優先の方針

**新しいログイン画面も、別の商談ナビも作らない。共通入口は `https://enger.jp/business/login` に変更する（2026-11-15追補）。**
企業担当者・Sales社員・営業パートナーが同じログインデザインとURLを使い、認証後に**サーバ側の正規の権限判定**で企業ポータル／Sales社員／割当企業限定のパートナー画面に振り分ける。既存Salesの**「商談を始める」**を起点に既存6ステップ商談ナビを共用する。社内は契約・CS・請求・入金を担当。

既存Salesの社員権限を社外へ付与することは禁止。画面は既存UIを再利用しても、パートナー用APIと所有者スコープは独立させる。

## D-1～D-7決定

| ID | 決定 |
|---|---|
| D-1 | **新規パートナー専用台帳＋`partner_sales`アプリ権限**。 `gw_guests` の流用・`gw_employees` 社員扱い・既存`sales`付与はしない |
| D-2 | 人材供給側の`partner_organizations`とは別概念の`sales_partner`として扱う |
| D-3 | **新しい営業状態表を作らない**。企業営業状態は`enger.dx2_sales_pipeline.status`、提案・案件化以降は既存Salesの提案・商談・dealを正とし、パートナー画面は派生表示のみ |
| D-4 | 同一企業の商談は**割当パートナー主担当・社員は同席可**、既存1社1active制約を維持。進行中の社員商談は強制終了しない。管理者移管・担当変更は履歴保存。二重実績・二重報酬は防止 |
| D-5 | パートナーは企業招待の「依頼」まで。発行・パスワード・再発行は社内のみ。既存ENGER BUSINESSログインを利用 |
| D-6 | パートナーには**企業に提案可能と確認された公開承認済み候補のみ**返す。全件匿名talent-listはこの導線で利用しない。既存企業側全件一覧の存否は別判断 |
| D-7 | 報酬の率・対象・期間・確定・支払期日はPhase 2着手前に承認。企業から受け取る`gw_sales_success_fees`とパートナー報酬台帳は分ける |

## 既存Salesを利用したパートナーの操作順

1. **既存ENGER BUSINESSログイン (`enger.jp/business/login`)** → サーバ権限判定 → パートナー用の制限されたSales表示。Sales社員も同入口を利用でき、法人ユーザーは既存企業ポータルへ。
2. 今日やること → **割当企業一覧のみ** → 企業詳細・会社サマリー・公開候補。
3. 承認された案件・人材を選択して提案。下書き・送信・重複防止・提案時スナップショット。
4. 企業詳細の既存**「商談を始める」**から既存6ステップ（4/2/7/10/4/3分）を進める。未実施・商談済み・事後登録を区別し、自動保存。
5. オファー・再提案・検討中・見送りを記録。必要に応じて企業ポータルの案内発行を社内へ依頼。
6. **Officeの既存契約依頼キューに引き継ぎ**。パートナーは自身の対応状況・KPI（Phase 2では報酬）を確認。
7. 社内担当が条件確定、契約、参画、請求・入金、継続CSを担当。

## 絶対条件（PR1とその後）

- **PR1（MF）は認可基盤のみ**：`partner_sales`追加、既存`canSell`は変更しない、パートナーの既存`/api/sales/*`アクセス全拒否、既存社員のアクセス非退行テスト。パートナー公開はPR1だけで行わない。
- パートナー用`/api/partner/*`では、認証・契約有効性・本人ID・テナント・割当企業を**サーバー側**で検証。service_role利用時も必ず確認。割当外企業・他人の履歴・原価・個人情報は返さない。
- ENGER DXで**提案可能判定を一元化し送信時再検証**。status、ゴミ箱、終了、stale、所属・募集確認、公開許可、企業除外を適用。不明・失敗はfail-closed。二重送信防止を設ける。
- 本番DBのテーブル・列・制約は、**マイグレーション前に読み取りで実測**する。DB書き込みはレビュー前に行わない。
- HR2週間トライアル・Office契約は既存機能を使用。トライアルの外部利用開始前に社内で契約確認・期限付権限を承認する（本格自動連携はPhase 2）。
- KPI：2週間で20社アプローチ・10有効提案・1有効商談（仮説）。10提案→1商談の目安、15提案0商談で改善アラート。商談実施とメール送信は別定義、重複計上なし。


## D-8（2026-11-15追補）：共通ログイン入口・デザイン統一

- **入口は `https://enger.jp/business/login` に固定**。新しいログインフォーム、役割選択画面、パートナー専用ログインURLは作らない。
- 写真入り左ペイン＋右側白カードの現行ENGER BUSINESSデザインを維持。基調：背景 `#F6F3EC`、文字 `#3E4C5E`、主CTA `#C0521F`、白カード、丸いCTA、Zen Kaku Gothic New。法人専用だった見出し・文言のみ共通利用者向けに変更する。
- ログインフォームは「企業IDまたはメールアドレス」「パスワード」「表示切替」「再設定」「ログイン」のまま。企業IDは企業担当者のみ、Sales社員・パートナーは各自のメールでログイン。役割は入力値やフロント表示から推定せずサーバで決定する。
- **現状の技術的制約**：enger-lp `src/pages/api/auth/login.ts` は `variant='business'` と `isBusinessMeetingUser` により非法人を403で拒否し、`app_metadata.apps` のbusiness判定でサイトを振り分ける。社員・パートナーを法人扱いにして迂回してはいけない。ログイン認証と利用権限の判定・遷移先決定を分離し、既存法人・フリーランスへの影響なしを検証する。
- **別オリジンのセッション引き継ぎは要実装**：`enger.jp` と `gw.8grp.co.jp` 間のCookie/localStorageをそのまま共用できない。MFは `js/api-client.js` の`kp_session`（Bearer）とMFAを利用。安全な、期限付きワンタイム認可コードのサーバ間交換などを設計・レビューし、JWT／refresh token／パスワードをURLに載せない。MFAを回避させず、なりすまし・リプレイ・open redirectを防止。
- **認証後の振り分け**：企業→既存 `/business/dashboard` または企業専用商談、Sales社員→既存Salesの業務画面、営業パートナー→割当企業限定のSales表示。複数権限はサーバが許す作業コンテキストのみ選択可能とし、暗黙の企業権限付与は禁止。
- **ログイン後デザインも統一**：背景クリーム／白カード／濃いグレーの文字／オレンジの主CTAを原則に、社員は既存機能を維持し、パートナーは「今日やること・企業/提案・商談・成果」の4ナビに限定。商談ナビの業務機能・進捗データは共通化する。
- **PR着手順**：PR1の社外権限分離を先行し、ログイン統合は専用PRとして後続化する。権限分離とSSOの検証完了前に社員・パートナーへ公開しない。
- **追加受入条件**：企業IDログイン無変更、社員メールログイン、パートナーメールログイン、契約停止、割当外企業404、戻る/再ログイン、MFA、別オリジンの認証・ログアウト、セッション期限切れ、他ロール誤転送なし、スマホ幅でUI崩れなし。

## PRの進め方

Phase 0の調査はそのまま。**PR1：MFの権限基盤と社員非退行テストから開始可能。**
PR2：パートナー台帳・割当 → PR3：ENGER提案可否の一元判定 → PR4：署名付き最小候補API → PR5：パートナーAPI → PR6：既存Sales入口を使う専用表示 → PR7：既存「商談を始める」のパートナー対応 → PR8：オファー帰属とOffice引き継ぎ → PR9：KPI。Phase 2でHR人物ID連携・報酬台帳・報酬明細。

各PRで関連する陰性テスト、社員の非退行テスト、画面確認結果を提出する。**パートナーへの本番開放と本番マージは別途承認**とし、まず3人程度の機能フラグ下で検証する。
